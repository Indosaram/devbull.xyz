nginx 설정 리로드는 프로세스를 내리지 않고 설정을 다시 읽어 새 연결부터 적용하는 방법이에요. 재시작과 달리 기존 연결을 끊는 것을 피하려고 쓸 때가 많아요. 문법 오류가 있으면 리로드는 거절되고, 이미 돌던 프로세스는 이전 설정을 유지하는 쪽이 일반적이에요. 아래는 백업, 검사, 리로드, 확인과 환경별 명령 차이예요.

![nginx 설정 리로드 쉽게 하는 법 소제목 카드. 한눈에 보기, 리로드와 재시작은 무엇이 다른가요, 단계별로 리로드하는 방법, 상황별 선택 가이드](/static/images/nginx-seoljeong-rirodeu/diagram.webp)

## 한눈에 보기

고친 파일이 실행 중인 nginx가 읽는 경로인지 먼저 확인해요. 백업 뒤 문법 검사를 하고, 통과하면 리로드해요. 반영 여부는 오류 로그와 테스트 요청으로 봐요. systemd, 컨테이너, 직접 실행은 리로드를 보내는 방법이 달라요.

## 리로드와 재시작은 무엇이 다른가요

리로드는 마스터가 설정을 다시 읽고 워커를 교체하는 쪽에 가까워요. 재시작은 서비스를 멈췄다가 다시 띄워요. 연결을 유지해야 하면 리로드가 기본 선택이에요. 바이너리 교체나 일부 프로세스 구성 변경은 리로드만으로 안 될 수 있으니 문서를 봐요.

| 항목 | 리로드 (`nginx -s reload`) | 재시작 (`systemctl restart nginx`) |
| --- | --- | --- |
| 하는 일 | 마스터가 설정을 다시 읽고 새 워커를 띄움 | 프로세스를 완전히 종료한 뒤 다시 실행 |
| 처리 중인 요청 | 기존 워커가 끝까지 처리 | 시점에 따라 끊길 수 있음 |
| 설정이 잘못된 경우 | 적용을 거부하고 이전 설정으로 계속 동작 | 서비스가 내려갈 수 있음 |
| 주로 쓰는 때 | 설정 값만 바꿨을 때 | 바이너리 교체, 프로세스 비정상, 리로드가 먹히지 않을 때 |
| 서비스 중단 | 사실상 없음 | 짧게 발생 |

## 단계별로 리로드하는 방법

백업, 검사, 리로드, 확인을 한 세트로 두면 실패해도 돌아갈 파일이 있어요.

### 1. 지금 설정을 백업해요

실행 중인 설정과 include된 파일을 함께 복사해 둬요. 저장소와 서버 파일이 다르면 어느 쪽이 원본인지도 적어요. 백업 없이 리로드하면 롤백이 추측이 돼요.

### 2. nginx -t로 문법을 검사해요

검사 대상 경로가 운영 설정과 같은지 확인해요. 실패하면 메시지의 파일과 줄을 고치고 다시 검사해요. 통과 전에는 리로드하지 않아요.

### 3. 리로드를 실행해요

패키지 설치면 서비스 관리자로 리로드하고, 직접 실행이면 마스터에 리로드 신호를 보내요. 둘은 대상 프로세스가 같아야 같은 결과예요. 다른 경로의 바이너리를 리로드하면 고친 파일이 안 읽혀요.

### 4. 반영 결과를 확인해요

오류 로그에 설정 읽기 실패가 없는지 봐요. 테스트 요청이 기대한 server와 업스트림으로 가는지 확인해요. 안 바뀌면 include되지 않은 파일을 고친 경우가 많아요.

## 상황별 선택 가이드

환경마다 리로드를 전달하는 입구가 달라요. 아래는 그 입구만 나눈 거예요.

### systemd로 관리하는 서버

systemctl reload를 쓰면 유닛이 관리하는 프로세스에 신호가 가요. nginx -s reload와 대상이 같아야 해요. 유닛이 다른 설정 경로를 쓰면 그 경로를 고쳐야 해요.

### 직접 컴파일해서 쓰는 서버

마스터 pid 파일의 프로세스에 리로드 신호를 보내요. pid 파일이 옛 프로세스를 가리키면 반영이 안 돼요. 바이너리와 설정 경로를 같이 확인해요.

### 컨테이너 환경

컨테이너 안의 nginx에 리로드를 보내거나, 설정을 마운트한 뒤 그 프로세스에 신호를 보내요. 컨테이너를 재만들면 리로드가 아니라 재생성이에요. 호스트의 nginx와 헷갈리지 마세요.

### 쿠버네티스 ingress

인그레스 컨트롤러가 설정을 만들어 리로드하는 구조가 많아요. 컨트롤러 설정을 직접 고치면 다음 동기화에 덮일 수 있어요. 인그레스 자원과 컨트롤러 로그를 같이 봐요.

### 배포 파이프라인

파이프라인은 검사 실패 시 리로드를 건너뛰게 나눠요. 성공해도 헬스 체크로 새 설정이 트래픽을 받는지 확인해요. 롤백은 백업 설정으로 다시 검사하고 리로드하는 순서예요.

## 주의할 점

문법 오류가 있는 리로드는 거절되는 편이지만, 이미 받은 연결의 동작까지 검증하지는 않아요. 워커 수 변경처럼 프로세스 구성이 바뀌는 항목은 문서를 보고 재시작이 필요한지 판단해요. 여러 사람이 다른 파일을 동시에 고치면 include 순서가 마지막 값을 덮어요.

## 자주 묻는 질문

명령 차이, 반영이 안 되는 이유, 연결 유지, 오류 시 중단, 컨테이너가 자주 나와요.

### nginx -s reload와 systemctl reload nginx는 같은 건가요?

둘 다 리로드를 요청하지만, 신호가 가는 프로세스가 같아야 같은 일이에요. systemd 유닛이 다른 pid를 관리하면 결과가 달라요. 운영에서는 그 서버를 띄운 방법으로 통일하는 편이 좋아요.

### 리로드했는데 설정이 그대로인 것 같아요.

다른 파일을 고쳤거나, 다른 프로세스에 신호를 보낸 경우가 많아요. 열린 설정 경로와 include를 다시 따라가요. 캐시된 응답을 새 설정으로 오해하는 경우도 있어요.

### 리로드 중에도 요청이 끊기지 않나요?

기존 연결을 유지하려는 동작이 목적이에요. 다만 업스트림이 바뀌면 새 연결부터 다른 대상으로 갈 수 있어요. 끊김이 없어야 하는 변경은 헬스 체크와 함께 봐요.

### 설정에 오류가 있으면 nginx가 멈추나요?

이미 돌고 있는 프로세스에 대한 리로드는 오류면 거절되고 이전 설정이 남는 쪽이 일반적이에요. 처음 기동은 오류면 뜨지 않아요. 그래서 기동 전 검사가 더 중요해요.

### 컨테이너 안에서는 어떻게 하나요?

컨테이너 안의 마스터에 리로드를 보내요. 컨테이너를 지우고 다시 만드는 것은 리로드가 아니에요. 설정 마운트가 컨테이너 경로와 맞는지 확인해요.

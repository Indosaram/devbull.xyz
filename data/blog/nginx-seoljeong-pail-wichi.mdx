nginx 설정 파일 위치는 대부분 `/etc/nginx/nginx.conf`이지만, 설치 방식과 배포판에 따라 달라질 수 있어요. 그래서 경로를 외우기보다 `nginx -V`와 `nginx -t`로 지금 서버가 실제로 읽는 파일을 확인하는 편이 안전합니다. 이 글은 공식 문서에 나온 기본 경로와 확인 절차를 순서대로 정리하고, 배포와 운영 중에 자주 헷갈리는 지점을 짚어요.

## 한눈에 보기

nginx는 최상위 설정 파일 하나를 읽고, 그 안의 `include` 지시어로 나머지 파일을 끌어오는 구조입니다. 그래서 "설정 파일 위치"는 두 갈래로 나뉘어요. nginx가 시작할 때 여는 진입 파일이 하나이고, 그 파일이 불러오는 사이트별·모듈별 조각 파일이 또 하나입니다.

패키지로 설치했다면 진입 파일은 대개 `/etc/nginx/nginx.conf`입니다. 다만 소스 컴파일, 공식 컨테이너 이미지, 개발자 노트북의 패키지 관리자처럼 설치 경로가 다른 경우가 있으므로, 운영 서버에서는 추측보다 명령으로 확인하는 편이 정확해요.

확인에 쓰는 명령은 다음 네 가지로 충분합니다.

- `nginx -V` : 빌드할 때 지정된 설정 경로(`--conf-path`)와 컴파일 옵션을 보여줍니다.
- `nginx -t` : 설정 문법을 검사하면서 실제로 읽은 파일 경로를 함께 출력합니다.
- `nginx -T` : `include`로 끌어온 파일까지 전부 이어 붙여 출력합니다.
- `systemctl status nginx` : systemd 유닛이 어떤 바이너리와 인자를 사용하는지 보여줍니다.

여기서 중요한 점은 `nginx -t`와 `nginx -T`가 "문법 검사"와 "전체 덤프"라는 서로 다른 목적을 가진다는 사실이에요. 경로만 빨리 확인하고 싶다면 `nginx -t`가 짧고, 어떤 파일이 어떤 순서로 합쳐졌는지 보고 싶다면 `nginx -T`가 맞습니다.

## 배포판·설치 방식별 설정 파일 위치 비교

아래 표는 공식 문서와 각 배포판 패키지의 관례를 기준으로 정리한 기본값입니다. 실제 경로는 운영 환경에서 `nginx -V`와 `nginx -T`로 다시 확인해 주세요.

| 구분 | 진입 설정 파일 | 사이트별 설정 | 비고 |
| --- | --- | --- | --- |
| Debian·Ubuntu 패키지 | `/etc/nginx/nginx.conf` | `/etc/nginx/sites-available`, `/etc/nginx/sites-enabled` | `sites-enabled`는 보통 심볼릭 링크 모음이에요 |
| RHEL·Rocky·Alma 패키지 | `/etc/nginx/nginx.conf` | `/etc/nginx/conf.d/*.conf` | `server` 블록을 파일 단위로 나눠 두는 관례가 많아요 |
| 소스 컴파일 설치 | `/usr/local/nginx/conf/nginx.conf` | 직접 `include`로 지정 | `--prefix` 값에 따라 경로가 달라져요 |
| 공식 컨테이너 이미지 | `/etc/nginx/nginx.conf` | `/etc/nginx/conf.d/*.conf` | 호스트 파일을 마운트해 덮어쓰는 방식이 일반적이에요 |
| 개발용 패키지 관리자(macOS) | 패키지 관리자가 안내하는 접두 경로 아래 `etc/nginx/nginx.conf` | 같은 디렉터리의 `servers` 등 | 설치 안내에 출력되는 경로를 그대로 쓰면 됩니다 |

표에서 눈여겨볼 부분은 진입 파일 이름이 거의 같다는 점이에요. 이름이 같아서 "무조건 `/etc/nginx/nginx.conf`"라고 단정하기 쉽지만, 소스 컴파일이나 컨테이너에서는 접두 경로가 달라집니다. 결국 이름보다 "이 프로세스가 어떤 파일을 여는가"를 확인하는 절차가 핵심이에요.

## 단계별로 설정 파일 위치 확인하기

**첫 단계, 실행 중인 프로세스부터 봅니다.** `ps -ef | grep nginx`로 master 프로세스의 실행 인자를 확인해요. 여기에 `-c` 옵션이 붙어 있다면 기본 경로가 아니라 사용자가 지정한 파일을 읽고 있다는 뜻입니다. `systemctl status nginx`를 함께 보면 유닛 파일이 어떤 바이너리를 실행하는지도 알 수 있어요.

**두 번째, 빌드 옵션에서 기본 경로를 확인합니다.** `nginx -V`를 실행하면 configure 인자가 한 줄로 출력되고, 그 안에 `--conf-path=` 항목이 들어 있습니다. 패키지 배포본은 이 값이 배포판 관례에 맞게 지정되어 있고, 소스 컴파일은 설치할 때 준 값이 그대로 남아요.

**세 번째, 문법 검사로 실제 경로를 확인합니다.** `nginx -t`를 실행하면 검사 결과와 함께 `configuration file ... test is successful` 형태의 메시지가 나옵니다. 이 메시지에 찍히는 경로가 지금 설정을 읽을 때 쓰는 진입 파일이에요. 실패 메시지가 나온다면 그 안에 문제가 된 파일 경로와 줄 번호가 함께 표시되므로, 위치를 찾는 데 오히려 도움이 됩니다.

**네 번째, include 체인을 따라갑니다.** 진입 파일을 열어 `include` 줄을 확인하세요. `include /etc/nginx/conf.d/*.conf;`처럼 디렉터리 전체를 받는 형태가 흔합니다. 이때 와일드카드는 파일 이름 순서로 확장되므로, 같은 `server_name`이 여러 파일에 있으면 어느 쪽이 우선인지 헷갈릴 수 있어요.

**다섯 번째, 전체 덤프로 최종 확인합니다.** `nginx -T`는 진입 파일과 `include`된 파일을 모두 합쳐서 출력합니다. 운영 서버에서 "내가 고친 파일이 정말 로드되고 있나"를 확인할 때 가장 확실한 방법이에요. 출력이 길기 때문에 `nginx -T | grep -n "server_name"`처럼 필요한 부분만 걸러 보는 편이 실용적입니다.

**컨테이너 환경이라면 한 단계가 더 필요합니다.** 호스트에서 파일을 고쳐도 컨테이너 안의 경로에 마운트되어 있지 않으면 반영되지 않아요. `docker exec`로 컨테이너에 들어가 `nginx -T`를 실행하고, 마운트 설정은 실행 옵션이나 오케스트레이션 정의에서 확인하세요.

## 상황별 선택: 어느 파일을 고쳐야 하나

새 도메인이나 사이트를 추가할 때는 진입 파일을 직접 건드리지 않는 편이 좋아요. Debian 계열이라면 `sites-available`에 파일을 만들고 `sites-enabled`에 링크를 걸고, RHEL 계열이나 컨테이너라면 `conf.d` 아래에 파일을 하나 더하는 방식이 관리하기 쉽습니다. 진입 파일은 `include`와 전역 설정만 남겨 두면 변경 이력이 깔끔해져요.

리버스 프록시나 업스트림 설정처럼 특정 사이트에 속한 내용은 해당 사이트 파일의 `server`·`location` 블록 안에 넣습니다. 반대로 워커 프로세스 수, 연결 수 한도, 로그 포맷처럼 서버 전체에 걸리는 항목은 `nginx.conf`의 최상위 또는 `http` 블록에 두는 것이 맞아요. 어느 블록에 어떤 지시어가 올 수 있는지는 공식 문서의 지시어 문맥(context) 표기가 기준입니다.

개발 장비에서 여러 프로젝트를 오가며 설정을 바꾼다면, 프로젝트별 파일을 따로 두고 심볼릭 링크로 켜고 끄는 방식이 편합니다. 링크만 바꾸면 되돌리기도 쉬워요.

## 주의할 점

설정을 고친 뒤에는 반드시 `nginx -t`로 먼저 검사하세요. 문법 오류가 있는 상태로 재시작하면 서비스가 내려갈 수 있지만, 검사를 통과한 뒤 `systemctl reload nginx`로 완화 적용하면 기존 연결을 유지한 채 새 설정을 반영할 수 있습니다.

같은 `server_name`과 같은 포트 조합이 두 파일에 존재하면 nginx는 먼저 읽은 쪽을 사용하고 나머지는 무시합니다. 이때 `conflicting server name` 경고가 로그에 남으므로, 사이트를 추가한 뒤에는 에러 로그를 한 번 확인하는 습관이 필요해요. `default_server`를 여러 블록에 중복 지정하는 경우도 같은 종류의 문제를 만듭니다.

패키지 관리자로 설치한 경우 업그레이드 과정에서 배포판이 제공하는 기본 설정 파일이 다시 배치될 수 있습니다. 운영 설정을 진입 파일에 몰아넣기보다 별도 파일로 분리해 두면 이런 상황에서 되돌리기 쉬워요. 심볼릭 링크로 사이트를 활성화했다면 링크 대상 경로가 유효한지도 함께 확인하세요.

## 자주 묻는 질문

### nginx 설정 파일이 안 보이면 어떻게 하나요?

패키지가 아니라 소스 컴파일이나 컨테이너로 설치했다면 `/etc/nginx` 자체가 없을 수 있어요. 이때는 `nginx -V`로 `--conf-path` 값을 확인하고, `nginx -t`가 출력하는 경로를 그대로 따라가면 됩니다. 프로세스 실행 인자에 `-c`가 붙어 있는지도 함께 확인해 보세요.

### nginx.conf와 conf.d 중 어디에 넣어야 하나요?

진입 파일에는 `include`와 서버 전역 설정만 두고, 사이트 단위 설정은 `conf.d`나 `sites-available` 쪽에 두는 것이 일반적입니다. 다만 파일이 몇 개 없는 소규모 구성이라면 한 파일에서 관리해도 동작에는 차이가 없어요. 중요한 것은 같은 `server_name`을 여러 파일에 중복으로 두지 않는 것입니다.

### 설정을 바꿨는데 반영이 안 되는 것 같아요.

`nginx -T`로 실제 로드된 설정을 덤프해서 내가 고친 내용이 포함되어 있는지 먼저 확인하세요. 내용이 없다면 다른 경로의 파일을 고쳤거나, 컨테이너 마운트가 어긋난 경우입니다. 내용이 있는데도 동작이 그대로라면 완화 적용이 아니라 재시작이 필요했는지, 또는 앞선 `server` 블록이 우선하고 있는지 확인해 보세요.

### 컨테이너 안의 설정 파일은 어떻게 확인하나요?

`docker exec`로 컨테이너에 들어가 `nginx -t`와 `nginx -T`를 실행하면 이미지가 실제로 읽는 경로를 알 수 있어요. 호스트에서 수정한 파일이 반영되지 않는다면 마운트 대상 경로가 이미지의 설정 경로와 일치하는지 확인해야 합니다. 설정을 이미지에 굽는 방식이라면 이미지를 다시 빌드해야 반영돼요.

## 한눈에 보기

Railway는 애플리케이션과 데이터베이스를 같은 프로젝트 안에서 같이 관리하는 클라우드 배포 플랫폼이에요. 구조는 크게 프로젝트, 서비스, 환경이라는 세 층으로 나뉘어요. 서비스는 실제로 실행되는 애플리케이션 또는 데이터베이스이며, 환경은 같은 구성을 여러 벌로 나눠 쓰는 단위예요. 프로젝트는 배포 단위를 묶는 최상위 그릇이에요. 운영 환경과 스테이징 환경을 따로 가져가는 식이에요. 예를 들면 하나의 프로젝트 안에 API 서버 서비스와 Postgres 서비스를 둬요.

배포는 대체로 저장소에 코드를 밀어 넣는 순간 시작돼요. 플랫폼이 코드를 받아 의존성을 설치하고 빌드한 뒤 실행 가능한 이미지로 만들어 컨테이너를 띄워요. 이 일련의 과정이 배포 목록에 단계별로 남기 때문에 어디서 실패했는지 로그로 바로 좁힐 수 있어요. 헬스체크가 통과하면 공개 도메인으로 트래픽을 받기 시작해요.

여기서 중요한 전제가 하나 있어요. Railway는 서버 관리 부담을 가져가는 대신, 애플리케이션이 설정을 환경 변수로 받고 상태를 로컬 디스크에 쌓지 않는 구조여야 해요. 이 전제만 지키면 언어와 프레임워크는 크게 가리지 않아요.

## Railway 배포가 처리하는 일

직접 서버를 운영할 때와 비교하면 역할 분담이 꽤 선명해요. 아래 표는 Railway가 가져가는 몫과 개발자가 정해야 하는 몫을 정리한 것이에요.

| 항목 | Railway가 처리하는 부분 | 개발자가 정하는 부분 |
| --- | --- | --- |
| 빌드 | 저장소 언어와 프레임워크 감지, 의존성 설치, 이미지 생성 | 빌드 명령, Dockerfile 사용 여부, 루트 디렉터리 |
| 실행 | 컨테이너 스케줄링, 재시작 정책 적용, 헬스체크 감시 | 시작 명령, 수신 포트, 헬스체크 경로 |
| 네트워크 | 공개 도메인 발급, 인증서 갱신, 내부 사설망 구성 | 도메인 연결, 공개할 서비스 범위 |
| 설정 | 환경 변수 주입, 시크릿 보관 | 변수 이름과 값, 환경별 분기 |
| 저장 | 볼륨 마운트, 데이터베이스 서비스 실행 | 마운트 경로, 백업 정책 |
| 관측 | 빌드 로그와 실행 로그 수집, 기본 메트릭 제공 | 알림 기준, 로그 활용 방식 |

표에서 눈에 띄는 부분은 실행과 네트워크예요. 도메인과 인증서는 자동으로 붙어요. 컨테이너가 죽으면 정책에 따라 다시 띄우요. 대신 배포할 때마다 컨테이너가 새로 뜨기 때문에, 애플리케이션이 시작되는 동안의 짧은 공백을 어떻게 다룰지가 운영 설계의 몫으로 남아요.

## 빌드 방식 비교

Railway는 소스 저장소를 그대로 올리는 방식과 이미지 기반 배포를 모두 지원해요. 프로젝트 성격에 따라 선택이 갈려요.

| 방식 | 동작 | 어울리는 경우 |
| --- | --- | --- |
| 자동 감지 빌드 | 저장소를 보고 언어와 프레임워크를 판단해 빌드 절차를 구성 | 별도 설정 없이 빠르게 올리고 싶은 신규 서비스 |
| Dockerfile 빌드 | 저장소의 Dockerfile로 이미지를 생성 | 로컬과 운영 환경을 동일하게 맞추고 싶은 서비스 |
| 이미지 지정 배포 | 외부 레지스트리에 있는 이미지를 그대로 실행 | CI에서 이미 만든 산출물을 재사용하는 파이프라인 |

빌드 결과가 플랫폼 판단에 의존해요. 자동 감지 방식은 편해요. 이미지 크기와 빌드 시간을 직접 관리해야 해요. 반대로 Dockerfile을 쓰면 재현성은 올라가요. 모노레포처럼 저장소 안에 여러 애플리케이션이 있다면 서비스마다 루트 디렉터리와 빌드 명령을 명시적으로 지정하는 편이 안전해요.

## 단계별로 배포하는 방법

### 프로젝트와 서비스 만들기

대시보드에서 새 프로젝트를 만들면 기본 환경이 같이 생겨요. 여기에 서비스를 추가하는 방식인데, 빈 서비스로 시작해 저장소를 붙이거나, 템플릿에서 출발하거나, 데이터베이스 서비스를 먼저 띄울 수 있어요. 데이터베이스를 먼저 만들면 접속 정보가 변수로 자동 생성되므로 애플리케이션 서비스를 붙일 때 그대로 참조하면 돼요.

### 저장소 연결하기

GitHub 저장소를 연결하면 지정한 브랜치에 커밋이 들어올 때마다 자동 배포가 걸려요. 이때 저장소 접근 권한 범위를 어디까지 줄지, 어떤 브랜치를 배포 트리거로 삼을지, 자동 배포를 켤지를 같이 정해야 해요. 운영 브랜치와 개발 브랜치를 분리해 두면 실수로 개발 코드가 운영에 올라가는 사고를 줄일 수 있어요.

### 빌드 설정 다듬기

저장소에 설정 파일을 두어 코드로 관리할 수도 있어요. 설정은 대시보드에서 바꿀 수도 있어요. 빌드 명령, 시작 명령, 헬스체크 경로, 재시작 정책 같은 항목을 파일로 두면 변경 이력이 남고 환경별로 같은 규칙을 반복 적용하기 쉬워요. 설정 파일과 대시보드 값이 다를 때 무엇이 우선인지는 공식 문서에서 확인하고 한쪽으로 통일하는 편이 좋아요.

### 환경 변수와 데이터베이스 연결

설정값은 전부 환경 변수로 주입하는 것이 기본이에요. 데이터베이스 접속 정보처럼 서비스 사이에서 공유되는 값은 다른 서비스의 변수를 참조하는 형태로 연결하면, 접속 정보가 바뀌어도 애플리케이션 쪽을 손대지 않아도 돼요. 시크릿은 저장소에 커밋하지 말고 플랫폼 변수로만 관리해요.

### 네트워크와 도메인 붙이기

공개가 필요한 서비스는 도메인을 발급받아 외부에서 접근할 수 있게 해요. 인증서 발급과 갱신은 플랫폼에 맡기는 흐름이 일반적이에요. 직접 가진 도메인을 쓰려면 DNS에 레코드를 추가해요. 반대로 데이터베이스나 내부 API는 공개 도메인을 붙이지 않고 사설망 주소로만 통신하도록 두는 것이 안전해요.

### CLI로 배포하기

대시보드 없이 터미널에서 밀어 올릴 수도 있어요. 프로젝트를 초기화하거나 기존 프로젝트에 연결한 다음, 현재 디렉터리를 배포하는 흐름이에요. CLI를 설치한 뒤 로그인해요. 로그 확인과 변수 조회도 같은 도구로 처리할 수 있어요. 명령은 공식 문서의 CLI 안내를 그대로 따르면 돼요. 저장소 연동 없이 로컬 산출물만 올리고 싶을 때 유용해요.

### 배포 확인과 롤백

배포가 끝나면 빌드 로그와 실행 로그를 나눠서 봐야 해요. 실행 실패는 환경 변수 누락이나 포트 불일치인 경우가 많아요. 빌드 실패는 의존성이나 빌드 명령 문제인 경우가 많요. 문제가 생겼을 때는 이전 배포를 다시 올리는 방식으로 되돌려요. 다만 롤백은 애플리케이션만 되돌릴 뿐 데이터베이스 스키마 변경까지 되돌리지는 않으므로, 마이그레이션은 별도로 안전한 순서를 설계해야 해요.

## 상황별 선택 기준

처음 서비스를 띄우는 단계라면 Railway의 장점이 가장 크게 드러나요. 저장소만 연결하면 공개 주소까지 나오기 때문에, 인프라 준비 없이 배포 파이프라인과 애플리케이션 동작을 먼저 검증할 수 있어요. 사이드 프로젝트나 사내 도구처럼 운영 인력이 따로 없는 경우에도 잘 맞아요.

스테이징이나 풀 리퀘스트 단위 검증이 필요할 때도 유용해요. 환경을 복제해 운영과 같은 구성을 따로 두거나, 변경 사항을 임시 환경에서 확인하는 방식이 지원돼요. 다만 임시 환경은 검증이 끝나면 정리해야 비용이 새지 않아요.

이미 Dockerfile과 이미지 빌드 파이프라인이 있는 팀이라면 이미지 지정 배포가 자연스러워요. 반대로 상태를 많이 들고 있는 워크로드, 예를 들면 대용량 파일을 로컬 디스크에 쓰는 서비스는 볼륨 제약과 백업 정책을 먼저 따져봐야 해요.

규제나 망 분리 요구로 특정 인프라 안에서만 돌아야 하는 시스템이라면 관리형 플랫폼 자체가 선택지가 아닐 수 있어요. 이 경우에는 배포 방식만 참고하고 실행 환경은 직접 구성하는 편이 맞아요.

## 주의할 점

첫째, 과금 구조가 사용량 기반이라는 점이에요. 실행 시간과 자원 사용량, 네트워크 사용량이 청구에 반영되므로, 트래픽이 몰리는 이벤트나 배치 작업을 앞두고는 예상 사용량을 미리 가늠해 두는 것이 좋아요.

둘째, 볼륨은 백업이 자동이 아니에요. 복구 리허설까지 해 둬요. 영속 데이터를 볼륨에 두고 있다면 별도 백업 절차를 만들어요.

셋째, 재배포는 곧 재시작이에요. 종료 신호를 받았을 때 처리 중인 요청을 마무리하는 로직을 애플리케이션에 넣어야 해요. 무중단이 필요한 서비스라면 헬스체크 경로를 정확히 지정해요.

넷째, 환경 변수 관리예요. 개발 환경 변수를 운영에 그대로 복사하면 의도치 않은 외부 서비스에 붙을 수 있으니, 환경별로 값을 분리하고 이름 규칙을 통일해요.

다섯째, 모노레포에서는 빌드 대상이 섞이기 쉬워요. 불필요한 변경에 배포가 트리거되지 않도록 감시 경로를 조정하는 편이 좋아요. 서비스별 루트 디렉터리와 빌드 명령을 명시해요.

## 자주 묻는 질문

### railway 배포란 무료로 시험해 볼 수 있는 건가요?

이후에는 사용량 기반 요금제로 이어지는 구조예요. 공식 사이트에서 체험용 크레딧을 제공해요. 정확한 금액과 정책은 시점에 따라 달라지므로 요금 페이지에서 문서와 대조하시길 권해요.

### GitHub 연동 없이 CLI만으로도 배포할 수 있나요?

가능해요. CLI로 로그인한 뒤 프로젝트를 연결하고 현재 디렉터리를 올리는 방식으로 배포할 수 있어요. 다만 자동 배포와 이력 추적을 원한다면 저장소 연동을 같이 쓰는 편이 관리에 유리해요.

### 데이터베이스도 같은 프로젝트에서 운영할 수 있나요?

네, Postgres나 Redis 같은 데이터베이스를 서비스로 추가하고 애플리케이션에서 변수로 참조할 수 있어요. 접속 정보가 자동으로 만들어지므로 연결 코드에 값을 하드코딩할 필요가 없어요.

### 배포 실패는 어디서부터 확인해야 하나요?

빌드 로그와 실행 로그를 나눠 보는 것이 출발점이에요. 빌드 단계에서 멈췄다면 빌드 명령과 의존성 설치 로그를, 실행 직후 종료된다면 환경 변수와 포트 설정을 먼저 확인해요.

### 롤백하면 데이터도 되돌아가나요?

아니요. 롤백은 이전에 성공한 배포로 애플리케이션을 되돌리는 동작이에요. 스키마 변경이나 데이터 자체는 별도 백업과 복구 절차로 관리해야 해요.

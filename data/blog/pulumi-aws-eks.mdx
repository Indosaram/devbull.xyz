pulumi aws eks로 클러스터를 만들 때는 AWS provider로 VPC와 IAM을 직접 선언할지, EKS 패키지의 클러스터 컴포넌트에 묶음을 맡길지부터 정해요. 컴포넌트는 제어 플레인, 관련 역할, 노드 그룹을 한 선언으로 재현하기 좋게 모아 주지만, 기본값이 만드는 네트워크가 운영 계정 정책과 다를 수 있어요. 기존 VPC를 쓰려면 서브넷 식별자와 태그를 입력으로 넘기고, 새로 만들 거면 preview에서 생길 리소스 목록을 먼저 봐요. 적용 전에는 삭제 대상이 없는지, kubeconfig는 스택 출력으로만 나오는지까지 같이 보면 첫 배포가 덜 흔들려요.

## 한눈에 보기

Pulumi는 TypeScript, Python, Go 같은 언어로 클라우드 리소스를 선언하고, 스택이 그 상태의 기준이 돼요. AWS provider는 VPC, 서브넷, IAM 역할, EKS 클러스터를 낮은 수준에서 다루고, EKS 패키지는 그 위에 클러스터와 노드 그룹을 묶는 컴포넌트를 올려요.

EKS가 관리해 주는 것은 제어 플레인이에요. 워커 노드, 네트워크, 권한, 애드온은 여전히 계정 쪽에서 준비해야 해요. 그래서 “클러스터 한 개”가 아니라 “VPC와 IAM, 노드 그룹을 컴포넌트에 어디까지 맡길지”를 먼저 적는 편이 안전해요.

## Pulumi와 EKS를 함께 쓰는 이유

콘솔로 만든 클러스터는 익히기 쉽지만, 다른 계정이나 리전에 같은 모양으로 다시 만들기 어려워요. 코드로 남기면 `pulumi preview`가 생성, 변경, 삭제 범위를 보여 줘서 적용 전에 차이를 읽을 수 있어요.

EKS 패키지의 클러스터 컴포넌트는 클러스터, 관련 IAM 역할, 노드 그룹을 한 흐름으로 다뤄요. 기존 VPC와 서브넷을 넘길 수도 있고, 기본값으로 네트워크와 노드 그룹을 함께 만들 수도 있어요. 기본값은 편하지만 운영 네트워크 정책과 같다고 가정하면 안 돼요.

애플리케이션과 인프라를 같은 언어로 둘 수 있는 점은 팀 리뷰에 유리해요. 대신 상태 파일과 배포 순서는 Pulumi 백엔드가 쥐고 있어서, 스택 접근 권한을 느슨히 두면 인프라 변경 권한이 같이 넓어져요.

## 단계별 구성 방법

컴포넌트를 쓰기 전에 자격 증명, 상태 저장 위치, 계정과 리전을 고정해요. 그다음 스택을 나누고, 클러스터 입력과 노드 그룹, 애드온 순서로 선언한 뒤 preview를 보고 적용해요.

### 사전 준비

AWS 자격 증명, Pulumi CLI, 선택한 언어 런타임을 준비해요. 상태를 Pulumi Cloud에 둘지 직접 관리하는 백엔드에 둘지에 따라 접근 제어와 백업 책임이 달라져요.

작업 계정과 리전을 한곳으로 고정하고, 그 계정에 클러스터를 만들 권한이 있는지 봐요. 운영과 개발을 계정으로 나눴다면 스택도 환경별로 나누는 편이 실수 범위를 줄여요.

### 프로젝트와 스택 초기화

`pulumi new aws-typescript` 같은 템플릿으로 프로젝트를 만들고 EKS 패키지를 추가해요. 언어는 팀이 리뷰하기 쉬운 쪽을 고르면 되고, TypeScript가 아니어도 EKS 패키지를 쓸 수 있어요.

스택 설정에는 리전과 클러스터 이름처럼 환경마다 달라지는 값을 넣어요. 같은 코드에 스택만 바꾸면 개발과 운영의 차이를 설정으로 남길 수 있어요.

### 클러스터 선언

`eks.Cluster`는 클러스터와 관련 IAM, 노드 그룹을 묶어 선언할 수 있어요. 기존 VPC를 쓰려면 `vpcId`와 `subnetIds`를 넘기고, 기본 네트워크를 쓰면 컴포넌트가 만드는 VPC와 서브넷이 계정 정책에 맞는지 먼저 봐요.

이름과 태그는 나중에 비용과 장애를 추적할 때 기준이 돼요. 환경, 소유 팀, 용도를 같은 규칙으로 붙이면 콘솔과 청구 화면에서 이 스택의 리소스를 찾기 쉬워요.

### 노드 그룹과 애드온

노드 그룹은 관리형과 자체 관리형 중에서 운영 방식을 보고 골라요. 관리형은 AWS가 노드 생명주기를 맡아 주고, 자체 관리형은 시작 템플릿과 교체 절차를 직접 가져가야 해요.

VPC CNI, CoreDNS, kube-proxy 같은 애드온은 클러스터와 따로 선언할 수 있어요. 애드온 변경은 `pulumi preview`로 교체 범위를 본 뒤, 운영 스택에 바로 올리지 말고 시험 스택에서 먼저 적용해요.

### 배포와 확인

`pulumi preview`에서 생성, 변경, 삭제 목록을 읽은 다음 `pulumi up`을 해요. 첫 클러스터라면 삭제 줄이 없는지, 예상하지 않은 VPC나 노드 그룹이 생기지 않는지 특히 봐요.

스택 출력의 kubeconfig로 kubectl 컨텍스트를 연결해요. `kubectl get nodes`와 `kubectl get pods -A`로 노드와 시스템 파드가 기동했는지 보면, 제어 플레인만 만들어지고 워커가 비어 있는 상태를 놓치지 않아요.

## 상황별 선택 기준

짧게 검증할 때는 EKS 컴포넌트 기본값을 쓰되, 생기는 VPC와 노드 그룹 이름을 preview에서 읽어요. 기본 네트워크는 편하지만 사내 대역이나 라우팅 규칙과 겹칠 수 있어요.

이미 VPC, 서브넷, IAM 역할이 있으면 컴포넌트 입력으로 넘기고 서브넷 태그와 신뢰 정책을 봐요. EKS는 로드 밸런서를 만들 때 서브넷 태그를 참고하므로, 태그가 빠지면 서비스 노출 단계에서 막혀요.

네트워크와 권한을 항목마다 통제해야 하면 AWS provider로 리소스를 직접 선언하는 편이 읽기 쉬워요. 같은 EKS 모양을 여러 팀이 반복하면, 컴포넌트를 얇게 감싼 내부 모듈로 입력만 받게 하는 편이 맞아요.

Terraform과 Pulumi를 같이 쓰면 같은 리소스를 양쪽이 동시에 소유하지 않게 경계를 정해요. 기존 리소스를 가져올 때는 import로 상태에 넣고, 다음 preview에서 교체가 생기지 않는지 봐요.

## 주의할 점

Pulumi 상태에는 출력값과 민감한 설정이 들어갈 수 있어요. 상태 저장소에 접근할 수 있는 사람이 스택을 바꿀 수 있으므로, 배포 권한과 상태 읽기 권한을 나눠요.

`pulumi destroy`는 클러스터에 묶인 리소스를 함께 지울 수 있어요. 운영 스택은 보호 옵션을 검토하고, 삭제 순서와 데이터 보존을 적용 전에 적어요.

서브넷 태그가 없으면 로드 밸런서 프로비저닝이 실패할 수 있어요. VPC를 직접 만들었다면 퍼블릭과 프라이빗 서브넷의 태그, 라우팅, NAT 경로를 같이 봐요.

IRSA를 쓰면 OIDC 공급자와 IAM 신뢰 정책을 한 세트로 관리해요. 서비스 계정에 붙인 역할이 그 워크로드에 필요한 권한만 갖는지 배포 뒤에 정책 문서를 읽어요.

제어 플레인과 워커 노드 비용은 AWS 청구에서 따로 보여요. Pulumi는 리소스를 선언하고 적용하는 도구이지, 청구 금액을 대신 계산하지 않아요.

애드온과 Kubernetes 버전은 운영 클러스터에서 바로 올리지 말고 시험 스택에서 먼저 적용해요. preview에서 노드 그룹 교체인지, 롤링으로 끝나는 변경인지 구분한 뒤에 운영에 올려요.

## 자주 묻는 질문

### Pulumi로 EKS를 만들면 kubectl 설정도 자동으로 되나요?

클러스터 컴포넌트는 kubeconfig를 스택 출력으로 내주지만, 로컬 kubectl 컨텍스트에 자동으로 넣지는 않아요. 출력값을 파일로 저장한 뒤 `KUBECONFIG`나 컨텍스트 명령으로 연결해요.

### 기존 VPC와 IAM 역할을 재사용할 수 있나요?

네, `vpcId`, `subnetIds`, `instanceRoles` 같은 입력으로 기존 자산을 넘길 수 있어요. 서브넷 태그, 라우팅, IAM 신뢰 정책이 EKS가 기대하는 형태인지는 적용 전에 봐요.

### Terraform과 Pulumi를 같은 AWS 계정에서 함께 써도 되나요?

가능하지만 같은 리소스를 두 도구가 동시에 관리하면 상태가 어긋나요. 소유권을 도구별로 나누고, 기존 리소스를 가져올 때는 import로 한쪽에만 넣어요.

### EKS 비용은 Pulumi에서 확인할 수 있나요?

Pulumi는 선언과 적용을 맡고, AWS 청구 금액을 화면에 보여 주지는 않아요. 비용은 Cost Explorer나 예산 알림에서 보고, 클러스터와 노드 그룹이 어떤 항목으로 잡히는지 따로 추적해요.

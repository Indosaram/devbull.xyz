pulumi awsx와 aws는 대체재가 아니라 층이 달라요. aws는 AWS API에 가까운 리소스이고, awsx는 그 위에 자주 쓰는 구성을 묶은 컴포넌트예요. awsx만으로 모든 자원을 정의할 수는 없고, 한 프로그램에서 같이 쓰는 구성이 흔해요. 아래는 언제 어느 쪽을 고르고, 나중에 바꾸면 무엇이 다시 만들어지는지예요.

![pulumi awsx vs aws 비교: 무엇을 언제 쓸까 소제목 카드. 한눈에 보기, 비교 표, 두 패키지의 관계 이해하기, 단계별로 선택하고 적용하는 방법](/static/images/pulumi-awsx-vs-aws/diagram.webp)

## 한눈에 보기

awsx를 쓰면 코드는 짧아지지만 내부에서 여러 aws 리소스가 생겨요. 세밀한 네트워크와 정책은 aws로 직접 쓰는 편이 읽기 쉬워요. 미리보기에서 생성과 교체를 봐야 컴포넌트가 숨긴 변경을 놓치지 않아요. 버전 조합은 잠금 파일과 레지스트리를 기준으로 해요.

## 비교 표

표는 추상화, 제어 범위, 적합한 상황, 주의점을 나눈 거예요. awsx는 표준 웹 구성, aws는 개별 리소스와 기존 코드에 맞아요. 같은 자원을 두 패키지가 동시에 소유하면 충돌해요. 표의 패키지 문서는 출처의 레퍼런스를 따라요.

| 항목 | aws (AWS Classic) | awsx (AWS Crosswalk) |
| --- | --- | --- |
| 성격 | Terraform AWS 프로바이더 기반 브리지 패키지 | aws 위에 올라가는 컴포넌트 라이브러리 |
| 추상화 수준 | 리소스 단위, 인자를 그대로 노출 | 용도 단위, 조합을 미리 구성 |
| 커버리지 | AWS 서비스 전반을 넓게 다룸 | 자주 쓰는 패턴 중심으로 범위가 한정됨 |
| 기본값 | 대부분 명시적으로 지정해야 함 | 합리적인 기본값이 미리 들어 있음 |
| 코드 분량 | 같은 구성을 만들 때 상대적으로 길어짐 | 표준 구성에서 짧고 읽기 쉬움 |
| 세밀한 제어 | 모든 인자를 직접 다룰 수 있음 | 노출된 옵션 밖은 하위 리소스로 내려가야 함 |
| 디버깅 | 리소스 하나하나가 그대로 보임 | 컴포넌트 내부 리소스를 따라가며 확인해야 함 |
| 적합한 대상 | 규제 대응, 세밀한 튜닝, 기존 인프라 이관 | 신규 서비스의 표준 구성, 빠른 프로토타이핑 |

## 두 패키지의 관계 이해하기

awsx는 aws 프로바이더 위에서 동작하는 컴포넌트 모음이에요. 컴포넌트 출력을 aws 리소스 인자에 넘길 수 있고, 반대도 가능한 경우가 많아요. 스택 상태에는 둘 다 리소스로 남아요. 컴포넌트가 만든 하위 리소스 이름을 바꾸면 교체로 보일 수 있어요.

## 단계별로 선택하고 적용하는 방법

필요한 자원에 awsx 컴포넌트가 있는지 레지스트리에서 봐요. 있으면 시험 스택에서 미리보기로 하위 리소스를 읽어요. 없는 자원은 aws로 정의하고, 참조만 연결해요. 운영 반영 전에 교체와 삭제가 없는지 사람이 승인해요.

## 상황별 선택 기준

새 서비스를 표준 구성으로 빨리 만들면 awsx로 시작하고, 요구가 구체화되면 그 부분만 aws로 내려가요. 기존 인프라를 이관하면 aws로 자원을 맞추는 편이 예측이 좋아요. 팀이 컴포넌트 내부를 자주 열어야 하면 aws가 읽기 쉬워요. 둘을 섞을 때는 소유 경계를 코드에 적어요.

| 상황 | 권장 방향 | 이유 |
| --- | --- | --- |
| 신규 서비스의 표준 웹 구성 | awsx 우선, 필요 부분만 aws | VPC·ALB·ECS 조합을 짧게 유지할 수 있음 |
| Terraform 코드를 그대로 옮기는 작업 | aws 우선 | 리소스 타입과 인자가 거의 일대일로 대응됨 |
| 보안·감사 요구가 강한 환경 | aws 우선 | 모든 인자를 명시적으로 남길 수 있음 |
| 여러 팀이 같은 네트워크를 공유 | 네트워크는 aws, 워크로드는 awsx | 공유 자원은 변경 이력을 촘촘히 남기는 편이 안전 |
| 빠른 검증용 임시 환경 | awsx | 기본값으로 빠르게 띄우고 버리기 쉬움 |

## 주의할 점

예제 버전과 설치 버전이 다르면 옵션 이름이 안 맞아요. awsx 업그레이드가 하위 리소스 교체로 이어질 수 있어요. 최신 이미지 태그처럼 흔들리는 값을 컴포넌트에 넣으면 매번 변경이 나와요. 상태 백엔드를 공유하지 않으면 협업 때 스택이 갈라져요.

## 자주 묻는 질문

커버 범위, 혼용, 재생성, 세밀한 설정, 도입 순서가 반복돼요.

### awsx만으로 모든 AWS 리소스를 정의할 수 있나요?

아니요. 자주 쓰는 패턴만 컴포넌트로 있어요. 없는 서비스는 aws로 정의해요. 실무에서는 둘을 같이 쓰는 구성이 많아요.

### aws와 awsx를 한 프로그램에서 같이 써도 되나요?

가능해요. 같은 스택 상태에 기록되고 참조를 주고받을 수 있어요. 같은 자원을 양쪽이 만들게 하지 마세요.

### awsx로 만든 리소스를 나중에 aws로 바꾸면 재생성이 일어나나요?

다른 리소스로 다시 정의하면 삭제 후 생성으로 보일 수 있어요. 전환 전에 미리보기로 교체를 확인해요. 별칭이나 가져오기가 필요한지는 그 리소스 문서를 봐요.

### awsx를 쓰면 세밀한 설정을 포기해야 하나요?

컴포넌트 옵션으로 조정할 수 있는 범위가 있어요. 없는 부분은 aws 리소스로 보완해요. 보완이 컴포넌트 기본값과 싸우면 그 부분은 aws로 내리는 편이 낫습니다.

### 팀에 처음 도입한다면 어느 쪽부터 시작하는 것이 좋나요?

기존 자원을 옮기면 aws부터, 새 표준 서비스면 awsx로 시작해 필요한 곳만 aws로 내려가세요. 어느 쪽이든 미리보기 승인을 팀 절차로 두세요.

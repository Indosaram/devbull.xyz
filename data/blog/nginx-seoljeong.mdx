nginx 설정은 프로세스 전역, 연결, HTTP 공통, 서버, 경로 블록이 계층으로 쌓여요. 도메인과 프록시, 정적 파일을 바꾸기 전에 어느 파일이 include되는지 알아야 리로드가 그 파일을 읽어요. 문법 통과와 요청이 기대한 블록으로 가는 것은 달라요. 아래는 구조, 단계, 자주 틀리는 지시어예요.

## 한눈에 보기

본파일에서 include로 사이트 파일을 나누는 구성이 흔해요. server는 도메인과 포트, location은 URI, upstream은 백엔드 묶음이에요. 고친 뒤에는 문법 검사와 리로드, 테스트 요청 순서가 기본이에요. 재시작은 연결을 끊을 수 있어서 보통은 리로드가 먼저예요.

## 설정 파일 구조와 주요 디렉티브 비교

표는 main, events, http, server, location, upstream이 맡는 일과 자주 쓰는 지시어를 나눈 거예요. 지시어를 잘못된 블록에 두면 문법은 통과해도 적용 범위가 달라져요. include 순서와 파일 이름 순서가 나중 값을 덮을 수 있어요.

| 항목 | 역할 | 주로 두는 위치 |
| --- | --- | --- |
| `worker_processes` | 워커 프로세스 수 결정 | main |
| `events` | 연결 처리 관련 설정 묶음 | main |
| `include` | 다른 설정 파일을 불러옴 | 어느 컨텍스트에서나 가능 |
| `http` | HTTP 전반 설정을 묶는 블록 | main |
| `upstream` | 백엔드 서버 그룹 정의 | http |
| `server` | 가상 호스트 단위 블록 | http |
| `server_name` | 요청 도메인 매칭 | server |
| `location` | URI 패턴별 처리 분기 | server |
| `root` / `alias` | 정적 파일 경로 지정 | server, location |
| `proxy_pass` | 요청을 넘길 대상 지정 | location |
| `try_files` | 파일 존재 여부에 따른 분기 | server, location |
| `access_log` / `error_log` | 로그 경로와 형식 지정 | http, server, location |

## 단계별 설정 방법

위치 확인부터 리로드까지 일곱 단계로 가면 실수 위치가 분명해요.

### 1. 설치 상태와 파일 위치 확인

실행 중인 바이너리와 그 프로세스가 연 설정 경로를 봐요. 배포판 기본 경로와 다르면 그 경로를 고쳐야 해요. 컨테이너면 마운트된 파일인지 확인해요.

```bash
nginx -v
nginx -V
nginx -t
```

### 2. main과 events 컨텍스트 정리

사용자, 워커, 오류 로그, pid는 main에 두고, 연결 처리 수는 events에 둬요. 이 값을 사이트 파일에 넣으면 문맥 오류가 나요. 워커 수 변경은 리로드만으로 안 될 수 있어요.

```nginx
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile      on;

    include /etc/nginx/conf.d/*.conf;
}
```

### 3. server 블록으로 도메인 분기

listen과 server_name으로 도메인을 나눠요. 같은 포트의 기본 서버가 의도한 블록인지 봐요. 사이트마다 로그 경로를 나누면 원인 찾기가 쉬워요.

```nginx
server {
    listen 80;
    server_name api.example.com;

    access_log /var/log/nginx/api.access.log;
    error_log  /var/log/nginx/api.error.log;

    location / {
        proxy_pass http://app_backend;
    }
}
```

### 4. location 블록으로 경로 분기

접두, 정확한 일치, 정규식은 우선순위가 달라요. try_files와 alias의 끝 슬래시를 맞추지 않으면 경로가 어긋나요. 한 경로만 다른 서버로 보낼 때도 location 단위로 나눠요.

```nginx
location /static/ {
    alias /srv/app/static/;
    expires 7d;
}

location /api/ {
    proxy_pass http://app_backend;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### 5. 업스트림과 리버스 프록시 구성

백엔드가 여러 대면 upstream에 모으고, 하나면 proxy_pass에 직접 적어도 돼요. 호스트 헤더를 넘기지 않으면 백엔드가 잘못된 이름으로 응답할 수 있어요. 대상이 죽으면 502 계열로 보여요.

```nginx
upstream app_backend {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://app_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

### 6. 정적 파일과 캐시 설정

해시가 붙은 자산은 오래 캐시해도 되고, 자주 바뀌는 문서는 짧게 하거나 캐시를 빼요. expires와 Cache-Control을 같이 쓰면 어느 쪽이 남는지 응답 헤더로 봐요. 루트와 alias를 섞지 마세요.

```nginx
location ~* \.(css|js|png|jpg|svg|woff2)$ {
    root /srv/app/public;
    expires 30d;
    add_header Cache-Control "public, immutable";
    access_log off;
}
```

### 7. 설정 검증과 리로드

문법 검사를 같은 설정 경로로 하고, 통과하면 리로드해요. 리로드 뒤 응답 헤더와 상태 코드로 기대한 블록인지 봐요. 실패하면 백업 파일로 되돌리고 다시 검사해요.

```bash
nginx -t
nginx -s reload
```

## 상황별 선택 가이드

정적 파일만이면 root와 try_files, 백엔드 하나면 proxy_pass, 여러 대면 upstream이에요. 도메인이 여러 개면 server를 나누고, TLS 종료를 nginx에 모을지 정해요. 경로 일부만 다른 서버로 보낼 때는 location 단위 프록시가 맞아요.

## 주의할 점

include되지 않은 파일을 고치면 리로드해도 안 바뀌어요. proxy_pass 슬래시는 경로를 넘기는 방식이 달라요. 기본 서버를 비워 두면 모르는 호스트가 다른 사이트로 가요. 운영 파일과 저장소가 다르면 다음 배포가 되돌려요.

## 자주 묻는 질문

파일 위치, 리로드, 슬래시, location 우선순위, 502, 파일 분할이 반복돼요.

### nginx 설정 파일은 어디에 있나요?

배포판과 컨테이너마다 달라요. 실행 중인 프로세스가 연 경로와 include를 따라가요. 문서 예시 경로를 그대로 단정하지 마세요.

### 설정을 바꾼 뒤 재시작과 리로드 중 무엇을 해야 하나요?

문법 통과 뒤 리로드가 기본이에요. 프로세스 구성 자체가 바뀌는 항목은 문서에서 재시작이 필요한지 봐요. 오류가 있는 파일로 재시작을 반복하면 중단이 길어요.

### proxy_pass 뒤에 슬래시를 붙이는 것과 안 붙이는 것의 차이는 무엇인가요?

슬래시 유무에 따라 요청 URI를 대상에 어떻게 붙이는지가 달라져요. 공식 proxy 모듈 문서의 그 설명을 보고 경로를 맞춰요. 한 글자 차이로 백엔드 경로가 어긋나요.

### location 블록의 우선순위는 어떻게 되나요?

정확한 일치, 우선 접두, 정규식, 일반 접두 순으로 해석이 갈려요. 정규식과 접두를 섞으면 기대한 블록이 아닐 수 있어요. 테스트 요청으로 어느 블록인지 확인해요.

### 502 Bad Gateway가 뜨면 어디부터 확인해야 하나요?

업스트림이 떠 있는지, proxy_pass 주소와 포트가 맞는지, 오류 로그의 연결 실패인지 봐요. 앱이 루프백이 아닌 주소에 바인딩하는지도 봐요. nginx 문법 성공과 업스트림 생존은 달라요.

### 설정 파일을 여러 개로 나눠도 되나요?

include로 나누는 것이 일반적이에요. 본파일이 그 파일을 읽는지, 순서가 나중 값을 덮지 않는지 확인해요. 조각만 따로 문법 검사하면 문맥이 빠져 오해가 생겨요.

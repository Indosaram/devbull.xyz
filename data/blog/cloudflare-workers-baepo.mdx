Cloudflare Workers 배포는 서버를 띄우는 일이 아니라, Wrangler로 번들을 올리고 라우팅과 바인딩을 붙이는 일이에요. 명령 자체는 짧지만, 설정 파일의 이름·진입점·호환성 날짜, 시크릿, 환경 분리가 어긋나면 배포 표시만 성공하고 요청은 실패해요. 처음이라면 로컬 실행으로 응답 형태를 맞춘 뒤 배포하고, 로그와 배포 이력으로 한 번 더 확인하는 순서가 안전해요. 아래는 공식 문서에서 안내하는 준비, 배포, 되돌리기 흐름만 정리해요.

## 한눈에 보기

Workers는 요청을 사용자와 가까운 위치에서 처리하는 서버리스 런타임이에요. 인스턴스 수를 직접 늘리는 대신, 코드 번들과 라우팅을 올리면 플랫폼이 실행 위치를 맡아요. 백엔드에서 손대는 축은 진입점 핸들러, Wrangler, 설정 파일, 바인딩, 그리고 배포 뒤 로그예요. 진입점은 요청을 받아 응답을 돌려주는 형태가 기본이고, KV나 R2, D1, Durable Objects 같은 자원은 설정에 선언한 이름으로 코드에 들어와요. 배포 성공과 서비스 정상은 다르므로, 이력 화면과 실시간 로그, 실제 경로 호출을 한 세트로 봐요.

## 배포 방식 비교

같은 Worker도 올리는 경로가 여러 가지예요. 로컬에서 반복 배포하려면 Wrangler가 기준이고, 화면에서 바로 고치는 편집기는 짧은 실험에 맞아요. 팀이 리뷰 후 배포하려면 저장소와 Git 연동을 얹는 편이 설정 파일이 어긋나지 않아요. 표는 준비 부담, 반복 배포, 환경 분리, 롤백을 나눠 둔 거예요. 상시 운영 경로는 CLI나 Git으로 두고, 대시보드 편집기는 긴급 확인용으로 남기는 구성이 흔해요. 화면에서만 고치면 저장소의 설정과 실제 상태가 갈라지기 쉬워요.

| --- | --- | --- | --- |
| 초기 준비 | 로컬에 Node 환경과 Wrangler 설치 | 브라우저 로그인만 필요 | 저장소와 프로젝트 연결 |
| 반복 배포 | 명령 실행으로 즉시 반영 | 편집기에서 저장하면 반영 | 브랜치 푸시 시 자동 실행 |
| 설정 관리 | 설정 파일을 저장소에서 버전 관리 | 화면에서 직접 수정 | 저장소의 설정 파일을 그대로 사용 |
| 환경 분리 | 환경별 설정과 명령으로 분리 | 환경 전환이 번거로움 | 브랜치와 환경을 매핑해 처리 |

| 적합한 상황 | 일반적인 운영 배포 | 빠른 실험과 긴급 수정 | 팀 협업과 리뷰 중심 운영 |

## 단계별 배포 방법

배포 명령 앞에 계정, 프로젝트, 로컬 확인, 설정 점검이 있어요. 한 번에 올리기보다 아래 순서대로 막히는 지점을 나눠 보면 원인 찾기가 빨라요.

### 사전 준비

Cloudflare 계정과 Node 실행 환경이 필요해요. Wrangler는 패키지로 제공되니 로컬에서는 npx로 바로 실행할 수 있고, CI와 버전을 맞추려면 개발 의존성으로 고정하는 편이 좋아요. 로그인은 브라우저 승인으로 마치고, 브라우저가 없는 환경에서는 API 토큰을 환경 변수로 넣어요.

### 프로젝트 생성

새 작업은 공식 생성 명령의 안내를 따라 템플릿과 언어를 고르면 진입점과 설정 파일이 같이 생겨요. 이미 있는 Node 프로젝트라면 Wrangler만 추가하고 설정 파일을 직접 써도 돼요. 진입점은 요청, 환경, 컨텍스트를 받는 fetch 핸들러가 기본이에요. 자원 접근은 설정에 선언한 바인딩이 들어오는 환경 객체를 통해요.

### 로컬 실행과 확인

배포 전에 로컬 개발 명령으로 라우팅과 응답 형식을 봐요. 원격 바인딩까지 붙여 봐야 하면 원격 모드를 써요. 로컬 전용 값은 별도 파일에 두고 저장소 무시 목록에 넣어요. 이 파일이 배포 환경의 시크릿을 대신하지는 않으니, 이름만 맞추고 값은 환경을 나눠요.

### 설정 파일 점검

올리기 전에 이름, 진입점, 호환성 날짜, 필요한 플래그, 일반 변수, 라우트, 로그 수집을 읽어요. 호환성 날짜는 배포마다 흔들리지 않게 고정하고, 민감한 값은 일반 변수 칸에 넣지 않아요. JSONC와 TOML 중 팀이 쓰는 형식 하나로 통일하면 리뷰가 쉬워요.

### 배포 실행

준비가 끝나면 배포 명령이 번들을 만들어 올리고 라우팅에 연결해요. 처음이면 플랫폼 서브도메인으로 바로 호출해 볼 수 있어요. 올리기 전에 드라이런으로 번들 구성만 보면, 빠지면 안 되는 의존성이나 예상보다 큰 산출물을 먼저 걸러요. 로컬과 CI는 같은 명령을 쓰는 편이 재현이 좋아요.

### 배포 검증

대시보드에서 배포 완료 표시를 보고, 배포 목록 명령으로 이력과 버전을 확인해요. 실시간 로그를 연 상태에서 정상 경로뿐 아니라 인증 실패와 없는 경로도 호출해요. 성공 배지만 보면 라우팅 실수를 놓치기 쉬워요.

### 롤백과 버전 관리

문제가 보이면 롤백 명령으로 직전 배포를 되돌리거나, 이력 화면에서 특정 버전을 골라요. 버전을 명시적으로 남기면 나중에 그 버전을 지정해 다시 배포할 수 있어요. 되돌린 뒤에는 로그와 어떤 변경이 문제였는지를 같이 적어 두세요. 빠른 복구와 원인 기록은 별개예요.

## 상황별 선택

API만 있으면 Worker 하나에 라우팅을 두고 저장소는 바인딩으로 붙여요. 정적 파일과 API를 같이 주면 자산 제공을 설정에 선언하고 나머지 경로는 Worker가 받아요. 페이지 중심이면 Pages와 Workers 중 어디가 맞는지 공식 안내를 보고 고르세요. 스테이징과 프로덕션이 필요하면 환경 섹션을 나누고, 배포 명령에 환경 이름을 붙여요. 시크릿은 등록 명령으로 올리고 저장소에 남기지 않아요. CI는 공식 액션이나 같은 배포 명령을 쓰고, 인증은 API 토큰으로 넣어요.

## 주의할 점

호환성 날짜를 올릴 때는 런타임 동작이 달라질 수 있으니 별도 배포로 나눠 검증해요. 시크릿을 설정 파일이나 코드에 넣으면 교체 대상이 돼요. 플랫폼 기본 주소를 외부에 공개할지, 커스텀 도메인만 쓸지도 정해 두세요. 바인딩 이름이 코드와 설정에서 다르면 배포는 돼도 실행 때 실패해요. 플랜마다 기능과 한도가 다르니, 요청이 많거나 실행이 긴 작업은 문서의 플랜 안내를 먼저 봐요. 로그를 꺼 두면 엣지에서만 나는 문제를 재현하기 어려워요.

## 자주 묻는 질문

배포 직후에 막히는 질문은 환경 차이와 되돌리기, 도메인, 비밀 값에 몰려 있어요.

### 로컬에서 잘 되던 코드가 배포 후 실패하는 이유는 무엇인가요?

로컬 파일에만 있던 값이 배포 환경에 없거나, 바인딩 이름이 코드와 설정에서 다른 경우가 많아요. 실시간 로그의 예외부터 보고, 환경별로 시크릿이 등록됐는지 확인해요. 로컬 성공은 원격 바인딩 성공을 보장하지 않아요.

### 배포한 Worker를 이전 버전으로 되돌릴 수 있나요?

가능해요. 롤백 명령으로 직전 배포를 되돌리거나, 대시보드 이력에서 버전을 골라요. 버전 관리를 쓰면 특정 배포본을 지정해 다시 올릴 수도 있어요.

### 커스텀 도메인은 어떻게 연결하나요?

Cloudflare에서 관리하는 도메인이면 설정의 라우팅이나 대시보드에서 호스트와 경로를 지정해요. 다른 등록기관에 있으면 네임서버 위임이 먼저예요. 연결 뒤에는 DNS와 인증서 상태를 같이 봐요.

### 시크릿과 일반 환경 변수는 어떻게 나눠 관리하나요?

민감하지 않은 값은 설정 파일의 변수에, 민감한 값은 시크릿 등록 명령으로 둬요. 로컬 값은 별도 파일에 두고 커밋하지 않아요. 환경이 여러 개면 시크릿도 환경마다 따로 등록해요.

### 배포 자동화는 어디서부터 시작하면 좋나요?

설정 파일을 저장소에 두고, 로컬에서 쓰던 배포 명령을 CI로 옮기면 돼요. 인증은 API 토큰을 비밀 값으로 넣고, 배포 전에 드라이런으로 번들을 검사해요. 그다음 브랜치와 환경을 연결해 자동 배포 범위를 정해요.

## 출처

배포 뒤에 자주 흔들리는 부분은 시크릿과 로그, 롤백 습관이에요. 환경 값을 나누는 방법은 [Cloudflare Workers 환경 변수와 시크릿 관리](/blog/cloudflare-workers-env-secrets)에서 이어서 볼 수 있어요.

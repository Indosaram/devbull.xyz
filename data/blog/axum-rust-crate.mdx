axum rust crate는 Tokio 위에서 HTTP 서버를 만드는 웹 프레임워크 패키지예요. 라우터, 추출기, 상태, tower 미들웨어를 조합하는 쪽이 핵심이고, 런타임 자체는 tokio가 맡아요. 첫 서버는 의존성, 라우터, 종료 처리만 있어도 올라가고, 운영으로 가면 에러 형식과 상태를 나눠야 해요. 아래는 구성 요소와 도입 순서예요.

## 한눈에 보기

axum은 hyper와 tower 위에 라우팅과 추출기를 얹은 크레이트예요. 핸들러는 async 함수이고, 공유 자원은 State로 넘겨요. 공통 처리는 미들웨어, 업무 로직은 핸들러로 나누는 편이 유지가 쉬워요. 버전을 올릴 때는 docs.rs의 그 버전 문서를 봐요.

## axum rust crate를 구성하는 요소

Router가 경로를 모으고, 추출기가 요청에서 값을 꺼내요. State는 Clone되는 공유 값이고, tower 레이어가 요청 전후를 감싸요. 응답은 IntoResponse를 구현한 타입이면 돼요. 서버를 실제로 띄우는 런타임 기능은 tokio 쪽 플래그에 있어요.

| 구성 요소 | 역할 | 처음 만질 때 확인할 점 |
| --- | --- | --- |
| Router | 경로와 핸들러를 등록하고 라우터를 합침 | 경로 충돌 여부, merge와 nest의 차이 |
| Handler | 요청을 받아 응답으로 바꾸는 비동기 함수 | 반환 타입이 응답으로 변환 가능한지 |
| Extractor | 경로·쿼리·본문·헤더를 인자로 받아냄 | 본문을 소비하는 추출자의 위치 |
| State | 핸들러들이 공유하는 값 | 상태 타입을 라우터에 언제 확정하는지 |
| Layer | tower 미들웨어를 라우터나 핸들러에 적용 | 적용 순서와 요청 흐름의 방향 |
| Service | tower의 공통 인터페이스 | 직접 구현보다 기존 레이어 재사용 |

## 다른 Rust 웹 프레임워크와의 결

표는 axum, actix-web, warp의 라우팅과 미들웨어 차이를 개념으로 나눈 거예요. axum은 tower 생태계를 그대로 쓰고, actix-web은 자체 미들웨어가 두텁고, warp는 필터 조합이 중심이에요. 팀이 tower에 익숙하면 axum이 읽기 쉬워요. 예제 양만으로 고르지 말고 미들웨어를 어디에 둘지 봐요.

| 항목 | axum | actix-web | warp |
| --- | --- | --- | --- |
| 기반 | tokio와 tower 생태계 | 자체 액터 계열 설계 | 필터 조합 |
| 확장 방식 | tower 레이어 재사용 | 자체 미들웨어 체계 | 필터 합성 |
| 학습 부담 | 추출자와 타입 추론 이해가 필요 | 매크로와 액터 개념 이해가 필요 | 필터 타입 오류 메시지가 길어짐 |
| 잘 맞는 경우 | tokio 기반 서비스에 공통 레이어를 얹을 때 | 기존 actix 생태계 자산을 쓸 때 | 함수형 조합 방식을 선호할 때 |

## 단계별 도입 방법

의존성부터 종료까지 일곱 단계로 나누면 어디가 빠졌는지 보여요.

### 첫 단계: 프로젝트와 의존성 준비

바이너리 프로젝트를 만들고 axum과 tokio를 넣어요. tokio는 매크로와 네트워크 기능 중 실제로 쓰는 플래그만 Cargo.toml에 켜요. 로깅이 필요하면 tracing 계열을 그때 추가해요.

### 두 번째 단계: 라우터와 핸들러

경로와 메서드를 Router에 등록하고, 핸들러는 작은 async 함수로 둬요. 헬스 경로를 먼저 만들면 배포 확인이 쉬워요. 라우터가 커지면 기능별로 나눠 합쳐요.

### 세 번째 단계: 추출자로 입력 받기

경로, 쿼리, 본문, 헤더는 추출기로 받아요. 추출 실패는 거절 응답이 되니, 클라이언트가 읽을 오류 형식을 정해 두세요. 본문을 미들웨어에서 먼저 읽으면 추출기가 빈 본문을 받아요.

### 네 번째 단계: 상태 공유

풀이나 설정은 State로 넘기고 Clone이 가능해야 해요. 핸들러마다 연결을 새로 만들지 않아요. 상태를 전역 정적에 두면 테스트가 어려워져요.

### 다섯 번째 단계: 미들웨어와 공통 처리

로그와 타임아웃은 레이어로 두고, 인증은 보호 라우터에만 붙여요. 나중에 추가한 레이어가 바깥에서 먼저 요청을 봐요. 공통 처리가 라우트를 판단하기 시작하면 책임이 섞여요.

### 여섯 번째 단계: 에러 처리와 응답

핸들러 오류를 한 형식으로 바꿔 상태 코드와 본문을 맞추세요. 미들웨어만 다른 형식을 쓰면 클라이언트가 원인을 못 읽어요. 내부 오류 문자열을 그대로 노출하지 않아요.

### 일곱 번째 단계: 서버 실행과 종료

바인드 주소는 설정의 포트를 읽게 해요. 종료 신호를 받으면 진행 중 요청을 끝낼 시간을 두고 런타임을 닫아요. 로컬에서만 되는 주소를 배포에 그대로 두면 헬스 체크가 실패해요.

## 상황별 선택 기준

작은 JSON API는 axum과 tower-http의 추적, 제한만으로 시작해요. 웹소켓이나 정적 파일이 필요하면 그 기능 예제를 따로 붙여요. 팀이 actix 예제에 이미 묶여 있으면 이관 비용과 tower 이점을 같이 봐요. hyper를 직접 쓰는 경우는 프로토콜을 커스터마이즈할 때로 좁혀요.

## 주의할 점

예제 버전과 Cargo.toml 버전이 다르면 추출기 시그니처가 안 맞아요. 요청마다 블로킹 작업을 async 안에서 돌리면 런타임이 막혀요. 상태 타입이 라우터와 미들웨어에서 다르면 컴파일이 실패해요. 배포 이미지에 설정 파일이 빠지면 로컬에서만 떠요.

## 자주 묻는 질문

프레임워크 선택, 미들웨어 순서, 상태, 버전, hyper가 반복돼요.

### axum과 actix-web 중 무엇을 선택해야 하나요?

tower 레이어를 그대로 쓰고 추출기 스타일이 맞으면 axum이에요. 기존 actix 코드와 인력이 많으면 이관 이유를 따로 정해요. 성능 숫자로 고르기보다 운영할 코드 형태를 봐요.

### 미들웨어는 어떤 순서로 적용되나요?

나중에 붙인 레이어가 바깥에서 먼저 요청을 받아요. 응답은 반대 방향이에요. 추적을 가장 바깥에 두면 전체 구간을 보기 좋아요.

### 상태 공유는 반드시 감싸서 넘겨야 하나요?

공유할 값이면 State로 넘기는 것이 axum의 방식이에요. 핸들러 인자로 매번 복사할 작은 값은 추출기 없이 클로저로 잡을 수도 있지만, 풀은 State가 맞아요. 타입은 라우터에 넘긴 것과 같아야 해요.

### 버전을 올릴 때 무엇을 확인해야 하나요?

바뀐 추출기와 라우터 API를 그 버전의 docs.rs에서 봐요. 시험 빌드로 시그니처 오류를 먼저 고치고, 종료와 미들웨어 순서가 같은지 확인해요. 예제 기본 브랜치와 릴리스 태그를 섞지 마세요.

### hyper를 직접 다뤄야 하나요?

대부분의 API 서버는 axum 라우터로 충분해요. 연결 수준의 커스텀이 필요할 때만 hyper와 tower Service를 직접 봐요. 그때도 핸들러 업무 로직과 분리하는 편이 좋아요.

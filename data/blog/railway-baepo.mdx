## 한눈에 보기

Railway는 애플리케이션과 데이터베이스 같은 서비스를 프로젝트 안에서 함께 관리하는 배포 플랫폼이에요. 저장소를 연결하면 빌드와 배포가 대시보드에서 이뤄지고, 환경 변수·도메인·로그를 같은 화면에서 확인할 수 있어요. 처음에는 무엇을 서비스로 둘 것인지와 어느 환경에 어떤 변수를 둘 것인지를 먼저 정하는 게 좋아요.

배포 전에 확인할 기본 흐름은 다음과 같아요.

- 실행할 애플리케이션과 데이터베이스를 각각 서비스로 나눠요.
- GitHub 저장소를 연결하거나 CLI로 배포할 방식을 정해요.
- 빌드 방식과 시작 명령, 포트 바인딩을 확인해요.
- 환경 변수와 시크릿을 환경별로 설정해요.
- 배포 후 로그와 도메인 접속을 확인해요.

## 단계별 배포 방법

### 프로젝트와 서비스 구조 정리

Railway에서는 프로젝트 안에 여러 서비스를 둘 수 있어요. 웹 애플리케이션, 백그라운드 워커, 데이터베이스를 한 프로젝트에 두되 각각 독립된 서비스로 나누면 로그와 변수를 분리하기 쉬워요. 반대로 작은 실험이라면 하나의 서비스로 시작하고 필요할 때 나누는 편이 간단해요.

환경은 개발, 스테이징, 운영처럼 나눠 두는 것이 좋아요. 같은 서비스라도 환경마다 변수와 도메인이 달라질 수 있기 때문이에요. 처음부터 모든 환경을 만들 필요는 없지만, 운영 배포 전에 최소한 운영 환경의 변수와 도메인을 따로 확인할 구조는 준비해 두세요.

### 저장소 연결과 빌드 설정

GitHub 저장소를 연결하면 Railway가 저장소를 읽고 빌드 방식을 정해요. 별도 설정이 없으면 Nixpacks가 프로젝트 언어와 구조를 감지해 빌드하고, Dockerfile이 있으면 그 정의를 따르는 흐름으로 이해하면 돼요. 자동 감지가 맞지 않으면 빌드 명령과 시작 명령을 직접 지정해요.

빌드 설정은 대시보드에서 바꿀 수도 있고, `railway.toml`이나 `railway.json` 같은 설정 파일로 관리할 수도 있어요. 설정 파일을 쓰면 코드 리뷰에서 배포 설정을 함께 확인할 수 있어요. 다만 설정 파일과 대시보드 설정이 충돌하지 않도록 어느 쪽을 기준으로 삼을지 팀 규칙을 정해 두는 게 좋아요.

### 환경 변수와 시크릿 관리

환경 변수는 서비스가 실행될 때 필요한 설정값이에요. 데이터베이스 주소, 외부 API 키, 실행 모드 같은 값을 Railway 대시보드의 변수 화면에서 관리해요. 저장소에는 실제 시크릿을 커밋하지 말고, 필요한 이름만 예시 파일로 남기는 편이 안전해요.

환경별로 값이 다르면 프로젝트의 환경을 나눠 같은 이름의 변수를 다르게 설정해요. 예를 들어 운영 환경의 데이터베이스 주소와 스테이징 환경의 주소를 분리하는 식이에요. 변수를 바꾼 뒤에는 재배포가 필요한지 확인하고, 실행 로그에서 설정이 제대로 읽혔는지 봐요.

### 도메인과 헬스 체크

배포가 끝나면 Railway가 제공하는 도메인으로 먼저 접속을 확인해요. 애플리케이션이 정상적으로 응답하는지, 정적 파일과 API 경로가 모두 열리는지 확인해요. 운영 도메인을 연결할 때는 DNS 레코드를 Railway 안내에 맞춰 설정하고, 인증서 발급과 전파에 시간이 걸릴 수 있다는 점을 기억해요.

헬스 체크를 설정하면 배포 후 서비스 상태를 판단하는 데 도움이 돼요. 애플리케이션에 상태 확인용 경로를 두고, 데이터베이스 연결까지 확인할지 아니면 프로세스 응답만 볼지 정해요. 헬스 체크 경로가 실제로 응답하는지 로컬과 배포 환경에서 모두 확인해 두세요.

### 배포 로그 확인과 롤백

배포가 실패하면 빌드 로그와 실행 로그를 나눠서 봐요. 빌드 로그에서는 의존성 설치와 빌드 명령이 어디서 멈췄는지 확인하고, 실행 로그에서는 포트 바인딩, 환경 변수 누락, 데이터베이스 연결 오류를 확인해요. 로컬에서는 성공했는데 배포에서만 실패한다면 런타임 버전과 시작 명령을 먼저 대조해 보세요.

문제가 생겼을 때는 이전 배포로 되돌리는 방법을 준비해 두는 게 좋아요. 대시보드에서 이전 배포를 선택해 다시 배포하거나, 수정한 커밋을 새로 배포하는 방식으로 대응해요. 롤백 후에도 환경 변수와 데이터베이스 마이그레이션 상태가 맞는지 확인해야 해요.

## 상황별 선택

혼자 만드는 작은 서비스라면 GitHub 저장소를 연결하고 기본 감지 빌드로 시작하는 방식이 간단해요. 먼저 Railway 제공 도메인으로 접속을 확인하고, 운영 도메인과 환경 변수는 서비스가 안정된 뒤 정리해도 늦지 않아요.

팀 단위로 운영하는 서비스라면 저장소 연결과 설정 파일을 함께 쓰는 편이 좋아요. 배포 설정을 코드로 남기면 변경 이력을 리뷰할 수 있고, 환경별 변수를 분리해 실수로 운영 설정을 건드리는 일을 줄일 수 있어요. 데이터베이스가 포함된 서비스라면 마이그레이션 순서와 백업 정책을 배포 절차에 함께 넣어야 해요.

모노레포처럼 여러 앱이 한 저장소에 있다면 서비스별 루트 디렉터리와 빌드 명령을 명확히 나눠요. 어떤 앱이 어떤 서비스로 배포되는지 표로 정리해 두면 자동 배포가 엉뚱한 서비스에 걸리는 일을 줄일 수 있어요. Dockerfile을 쓰는 경우에는 이미지 크기와 빌드 캐시도 함께 점검해요.

## 주의할 점

가장 흔한 문제는 애플리케이션이 배포 환경의 포트와 바인딩 주소를 따르지 않는 경우예요. Railway가 제공하는 포트 환경 변수를 사용하고, 외부에서 접근할 수 있는 주소에 바인딩해야 해요. 로컬에서만 쓰던 고정 포트를 그대로 두면 배포 후 접속이 되지 않을 수 있어요.

시크릿은 저장소에 커밋하지 말고 Railway 변수 화면에서 관리해요. 로그에 환경 변수 값이 그대로 남지 않도록 애플리케이션의 로깅 설정도 확인해요. 데이터베이스 마이그레이션은 배포와 동시에 자동 실행하기보다, 실패했을 때 되돌릴 수 있는 순서로 나눠 두는 편이 안전해요.

자동 배포를 켜 두면 의도하지 않은 브랜치의 커밋이 운영에 반영될 수 있어요. 운영 서비스에는 배포 브랜치와 승인 절차를 정하고, 배포 후에는 로그와 주요 API 응답을 확인해요. 가격과 사용 한도는 플랜에 따라 달라질 수 있으므로 공식 가격 페이지에서 현재 조건을 확인해요.

## 자주 묻는 질문

### Railway 배포는 GitHub 저장소가 꼭 필요한가요?

GitHub 연동이 가장 일반적이지만 Railway CLI로 로컬 디렉터리를 업로드하는 방법도 있어요. Dockerfile 기반으로 배포하는 선택지도 있으니 팀의 릴리스 방식에 맞춰 골라요.

### 배포가 실패하면 어디부터 확인해야 하나요?

먼저 빌드 로그에서 의존성 설치와 빌드 명령이 성공했는지 보고, 그다음 실행 로그에서 포트 바인딩과 환경 변수 누락을 확인해요. 로컬에서는 되는데 배포에서만 실패한다면 시작 명령과 런타임 버전을 대조해 보세요.

### 환경 변수는 어디에 두나요?

Railway 대시보드의 서비스 변수 화면에서 관리하고, 저장소에는 예시 파일만 두는 편이 안전해요. 환경별로 값이 다르면 프로젝트의 환경을 나눠 같은 이름의 변수를 다르게 설정해요.

### 배포 후 도메인은 어떻게 연결하나요?

먼저 Railway가 제공하는 도메인으로 접속을 확인한 뒤, 운영 도메인은 DNS 레코드를 Railway 안내에 맞춰 설정해요. 인증서 발급과 전파에는 시간이 걸릴 수 있으니 바로 되지 않아도 당황하지 않아요.

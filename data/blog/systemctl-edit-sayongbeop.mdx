systemctl edit는 원본 유닛을 건드리지 않고 drop-in 파일로 일부 지시어만 덮는 방법이에요. 패키지 업데이트가 원본을 바꿔도 오버라이드는 남아요. 전체 사본 편집과 런타임 전용 편집은 파일이 생기는 위치와 재부팅 후 유지가 달라요. 아래는 편집, 병합 확인, 목록형 지시어를 비우는 이유예요.

![systemctl edit 사용법: drop-in 오버라이드 정리 소제목 카드. 한눈에 보기, drop-in과 전체 편집 비교, 단계별로 systemctl edit 사용하기, 목록형 지시어는 빈 값으로 초기화합니다](/static/images/systemctl-edit-sayongbeop/diagram.webp)

## 한눈에 보기

edit는 /etc 아래 유닛 이름.d/override.conf를 만들어요. 적용하려면 데몬 리로드 뒤 서비스를 재시작해야 동작이 바뀌는 경우가 많아요. 병합 결과는 cat으로 확인해요. 원본을 직접 고치면 패키지 업데이트와 충돌해요.

## drop-in과 전체 편집 비교

표는 edit, full, runtime이 만드는 파일과 재부팅 후 유지를 나눈 거예요. 일부만 바꿀 때는 drop-in, 유닛 전체를 대체할 때만 full, 재부팅 때 사라져도 되면 runtime이에요. 원본 유닛 파일은 세 방식 모두 직접 수정하지 않아요.

| 방식 | 명령 | 만들어지는 파일 | 원본 유닛 수정 | 재부팅 후 유지 |
| --- | --- | --- | --- | --- |
| drop-in 오버라이드 | `systemctl edit 유닛` | `/etc/systemd/system/유닛.d/override.conf` | 아니요 | 유지됩니다 |
| 전체 사본 편집 | `systemctl edit --full 유닛` | `/etc/systemd/system/유닛` | 아니요(사본 생성) | 유지됩니다 |
| 런타임 오버라이드 | `systemctl edit --runtime 유닛` | `/run/systemd/system/유닛.d/override.conf` | 아니요 | 사라집니다 |

## 단계별로 systemctl edit 사용하기

이름 확인, 편집, 내용, 병합, 적용 순서로 하면 다른 유닛을 고치는 실수를 막아요.

### 편집할 유닛 이름 확인

systemctl status에 나온 유닛 이름을 그대로 써요. 템플릿 유닛이면 인스턴스 이름까지 포함해요. 비슷한 이름의 사용자 유닛과 시스템 유닛을 섞지 마세요.

### 편집기 열기

edit 유닛이름으로 오버라이드 파일을 열어요. 전체 사본이 필요하면 full 옵션, 재부팅 때 지울 거면 runtime 옵션이에요. 저장하지 않고 닫으면 파일이 안 생겨요.

### 오버라이드 내용 작성

필요한 섹션 헤더를 적고 바꿀 지시어만 넣어요. 섹션 이름이 없으면 병합이 무시돼요. 목록형 지시어는 빈 값으로 비운 뒤 새 값을 적어야 원본과 합쳐지지 않아요.

### 병합 결과 확인

cat으로 원본과 drop-in이 합쳐진 결과를 봐요. 기대한 지시어가 최종에 있는지, 옛 값이 남았는지 확인해요. 파일이 있는데 cat에 없으면 유닛 이름이 다른 거예요.

### 서비스에 적용

daemon-reload로 유닛 정의를 다시 읽게 한 뒤 서비스를 재시작해요. 리로드만으로는 이미 뜬 프로세스의 실행 파일이 안 바뀔 수 있어요. 상태와 로그로 새 설정이 적용됐는지 봐요.

## 목록형 지시어는 빈 값으로 초기화합니다

ExecStart처럼 여러 줄이 쌓이는 지시어는 drop-in에 새 줄만 쓰면 원본 명령과 같이 실행돼요. 빈 값으로 한 번 비우고 그 다음에 원하는 명령을 적어야 교체예요. 환경 변수 목록도 같은 방식으로 초기화가 필요한지 man 페이지의 그 지시어를 봐요.

## 상황별 선택 가이드

환경 파일 경로나 재시작 정책만 바꾸면 drop-in이 맞아요. 유닛 거의 전체를 바꿀 거면 full 사본을 검토하되, 업스트림 변경을 따라가지 못하는 비용을 알아 두세요. 시험은 runtime으로 하고, 재부팅 전에 지우거나 etc로 옮기세요. 여러 대면 drop-in 파일을 설정 관리로 배포해요.

## 자주 하는 실수와 주의할 점

daemon-reload를 빼먹으면 파일은 있는데 옛 정의로 떠요. 섹션 헤더를 빠뜨리면 지시어가 무시돼요. ExecStart를 추가만 하면 명령이 두 번 돌아요. runtime 파일을 영구 설정으로 착각하면 재부팅 후 사라져요. 벤더 원본을 직접 고치면 패키지 업데이트가 덮어요.

## 자주 묻는 질문

직접 수정과의 차이, 적용이 안 될 때, 되돌리기, ExecStart, runtime이 반복돼요.

### systemctl edit와 유닛 파일을 직접 수정하는 것의 차이는 무엇인가요?

edit는 오버라이드만 남겨 원본과 패키지 업데이트를 살려요. 원본을 고치면 다음 패키지 갱신과 충돌하거나 덮여요. 병합 결과로 최종 동작을 확인하면 돼요.

### 편집했는데 서비스 동작이 그대로입니다. 무엇을 확인해야 하나요?

daemon-reload와 재시작을 했는지, cat 결과에 지시어가 있는지, 유닛 이름이 맞는지 봐요. 다른 유닛이 그 포트를 쓰고 있을 수도 있어요. 로그의 시작 명령을 오버라이드와 비교해요.

### drop-in 오버라이드를 원래대로 되돌리려면 어떻게 하나요?

override 파일을 지우거나 edit로 내용을 비운 뒤 daemon-reload와 재시작을 해요. runtime이면 그 경로의 파일을 지우면 재부팅 전에도 사라지게 할 수 있어요. 지우기 전에 cat으로 어떤 값이 빠지는지 봐요.

### ExecStart를 바꿨는데 기존 명령도 같이 실행됩니다. 왜 그런가요?

목록형 지시어라 drop-in 줄이 원본에 추가되기 때문이에요. 빈 값으로 초기화한 다음 새 명령을 적어야 교체예요. 병합 결과에서 명령이 한 줄만 남았는지 확인해요.

### --runtime 옵션은 언제 쓰면 좋나요?

재부팅 전에 시험을 끝내고 설정을 남기지 않을 때 써요. 파일은 /run 아래에 생겨서 재부팅하면 사라져요. 영구 변경으로 확인되면 etc의 drop-in으로 다시 적어요.

## 한눈에 보기

Koyeb와 Render는 둘 다 저장소를 연결하면 빌드와 배포를 자동으로 처리하는 배포 플랫폼이에요. 서버를 직접 만들지 않아도 컨테이너 이미지나 소스 저장소를 올려 웹 서비스를 띄울 수 있고, TLS 인증서가 자동으로 붙는 커스텀 도메인, 환경 변수와 시크릿, 빌드 로그와 런타임 로그, 이전 배포로 되돌리는 롤백 같은 기본 기능을 대시보드에서 제공해요. 즉 “서버 운영 자체”를 플랫폼에 맡기고, 애플리케이션 코드와 설정에만 집중하는 모델이에요.

차이는 무료 플랜의 무게중심이에요. Koyeb은 웹 서비스 중심으로 무료 인스턴스를 제공하고, 요청이 없으면 서비스를 내려 두는 방식으로 비용을 줄여요. Render는 무료 웹 서비스와 무료 정적 사이트를 함께 제공하고, 데이터베이스나 백그라운드 작업까지 같은 플랫폼에서 다루는 쪽에 가까워요. 그래서 “API 서버 하나만 필요하다”와 “사이드 프로젝트 전체를 한곳에 두고 싶다”가 첫 번째 갈림길이 돼요.

여기서 중요한 전제가 있어요. 두 플랫폼의 무료 플랜 정책은 시점에 따라 조정되기 때문에, 서비스 개수나 인스턴스 사양, 리전, 데이터베이스 무료 제공 범위는 반드시 공식 가격 페이지에서 다시 확인해야 해요. 이 글은 개념과 절차를 중심으로 비교하고, 확정적인 수치나 가격은 다루지 않아요.

## Koyeb 무료 플랜의 특징

Koyeb의 무료 플랜은 “작은 웹 서비스를 빠르게 올리는 것”에 최적화되어 있어요. 저장소를 연결하면 빌드가 돌아가고, 빌드가 끝나면 컨테이너가 뜨면서 공개 주소가 발급돼요. Dockerfile이 있으면 그대로 쓰고, 없으면 빌드팩이 언어를 감지해서 빌드 절차를 만들어 줘요. 이미 빌드된 컨테이너 이미지를 레지스트리에서 가져오는 방식도 지원하기 때문에, 로컬에서 만든 이미지를 그대로 배포하려는 팀에 잘 맞아요.

무료 인스턴스는 유휴 상태에서 서비스를 내려 두는 방식으로 운영돼요. 이 구조 덕분에 무료로 서비스를 유지할 수 있지만, 오랜만에 들어온 첫 요청은 서비스가 올라오는 동안 기다리게 돼요. 그래서 개인 프로젝트나 데모, 내부 도구처럼 간헐적으로 호출되는 서비스에 적합하고, 외부에 공개된 상시 API에는 유료 인스턴스를 검토하는 편이 안전해요.

설정 면에서는 대시보드에서 서비스, 환경 변수, 도메인, 헬스 체크를 다루고, 자동화가 필요하면 CLI와 API로 같은 작업을 스크립트화할 수 있어요. 무료 플랜에서 선택할 수 있는 리전과 서비스 개수는 제한이 있을 수 있으니, 배포 전에 공식 문서의 플랜 설명을 확인해 두세요.

## Render 무료 플랜의 특징

Render의 무료 플랜은 서비스 종류가 넓다는 점이 특징이에요. 무료 웹 서비스는 일정 시간 요청이 없으면 잠들고, 다음 요청이 들어오면 다시 깨어나는 방식으로 동작해요. 잠들어 있는 동안 들어온 요청은 서비스가 준비될 때까지 대기하게 되므로, 첫 응답 지연을 사용자 경험에서 어떻게 처리할지 미리 정해 두는 게 좋아요. 반면 정적 사이트는 무료로 호스팅되면서 잠들지 않기 때문에, 프론트엔드를 정적으로 빌드해 두고 API만 무료 웹 서비스로 두는 조합이 실용적이에요.

Render는 render.yaml 블루프린트를 통해 인프라를 선언적으로 관리할 수 있어요. 서비스 정의, 빌드 명령, 시작 명령, 환경 변수, 디스크와 데이터베이스 연결을 파일로 남길 수 있어서, 저장소를 보는 것만으로 배포 구성을 파악할 수 있어요. 팀 단위로 운영하거나 스테이징과 프로덕션 구성을 나눠야 할 때 이 방식이 특히 유용해요.

주의할 점은 무료 데이터베이스의 수명이에요. Render의 무료 데이터베이스는 보관 기간 제한이 있어서, 만료 전에 유료 플랜으로 전환하거나 데이터를 백업하고 외부 데이터베이스로 옮기는 계획을 세워야 해요. 학습용이나 프로토타입 단계에서는 충분하지만, 데이터가 계속 쌓이는 서비스라면 처음부터 유료 데이터베이스를 전제로 설계하는 편이 안전해요.

## 배포 절차: 두 플랫폼에서 공통으로 확인할 흐름

플랫폼 이름만 다를 뿐, 무료 플랜으로 웹 서비스를 올리는 절차는 거의 같은 순서로 진행돼요. 아래 항목을 체크리스트처럼 하나씩 확인하면 두 플랫폼 어디서든 같은 방식으로 배포할 수 있어요.

### 저장소와 브랜치 연결

계정을 만들고 대시보드에서 새 웹 서비스를 생성한 뒤, 배포할 GitHub 저장소를 연결해요. 이때 프로덕션 브랜치를 명확히 지정하고, 필요하면 특정 브랜치를 미리보기 환경으로 쓰는 설정을 검토해요. 저장소 접근 권한은 최소 범위로 주고, 조직 저장소라면 관리자 승인이 필요한지 먼저 확인해 두세요.

### 빌드와 시작 명령

Dockerfile이 있으면 그대로 쓰고, 없으면 플랫폼이 언어를 감지해 빌드를 구성해요. 빌드 명령과 시작 명령이 실제로 로컬에서 검증된 것과 같은지 확인하는 게 중요해요. 시작 명령이 포그라운드에서 실행되어야 하고, 플랫폼이 주입하는 포트 환경 변수를 애플리케이션이 그대로 읽도록 설정해야 해요. 이 부분을 놓치면 빌드는 성공하는데 서비스가 계속 재시작되는 상황이 생겨요.

### 환경 변수와 시크릿

데이터베이스 접속 정보, 외부 API 키, 세션 비밀값은 코드가 아니라 플랫폼의 환경 변수와 시크릿 기능에 넣어요. 무료 플랜에서도 시크릿을 따로 관리하는 기능을 제공하니, 값이 로그에 찍히지 않도록 애플리케이션 로깅 설정도 함께 점검해요. 환경 변수를 바꾸면 재배포가 필요하다는 점도 기억해 두세요.

### 도메인, 헬스 체크, 로그

기본 주소가 발급되면 커스텀 도메인을 연결하고 인증서가 자동 발급되는지 확인해요. 헬스 체크 경로를 지정해 두면 배포 후 서비스가 정상인지 플랫폼이 판단할 수 있어요. 마지막으로 빌드 로그와 런타임 로그를 열어 기동 실패, 포트 바인딩 오류, 메모리 부족 같은 신호가 없는지 확인하는 것으로 배포를 마무리해요.

## 상황별 선택 기준

컨테이너 이미지를 그대로 올리고 싶다면 Koyeb이 간결해요. 이미지 기반 배포는 빌드 환경 차이를 줄여 주고, 로컬에서 검증한 실행 환경을 거의 그대로 옮길 수 있어요. 반면 프론트엔드 정적 사이트와 API, 데이터베이스를 한 대시보드에서 관리하고 싶다면 Render 쪽 구성이 편해요. 블루프린트로 배포 구성을 코드로 남길 수 있다는 점도 팀 운영에서 큰 차이를 만들어요.

첫 응답 지연이 사용자 경험에 민감한 서비스라면 무료 플랜만으로 버티기 어려울 수 있어요. 이때는 최소 사양의 유료 인스턴스로 전환하는 비용과, 직접 서버를 운영할 때 드는 관리 비용을 함께 비교해 보세요. 반대로 간헐적으로 호출되는 내부 도구나 데모 환경이라면 유휴 시 내려가는 동작이 오히려 비용 절감으로 이어져요.

데이터가 계속 쌓이는 서비스라면 데이터베이스 정책을 먼저 확인하세요. 무료 데이터베이스의 보관 기간 제한 여부, 백업 제공 여부, 만료 시 데이터 이동 절차를 미리 정해 두면 나중에 마이그레이션으로 시간을 쓰지 않아요. 리전 선택도 함께 보세요. 무료 플랜에서 선택 가능한 리전이 제한되면 사용자와의 물리적 거리가 지연 시간에 영향을 줄 수 있어요.

## 주의할 점

무료 플랜의 가장 큰 제약은 유휴 시 서비스가 내려간다는 점이에요. 외부 모니터링이 주기적으로 헬스 체크를 호출하면 서비스가 계속 깨어 있어 무료 한도를 빠르게 소진할 수 있어요. 모니터링 주기를 조정하거나, 정말 필요한 알림만 남기는 방식으로 운영해 보세요.

무료 데이터베이스는 만료와 백업을 전제로 설계해야 해요. 만료 시점이 다가오면 유료 전환 여부를 결정하고, 그 전에 덤프를 떠서 외부 데이터베이스로 옮길 수 있도록 절차를 문서화해 두세요. 로그 보관 기간과 빌드 로그 용량도 플랜마다 다르니, 장애 원인을 추적해야 하는 서비스라면 로그를 외부로 보내는 구성을 고려하는 편이 좋아요.

플랫폼 종속도 염두에 두세요. 포트 주입 방식, 빌드 환경 변수, 파일 시스템이 임시로 유지되는 특성 같은 부분은 플랫폼마다 달라요. 로컬 파일에 업로드 파일을 저장하는 구조라면 오브젝트 스토리지로 분리해 두어야 이전이 쉬워요. 마지막으로 무료 플랜의 상용 사용 가능 범위와 약관을 확인하고, 필요한 경우 지원 정책도 함께 살펴보세요.

## 자주 묻는 질문

### Koyeb 무료 플랜으로 상용 서비스를 운영해도 되나요?

약관상 허용 범위 안에서는 운영할 수 있지만, 유휴 시 서비스가 내려가는 특성 때문에 상시 응답이 필요한 상용 API에는 권장되지 않아요. 결제가 걸린 트래픽을 받는 서비스라면 최소 사양의 유료 인스턴스로 전환하는 편이 안정적이에요. 전환 전에는 공식 가격 페이지에서 플랜별 제공 범위를 확인하세요.

### Render 무료 웹 서비스가 잠들면 어떻게 되나요?

일정 시간 요청이 없으면 서비스가 잠들고, 다음 요청이 들어오면 다시 깨어나요. 깨어나는 동안 요청은 대기하게 되므로 첫 응답이 느려질 수 있어요. 이 지연이 문제라면 유료 인스턴스로 전환하거나, 정적 사이트와 API를 분리해 지연 영향을 줄이는 구성을 검토하세요.

### 두 플랫폼 모두 무료로 데이터베이스를 쓸 수 있나요?

양쪽 모두 무료 범위의 관리형 데이터베이스를 제공하지만 조건이 달라요. Render의 무료 데이터베이스는 보관 기간 제한이 있어 만료 전 전환 계획이 필요하고, Koyeb는 무료 범위가 플랜 정책에 따라 달라질 수 있어요. 실제 제공 조건은 각 플랫폼의 가격 페이지와 문서에서 확인하는 게 정확해요.

### 무료 플랜에서 첫 응답이 느린 이유는 무엇인가요?

서비스가 내려가 있는 상태에서 요청을 받으면 컨테이너를 다시 올리는 준비 시간이 필요하기 때문이에요. 애플리케이션 부팅 시간이 길수록 지연도 길어지므로, 시작 시 마이그레이션이나 대량 초기화를 줄이면 체감 지연을 줄일 수 있어요. 근본적으로 지연을 없애려면 유휴 시에도 유지되는 인스턴스가 필요해요.

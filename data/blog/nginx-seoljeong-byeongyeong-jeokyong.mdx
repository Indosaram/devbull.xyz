nginx 설정 변경 적용은 대부분 reload로 끝낼 수 있고, restart는 프로세스를 새로 띄워야 하는 변경에만 쓰면 됩니다. 설정 파일을 고친 뒤에는 먼저 문법 검사를 통과시키고, 그다음 마스터 프로세스에 reload 신호를 보내는 순서가 안전해요. 이 글은 그 판단 기준과 실제 명령 순서, 반영이 안 될 때 확인할 지점을 정리해요.

## 한눈에 보기

nginx 설정 변경 적용은 "수정 → 검사 → 신호 → 확인" 네 단계로 진행해요. 이 순서를 지키면 오타 하나로 트래픽이 끊기는 상황을 대부분 피할 수 있어요.

- 바꿀 설정 파일이 실제로 로드되는 파일인지 확인해요.
- `nginx -t`로 문법과 참조 경로를 검사해요.
- `nginx -T`로 include가 병합된 최종 설정을 눈으로 확인해요.
- 마스터 프로세스에 reload 신호를 보내요.
- 응답 헤더, 액세스 로그, 에러 로그로 반영 여부를 확인해요.

핵심은 검사와 반영을 분리하는 거예요. 검사 없이 신호부터 보내면, 설정 오류가 그대로 운영 요청 경로에 영향을 줄 수 있어요. 반대로 검사를 통과한 뒤 신호를 보내면, 새 설정에 문제가 있어도 nginx가 적용을 거부하고 이전 설정을 그대로 유지해요.

## reload와 restart는 무엇이 다른가요

nginx는 마스터 프로세스와 워커 프로세스로 역할이 나뉘어 있어요. 마스터는 설정을 읽고 워커를 관리하며, 워커가 실제 클라이언트 요청을 처리해요. reload는 마스터에 HUP 신호를 보내 새 설정을 다시 읽게 하고, 새 워커를 띄운 뒤 기존 워커를 정리하는 방식이에요. 기존 워커는 처리 중인 요청을 마무리하고 종료하므로, 연결을 받는 소켓은 그대로 유지돼요.

restart는 프로세스를 통째로 내렸다가 다시 올려요. 설정뿐 아니라 바이너리, 로드된 모듈, 프로세스가 물고 있던 자원까지 새로 초기화돼요. 대신 프로세스가 내려가 있는 짧은 구간에 요청이 실패할 수 있어요.

| 항목 | reload | restart |
| --- | --- | --- |
| 전달 방식 | 마스터에 HUP 신호 | 프로세스 종료 후 재기동 |
| 처리 중인 요청 | 마무리 후 종료 | 끊길 수 있음 |
| 새 설정에 문법 오류가 있을 때 | 적용을 거부하고 이전 설정 유지 | 기동 실패로 서비스 중단 위험 |
| 소켓 유지 | 유지 | 잠시 닫힘 |
| 설정 파일 외 변경 | 반영되지 않음 | 반영됨 |
| 어울리는 상황 | 라우팅, 프록시 대상, 인증서 교체 | 바이너리 교체, 모듈 추가, 프로세스 자원 변경 |

표에서 눈여겨볼 줄은 "설정 파일 외 변경"이에요. 시스템의 파일 디스크립터 한도나 systemd 유닛 값처럼 nginx 설정 파일 바깥에서 바꾼 값은 reload로 반영되지 않아요. 이런 변경은 프로세스를 새로 띄워야 적용돼요.

## 단계별 적용 방법

### 설정 파일 위치와 include 구조 확인

nginx 설정은 보통 `/etc/nginx/nginx.conf`에서 시작하고, `include` 지시자로 `conf.d` 아래 파일이나 `sites-enabled` 같은 디렉터리의 파일을 끌어와요. 배포판마다 기본 경로가 다르니, 편집한 파일이 실제로 로드되는지 먼저 확인하는 게 좋아요. `nginx -T`를 실행하면 include가 모두 펼쳐진 최종 설정이 출력돼요. 편집한 파일 내용이 이 출력에 보이지 않는다면 include 경로나 심볼릭 링크가 어긋난 거예요.

### 문법 검사

`nginx -t`는 설정 문법과 include 경로, 인증서 파일 접근 가능 여부까지 확인해요. 통과하면 설정 파일 테스트 성공 메시지와 함께 정상 종료 코드가 떨어지고, 실패하면 문제가 된 파일과 줄 위치를 알려줘요. 이때 출력된 줄부터 확인하면 대부분 원인을 바로 찾을 수 있어요.

검사는 반드시 실행 중인 nginx가 읽는 것과 같은 설정을 대상으로 해야 해요. 배포 스크립트가 다른 경로의 설정 파일을 검사하면 아무 의미가 없어요. 컨테이너에서 nginx를 띄웠다면 호스트가 아니라 컨테이너 안에서 검사해야 해요.

### 병합된 설정 확인

`nginx -T`는 문법 검사와 함께 병합된 설정 전체를 출력해요. 같은 이름의 `upstream` 블록이 여러 파일에 흩어져 있거나, `server` 블록이 중복 선언된 경우처럼 눈으로 찾기 어려운 문제를 잡는 데 유용해요. 출력량이 많으니 파일 단위로 나눠 보고, 최근에 손댄 블록이 예상한 위치에 있는지 확인해요.

### reload 실행

systemd로 관리하는 환경이라면 `systemctl reload nginx`를 쓰면 돼요. 유닛 파일에 reload 동작이 정의되어 있어서 신호를 직접 다루지 않아도 돼요. 신호를 직접 보내려면 `nginx -s reload`를 쓰거나, 마스터 프로세스의 PID를 확인해 `kill -HUP <마스터 PID>`를 실행해요. PID 파일 경로는 배포판과 빌드 옵션에 따라 다르니 `nginx -T` 출력이나 실행 중인 프로세스로 확인하는 게 정확해요.

컨테이너 환경이라면 컨테이너 안에서 같은 명령을 실행해요. 컨테이너를 통째로 재시작하면 무중단 이점이 사라지니, 설정만 바꾼 경우에는 reload를 먼저 시도하는 편이 좋아요.

### 반영 확인

설정이 반영됐는지는 응답 헤더와 로그로 확인해요. 새로 추가한 `add_header`나 리다이렉트 규칙이 응답에 나타나는지 보고, 에러 로그에 새 설정 관련 경고가 없는지 확인해요. 프록시 대상 서버를 바꿨다면 액세스 로그의 업스트림 주소가 바뀌었는지도 함께 봐요.

reload 직후에는 기존 워커가 처리 중인 요청을 마무리하는 구간이 있어요. 그래서 아주 짧은 순간에는 이전 설정과 새 설정이 함께 동작할 수 있어요. 이 동작을 모르면 "왜 어떤 요청은 새 규칙이 안 먹지" 하는 혼동이 생겨요.

### 되돌리기

변경 전 설정을 백업해 두면 롤백이 단순해져요. 백업본을 원래 경로로 되돌리고 다시 `nginx -t`로 검사한 뒤 reload하면 돼요. 문제가 된 설정 파일만 이전 내용으로 교체하는 방식이 가장 빠르고, 다른 변경까지 함께 되돌리지 않아도 돼요.

## 상황별 선택 기준

어떤 변경이 reload로 충분한지 판단하는 기준은 "설정 파일 안에서 끝나는 변경인가"예요.

- 프록시 대상이나 `upstream` 구성 변경: reload로 충분해요.
- TLS 인증서 교체: reload로 반영돼요. 인증서 파일 권한과 경로를 먼저 확인해요.
- 라우팅 규칙, 리다이렉트, 헤더 추가: reload로 충분해요.
- `listen` 지시자나 소켓 경로 변경: reload로도 반영되지만 바인딩 실패 여부를 에러 로그로 반드시 확인해요.
- nginx 바이너리 업그레이드, 동적 모듈 추가: restart가 필요해요.
- 워커 프로세스 수, 파일 디스크립터 한도, systemd 유닛 값 변경: 프로세스를 새로 띄워야 반영돼요.

바이너리 교체의 경우에는 무중단 교체 방식이 따로 마련되어 있어요. 급하지 않은 상황이라면 공식 문서의 업그레이드 절차를 먼저 읽고 진행하는 편이 안전해요.

## 주의할 점

문법 검사 없이 reload하는 습관은 가장 흔한 사고 원인이에요. `nginx -t`는 비용이 거의 들지 않으니 배포 스크립트에 반드시 넣는 게 좋아요.

include 경로와 심볼릭 링크도 자주 걸리는 지점이에요. 파일을 새로 만들었는데 include 패턴에 걸리지 않으면 아무 일도 일어나지 않아요. 반대로 쓰지 않는 파일이 include되어 있으면 의도하지 않은 설정이 함께 적용돼요.

같은 이름의 `upstream`을 여러 파일에 정의하면 중복 선언 오류가 나요. 설정을 쪼개 관리한다면 이름 규칙을 정해 두는 게 좋아요.

reload가 실패하면 nginx는 이전 설정을 유지해요. 그래서 "reload 명령이 성공했는데 동작이 그대로"인 상황은 대부분 검사 단계에서 조용히 넘어간 문제이거나, 편집한 파일이 로드 대상이 아닌 경우예요. 이때는 `nginx -T`로 실제 병합 결과를 확인하는 게 가장 빠른 길이에요.

컨테이너에서는 설정 파일이 이미지 안에 들어 있는지, 볼륨으로 마운트되는지도 확인해야 해요. 마운트된 파일을 호스트에서 교체하는 방식은 편집기 저장 동작에 따라 inode가 바뀌면서 컨테이너가 보는 파일과 어긋날 수 있어요.

## 자주 묻는 질문

### nginx -t는 통과하는데 reload 후에도 이전 설정이 적용된 것 같아요.

검사한 파일과 실행 중인 nginx가 읽는 파일이 다를 가능성이 커요. `nginx -T`로 병합된 설정을 출력해, 바꾼 내용이 실제로 포함되어 있는지 먼저 확인해 보세요. 포함되어 있다면 응답 헤더나 액세스 로그를 보고 어느 블록이 우선 적용되는지 확인해야 해요.

### reload와 restart 중 무엇을 먼저 시도해야 하나요?

설정 파일만 바꾼 경우에는 reload를 먼저 시도하는 게 기본이에요. 연결을 유지하면서 새 설정을 적용할 수 있기 때문이에요. 바이너리나 모듈, 프로세스 자원처럼 설정 파일 바깥의 요소를 바꿨다면 처음부터 restart로 진행해요.

### 설정 파일을 바꿨는데 반영이 안 돼요. 어디부터 확인해야 하나요?

편집한 파일이 include 대상인지, 심볼릭 링크가 올바른지, 문법 검사에서 경고가 나오지 않았는지 순서대로 확인해요. 그다음 에러 로그에서 reload 시점의 메시지를 찾아보세요. 적용 거부 메시지가 있다면 그 줄이 원인이에요.

### 컨테이너에서 실행 중인 nginx 설정은 어떻게 반영하나요?

호스트가 아니라 컨테이너 안에서 문법 검사를 하고 reload 신호를 보내야 해요. 컨테이너를 재시작하면 무중단 이점이 사라지므로, 설정 변경만이라면 reload를 우선 고려해요. 마운트 방식으로 설정을 주입한다면 파일 교체 후 컨테이너가 새 내용을 보고 있는지도 확인해요.

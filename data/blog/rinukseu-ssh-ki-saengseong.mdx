리눅스 ssh 키 생성은 `ssh-keygen`으로 개인키와 공개키를 한 쌍 만들고, 공개키만 서버 `authorized_keys`에 넣는 흐름이에요. 새 서버는 ed25519를 먼저 검토하고, 오래된 장비나 외부 시스템과 맞춰야 할 때만 RSA를 비교해요. 개인키는 작업 환경에만 두고, `~/.ssh`와 개인키, `authorized_keys` 권한을 좁히지 않으면 OpenSSH가 키를 무시해요. 등록 뒤에는 `ssh -i`로 접속하고, 실패하면 `-v`로 키를 못 찾는지 권한 때문에 거절하는지 나눠 봐요.

## 한눈에 보기

키 인증의 기준은 “개인키는 내 쪽에만, 공개키만 서버에”예요. 공개키는 `~/.ssh/authorized_keys`에 들어가고, 개인키는 접속하는 클라이언트가 가져요. 둘을 바꾸면 키를 잘못 복사하거나 권한을 느슨히 두기 쉬워요.

운영에서 자주 쓰는 순서는 이래요.

- 키 종류: 신규 환경은 ed25519, 레거시 연동은 RSA를 비교해요.
- 키 쌍: `ssh-keygen -t ed25519 -C "ops@example.com"`를 실행해요.
- 공개키: `cat ~/.ssh/id_ed25519.pub`로 `.pub` 내용만 읽어요.
- 서버 등록: `ssh-copy-id -i ~/.ssh/id_ed25519.pub user@host`를 쓰거나 공개키를 직접 추가해요.
- 권한: `~/.ssh`, `authorized_keys`, 개인키 권한을 각각 좁혀요.
- 접속: `ssh -i ~/.ssh/id_ed25519 user@host`로 인증이 되는지 봐요.

단일 서버에도 그대로 쓰고, 배포 자동화나 점프 호스트도 같은 개념이에요. 자동화는 키를 어디에 두고 어느 계정에 연결할지까지 같이 정해야 해요.

## 키 종류 비교

기준은 “최신 알고리즘”이 아니라 “서버와 클라이언트가 함께 지원하는가”예요. OpenSSH에서는 ed25519가 흔한 선택이고, 오래된 장비나 특정 솔루션에는 RSA가 아직 필요해요. ECDSA는 조직 표준이 있을 때 검토해요.

| 항목 | ed25519 | RSA | ECDSA |
| --- | --- | --- | --- |
| 키 길이 | 짧고 관리 부담이 적음 | 상대적으로 긴 키를 씀 | 곡선 기반이라 짧은 편 |
| 호환성 | 최신 OpenSSH에서 무난 | 오래된 시스템과 호환 범위가 넓음 | 환경별 지원 차이를 봐야 함 |
| 권장 상황 | 신규 서버, 일반 운영 접속 | 레거시 장비, 외부 시스템 연동 | 조직 표준이 정해진 경우 |
| 운영 메모 | 기본 선택지로 검토 | `-b`로 키 길이를 지정 | 서버와 클라이언트 지원 여부를 봄 |

ed25519가 모든 환경의 정답은 아니에요. 서버 OpenSSH, 외부 서비스, 조직 보안 기준을 같이 봐요. 호환 문제가 없으면 ed25519를 먼저 고르고, 벤더 장비와 맞춰야 하면 RSA를 검토해요.

새로 만들 때는 기존 키를 덮어쓰지 않게 저장 경로를 봐요. `ssh-keygen`은 기본 경로에 파일이 있으면 덮어쓸지 묻으므로, 운영 키 디렉터리에서는 파일 이름을 따로 주는 편이 안전해요.

## 단계별 생성 방법

생성, 공개키 확인, 서버 등록, 권한, 접속 순서로 가면 개인키를 서버에 올리는 실수를 줄일 수 있어요.

### 키 쌍 만들기

`ssh-keygen -t ed25519 -C "ops@example.com"`를 실행해요. `-C`에는 키를 구분할 주석을 넣는데, 개인 메일 대신 운영 별칭을 쓰면 나중에 추적이 쉬워요. 저장 경로와 패스프레이즈를 묻고, 기본 경로를 쓰면 `~/.ssh/id_ed25519`와 `~/.ssh/id_ed25519.pub`가 생겨요.

패스프레이즈는 비울 수 있지만, 개인키 유출을 대비해 두는 편이 안전해요. 사람이 매번 입력할 수 없는 배포라면 패스프레이즈 없는 키를 그냥 두기보다, 전용 배포 키와 좁은 권한, 시크릿 저장소를 같이 설계해요.

### 공개키 확인

`cat ~/.ssh/id_ed25519.pub`로 공개키를 읽어요. 출력은 `ssh-ed25519`로 시작하고 끝에 주석이 붙어요. `.pub`가 없는 `id_ed25519`는 개인키라서 공유하거나 서버에 올리면 안 돼요.

복사할 때 줄바꿈이 깨지지 않게 해요. `authorized_keys`에는 키가 여러 줄로 쌓이므로, 기존 줄을 지우지 않고 필요한 공개키만 추가해요.

### 서버에 등록

`ssh-copy-id -i ~/.ssh/id_ed25519.pub user@host`는 공개키를 원격 `~/.ssh/authorized_keys`에 추가해요. 명령이 없거나 직접 배포해야 하면 공개키만 복사해 그 파일에 붙여요. 원격 홈과 `.ssh` 권한도 같이 정리해요.

서버에 가는 것은 공개키예요. 개인키를 서버에 두면 그 서버가 뚫렸을 때 다른 서버로 이동하는 발판이 돼요. “서버에는 공개키만, 클라이언트에는 개인키만”을 기본으로 둬요.

### 권한 정리

로컬은 `chmod 700 ~/.ssh`, `chmod 600 ~/.ssh/id_ed25519`를 적용해요. 서버는 `chmod 700 ~/.ssh`, `chmod 600 ~/.ssh/authorized_keys`를 봐요. 권한이 느슨하면 OpenSSH가 키를 무시하거나 인증을 거절해요.

홈 디렉터리가 다른 사용자에게 쓰기 가능해도 키 인증이 실패할 수 있어요. 권한이 맞아도 SELinux, 마운트 옵션, sshd 설정이 막을 수 있으니 실패가 반복되면 로그와 설정을 같이 봐요.

### 접속 확인

`ssh -i ~/.ssh/id_ed25519 user@host`로 접속해요. 되면 `~/.ssh/config`에 Host 별칭을 두어 명령을 줄여요. `Host ops-server`, `HostName server.example.com`, `User deploy`, `IdentityFile ~/.ssh/id_ed25519`를 넣으면 `ssh ops-server`로 접속해요.

실패하면 `ssh -v user@host`로 어느 단계에서 거절되는지 봐요. 키를 못 찾는지, 권한 때문에 무시되는지, `authorized_keys`에 없는지, 호스트 키 확인에서 멈추는지 나누면 원인을 좁혀요.

## ssh-agent와 키 관리

`ssh-agent`는 패스프레이즈를 매번 묻지 않도록 개인키를 메모리에 둬요. `eval "$(ssh-agent -s)"`로 시작하고 `ssh-add ~/.ssh/id_ed25519`로 등록해요. 등록된 키는 `ssh-add -l`로 봐요.

에이전트 포워딩은 편하지만, 뚫린 원격 호스트가 에이전트로 다른 서버에 붙을 수 있어요. 꼭 필요할 때만 켜고 기본은 `ForwardAgent no`로 둬요. 점프 호스트를 쓰면 접근 범위와 세션 정책을 같이 제한해요.

키를 바꿀 때는 새 키를 만든 뒤 공개키를 추가하고, 접속이 되는 것을 본 다음 기존 공개키를 빼요. 퇴사자나 외부 협력사 키는 목록으로 관리하고, 끝나면 `authorized_keys`에서 바로 제거해요.

## 상황별 선택

신규 리눅스 서버의 일반 접속은 ed25519를 먼저 검토해요. 키가 짧고 관리가 단순하며 최신 OpenSSH에서 무난해요. 이미지가 오래됐거나 대상이 장비라면 지원 알고리즘을 먼저 봐요.

오래된 장비, 네트워크 장비, 외부 솔루션은 RSA를 검토해요. `-b`로 길이를 지정할 수 있지만, 무조건 길게 하기보다 대상이 받는 범위와 조직 기준을 봐요. ECDSA는 조직 표준이나 기존 체계를 유지할 때 골라요.

배포 자동화는 사람 키와 자동화 키를 분리해요. 자동화 키는 시크릿 저장소에 두고, 배포 계정 권한을 최소화하며, 가능하면 허용 명령만 실행되게 서버 설정을 같이 봐요. 같은 공개키를 여러 서버에 넣을 수 있지만, 서버별로 나누면 폐기와 추적이 쉬워요.

## 주의할 점

- 개인키는 서버나 코드 저장소에 올리지 않아요.
- `authorized_keys`와 `.ssh` 권한을 같이 봐요.
- 패스프레이즈를 잃으면 그 키는 복구되지 않아요.
- 호스트 키가 바뀌면 무조건 무시하지 말고 변경 원인을 봐요.
- 퇴사자나 외부 협력사 공개키는 서버에서 빼요.
- 에이전트 포워딩은 필요한 세션에만 켜요.
- 교체할 때는 새 키 접속을 본 뒤 기존 키를 빼요.

`authorized_keys`는 키가 쌓이기 쉬운 파일이에요. 주석을 의미 있게 남기고, 쓰지 않는 키를 정리하면 사고 때 추적이 쉬워요. 줄을 지울 때는 그 키로 붙어 있는 세션이 없는지도 봐요.

## 자주 묻는 질문

### ssh-keygen 없이도 키를 만들 수 있나요?

리눅스에서는 OpenSSH의 `ssh-keygen`이 사실상 표준이에요. 다른 도구로 만든 키도 OpenSSH 형식과 맞으면 쓸 수 있지만, 운영에서는 배포판에 들어 있는 `ssh-keygen`으로 만드는 편이 검증하기 쉬워요.

### 키 파일 이름을 바꾸면 접속이 안 되나요?

이름 자체가 인증을 깨지는 않아요. 다만 클라이언트가 기본 이름을 못 찾으므로 `IdentityFile`이나 `ssh -i`로 경로를 지정해야 해요.

### 패스프레이즈를 잊으면 복구할 수 있나요?

패스프레이즈는 키를 암호화하는 값이라 복구 절차가 없어요. 잊었다면 새 키 쌍을 만들어 공개키를 다시 등록하고, 기존 공개키를 빼는 편이 안전해요.

### 서버에 공개키를 추가했는데도 계속 비밀번호를 묻나요?

`authorized_keys` 경로와 권한, sshd 설정, 접속 계정 홈 권한을 봐요. `ssh -v`로 클라이언트가 어떤 키를 내는지 보고, 서버 로그의 거절 이유와 맞춰요.

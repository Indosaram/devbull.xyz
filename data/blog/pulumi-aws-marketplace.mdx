pulumi aws marketplace는 Pulumi를 AWS Marketplace 조달 흐름으로 계약하고, 실제 인프라는 Pulumi 코드로 배포하도록 역할을 나누는 방식입니다. 핵심은 Marketplace 구독이 AWS 리소스 권한을 대신하지 않는다는 점을 이해하는 것입니다. 따라서 조달 범위, Pulumi 조직 연결, AWS IAM 권한을 각각 확인해야 합니다.

## 한눈에 보기

AWS Marketplace는 소프트웨어를 검색하고 구독하며 청구를 AWS 계정과 함께 관리하는 조달 채널입니다. Pulumi는 코드로 클라우드 인프라를 선언하고 배포하는 도구이며, AWS 공급자를 통해 AWS API를 호출합니다. 두 요소를 함께 쓰면 계약과 결제는 Marketplace 쪽에서, 인프라 변경은 Pulumi 코드와 파이프라인에서 관리하는 구조가 됩니다.

이때 자주 혼동하는 부분이 권한입니다. Marketplace에서 Pulumi 리스팅을 구독해도 AWS 계정 안에 Pulumi용 IAM 역할이 자동으로 생기지는 않습니다. Pulumi가 사용할 자격 증명과 권한은 별도로 설계해야 합니다.

또한 Marketplace 리스팅의 가격, 과금 단위, 계약 기간, 지원 범위는 시점과 판매 방식에 따라 달라질 수 있습니다. 따라서 도입 전에 실제 리스팅의 계약 조건과 Pulumi 공식 문서의 조직 연결 안내를 함께 확인하는 편이 안전합니다.

## Pulumi와 AWS Marketplace의 관계

Pulumi는 특정 클라우드에 종속된 배포 도구라기보다 여러 공급자를 지원하는 인프라 코드 도구입니다. AWS를 대상으로 할 때는 Pulumi AWS 공급자를 사용해 VPC, 서브넷, 로드 밸런서, 데이터베이스 같은 리소스를 코드로 정의합니다. `pulumi preview`로 변경 계획을 확인하고 `pulumi up`으로 적용하는 흐름이 기본입니다.

AWS Marketplace는 이런 Pulumi 사용을 “조달”하는 접점입니다. 조직이 AWS 계정의 청구 체계로 소프트웨어 비용을 관리하거나, 구매 승인 절차를 AWS Marketplace에 맞춰 운영할 때 검토할 수 있습니다. 반대로 실제 배포 대상과 권한은 여전히 AWS 계정과 Pulumi 프로젝트 설정에 있습니다.

Pulumi Cloud를 사용하는 조직이라면 Marketplace 계약과 Pulumi 조직 연결이 필요할 수 있습니다. 이 연결은 리스팅 안내에 따라 진행되며, 연결 후에도 프로젝트의 상태 저장소와 비밀 값 관리 방식은 별도로 정해야 합니다.

## 비교 표: 직접 계약과 Marketplace 조달

| 항목 | AWS Marketplace 조달 | Pulumi와 직접 계약 |
| --- | --- | --- |
| 계약·결제 | AWS 계정 청구 흐름과 함께 관리 | Pulumi 계약과 청구 기준으로 관리 |
| 구매 승인 | AWS 조달 절차를 따르는 조직에 적합 | Pulumi 계약 절차를 따르는 조직에 적합 |
| 비용 가시성 | AWS 비용 관리와 함께 검토 가능 | Pulumi 청구와 내부 예산 기준으로 검토 |
| 권한 설계 | AWS 계정 권한과 별도로 IAM 설계 필요 | 동일하게 IAM과 Pulumi 조직 권한 설계 필요 |
| 적합한 상황 | AWS 청구 통합과 조달 일원화가 중요한 경우 | Pulumi 계약과 지원 체계를 직접 관리하려는 경우 |

표에서 알 수 있듯이 조달 방식이 달라져도 인프라 배포 권한은 자동으로 해결되지 않습니다. Marketplace는 구매와 청구의 편의를 다루고, Pulumi는 인프라 변경의 실행을 다룬다고 구분하면 이해하기 쉽습니다.

## 단계별 도입 방법

먼저 조직의 조달 요구를 정리합니다. AWS 청구로 Pulumi 비용을 통합해야 하는지, 보안 검토와 구매 승인을 어떤 절차로 처리하는지 확인합니다. 이 단계에서 Marketplace 조달이 필요한지, 직접 계약이 더 단순한지 판단할 수 있습니다.

다음으로 AWS Marketplace에서 Pulumi 리스팅을 확인합니다. 리스팅의 설명, 계약 조건, 과금 방식, 지원 범위, 구독 후 연결 절차를 읽고 내부 요구와 맞는지 비교합니다. 확인되지 않은 가격이나 기능을 가정하지 말고 리스팅과 공식 문서에 적힌 범위만 기준으로 삼는 것이 좋습니다.

구독 또는 계약을 진행한 뒤에는 Pulumi 조직과 AWS 계정의 관계를 정리합니다. Pulumi Cloud 조직을 사용하는 경우 리스팅 안내에 따라 조직 연결을 완료하고, 프로젝트를 둘 상태 저장소와 접근 권한을 결정합니다. 조직 구성원에게 필요한 역할만 부여해야 합니다.

이어서 AWS 자격 증명을 구성합니다. Pulumi 프로그램이 AWS API를 호출하려면 IAM 역할, 액세스 키, 프로파일 같은 수단이 필요합니다. 운영 환경에서는 장기 액세스 키를 코드에 두지 말고, 파이프라인이나 실행 환경에 맞는 역할 기반 구성을 우선 검토합니다.

마지막으로 작은 범위의 스택에서 `pulumi preview`와 `pulumi up`을 실행해 검증합니다. 배포 후에는 상태 저장소, 비밀 값, IAM 정책, 비용 태그가 의도대로 동작하는지 확인합니다. 검증이 끝난 뒤에 운영 스택으로 범위를 넓히는 편이 안전합니다.

## 상황별 선택 기준

AWS 청구 통합이 중요한 조직이라면 Marketplace 조달을 검토할 만합니다. 여러 소프트웨어 구매를 AWS 계정 기준으로 관리하고 있다면 계약과 결제가 한 흐름에 모이는 점이 운영상 편리할 수 있습니다.

반대로 Pulumi와의 계약 조건, 지원 채널, 조직 연결 방식을 직접 관리하는 편이 명확하다면 직접 계약이 더 적합할 수 있습니다. 특히 Pulumi Cloud的组织 구조와 권한 체계를 이미 운영 중이라면 기존 체계와 어떻게 맞물리는지 먼저 확인해야 합니다.

Pulumi CLI만으로 코드를 실행하고 상태 저장소를 직접 운영하는 경우에는 Marketplace 구독이 필수라고 단정할 수 없습니다. 이 경우에도 Pulumi Cloud의 관리형 기능이 필요한지, 조직의 조달 정책이 Marketplace를 요구하는지를 기준으로 판단해야 합니다.

## 주의할 점

Marketplace 구독과 AWS IAM 권한을 같은 것으로 보면 안 됩니다. 구독은 조달과 청구에 가깝고, 인프라를 만들고 수정하는 권한은 IAM 정책과 역할에서 나옵니다. Pulumi가 사용하는 자격 증명에는 필요한 리소스 범위에 맞는 최소 권한을 부여해야 합니다.

Pulumi 상태 파일과 비밀 값의 관리 위치도 중요합니다. 상태 저장소를 어디에 두는지, 민감한 값이 코드나 로그에 남지 않는지, 여러 환경의 스택을 어떻게 분리할지 미리 정해야 합니다. 운영 계정과 개발 계정의 자격 증명을 섞지 않는 것도 기본입니다.

리스팅의 계약 조건은 변경될 수 있으므로 도입 시점의 안내를 확인해야 합니다. 과금 단위, 갱신 방식, 해지 절차, 지원 범위가 내부 정책과 맞는지 검토하고, 필요한 경우 재무와 보안 담당자에게 함께 확인하는 편이 좋습니다.

Pulumi 조직의 구성원 권한도 점검해야 합니다. 배포 권한이 있는 사용자와 코드 리뷰만 하는 사용자를 구분하고, 운영 스택에 적용되는 정책을 명확히 하세요. Marketplace를 통해 계약했더라도 이러한 운영 통제는 별도로 설계해야 합니다.

## 자주 묻는 질문

### AWS Marketplace에서 Pulumi를 구독하면 AWS 리소스 권한도 함께 생기나요?

아니요. Marketplace 구독은 조달과 청구에 관련된 절차이고, AWS 리소스를 생성하거나 수정하는 권한은 IAM에서 별도로 부여해야 합니다. Pulumi가 사용할 역할이나 자격 증명의 최소 권한을 먼저 설계하세요.

### Pulumi CLI만 사용하는데 Marketplace가 꼭 필요한가요?

항상 필요한 것은 아닙니다. Marketplace는 조직의 구매 승인과 AWS 청구 통합 요구가 있을 때 검토하는 채널입니다. CLI와 상태 저장소 운영 방식은 별도로 정해야 하므로, Pulumi Cloud 기능 필요 여부와 조달 정책을 함께 확인하세요.

### Marketplace 계약과 Pulumi 코드 배포는 어떻게 연결되나요?

계약은 Pulumi Cloud 조직 사용과 연결될 수 있고, 실제 배포는 Pulumi 프로그램과 AWS 공급자가 수행합니다. 리스팅 안내에 따라 조직 연결과 AWS 자격 증명을 설정한 뒤 `pulumi preview`로 변경 계획을 확인하고 `pulumi up`으로 적용하세요.

### 기존 Pulumi 프로젝트를 Marketplace 도입 후에도 그대로 쓸 수 있나요?

프로젝트 코드는 일반적으로 그대로 사용할 수 있지만, 조직 연결, 상태 저장소, 자격 증명, 접근 권한은 도입 방식에 맞게 점검해야 합니다. 운영 스택을 바로 바꾸기보다 개발 스택에서 먼저 검증하는 편이 안전합니다.

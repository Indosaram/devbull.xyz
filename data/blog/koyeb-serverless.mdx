## 한눈에 보기

Koyeb은 애플리케이션을 앱(App)과 서비스(Service)라는 두 층으로 나눠 관리해요. 앱은 여러 서비스를 묶는 논리적 단위이고, 실제로 트래픽을 받거나 작업을 처리하는 것은 서비스예요. 서비스는 다시 배포 단위로 나뉘고, 각 배포는 하나 이상의 인스턴스로 실행돼요. 이 구조를 먼저 이해하면 대시보드 화면과 CLI 출력이 훨씬 읽기 쉬워져요.

서비스 타입은 크게 두 가지예요. 외부 HTTP 트래픽을 받는 웹 서비스와, 큐 소비나 정기 작업처럼 포트를 열지 않고 도는 워커 서비스예요. 워커는 HTTP 헬스체크 대신 프로세스가 살아 있는지를 기준으로 관리되므로, 배치 작업을 별도 서버 없이 운영할 때 유용해요.

배포 소스는 세 갈래로 정리돼요. GitHub 저장소를 연결해 푸시할 때마다 자동으로 배포하는 방식, 레지스트리에 올린 컨테이너 이미지를 그대로 쓰는 방식, 그리고 CLI나 API로 배포를 직접 만드는 방식이에요. 빌드가 필요하면 Dockerfile을 쓰거나 빌드팩에 맡길 수 있어요. 이미지가 이미 준비되어 있으면 빌드 단계를 건너뛰기 때문에 배포 흐름이 단순해져요.

운영 기능은 대체로 다음 항목으로 정리돼요.

- 요청량에 따른 오토스케일링과 스케일 투 제로
- 최소 인스턴스 수를 유지하는 옵션
- 헬스체크와 무중단 배포, 이전 배포로의 롤백
- 환경변수와 시크릿 관리
- 로그 스트리밍과 기본 메트릭
- 여러 리전 중 선택 배치와 프라이빗 네트워킹
- 관리형 데이터베이스 연동과 GPU 인스턴스 옵션

여기서 짚어 둘 점은 Koyeb이 "서버리스"라는 이름을 쓰지만 실행 단위가 아주 짧은 함수 호출은 아니라는 사실이에요. 요청이 없을 때 인스턴스를 최소로 줄이는 스케일 투 제로가 서버리스다운 성격을 만들고, 평소에는 일반 컨테이너처럼 동작해요. 그래서 기존에 쓰던 프레임워크와 미들웨어를 크게 바꾸지 않고 옮길 수 있어요.

## 단계별 배포 절차

첫 단계는 애플리케이션을 플랫폼에 맞게 다듬는 일이에요. 프로세스가 모든 인터페이스에서 수신하도록 바인딩하고, 수신 포트는 플랫폼이 주입하는 환경변수를 읽어 쓰는 편이 안전해요. 로그는 표준 출력과 표준 에러로 보내야 대시보드에서 바로 확인할 수 있어요. 파일 시스템은 배포마다 초기화된다고 가정하고, 업로드 파일이나 세션은 외부 저장소로 옮겨 두는 게 좋아요.

두 번째는 소스를 정하는 단계예요. GitHub 저장소를 연결하면 브랜치 푸시가 곧 배포가 돼요. 저장소에 Dockerfile이 있으면 그대로 빌드하고, 없으면 빌드팩이 언어를 감지해 빌드해요. 이미 CI에서 이미지를 만들고 있다면 레지스트리 이미지를 지정하는 편이 파이프라인을 단순하게 유지해 줘요.

세 번째는 앱과 서비스를 만드는 단계예요. 대시보드에서 앱을 만들고 그 안에 서비스를 추가하거나, CLI와 API로 같은 작업을 반복할 수 있어요. 이때 서비스 타입을 웹으로 할지 워커로 할지 정하고, 리전과 인스턴스 규격을 고르면 돼요. 처음에는 기본값으로 배포해 보고, 트래픽 패턴을 확인한 뒤 규격을 조정하는 편이 안전해요.

네 번째는 설정을 채우는 단계예요. 환경변수와 시크릿을 나눠 넣고, 헬스체크 경로를 지정해요. 헬스체크는 단순히 프로세스가 살아 있는지만 보는 대신, 데이터베이스 연결처럼 실제 의존성까지 확인하는 엔드포인트를 두면 배포 판정이 정확해져요.

다섯 번째는 배포와 확인이에요. 배포가 끝나면 로그에서 기동 메시지를 확인하고, 기본 제공 도메인으로 요청을 보내 응답을 검증해요. 문제가 있으면 이전 배포로 되돌릴 수 있고, 원인 파악을 위해 빌드 로그와 런타임 로그를 나눠서 봐야 해요.

여섯 번째는 스케일과 도메인 정리예요. 최소 인스턴스를 유지할지, 어느 시점에 늘릴지를 정하고, 필요하면 사용자 도메인을 연결해요. 인증서 발급과 갱신은 플랫폼이 처리하므로 별도 작업이 필요 없어요.

## 배포 후 운영에서 봐야 할 지표

운영 단계에서 가장 먼저 체감되는 것은 스케일 투 제로의 양면성이에요. 트래픽이 없는 시간에는 인스턴스가 줄어 비용이 아껴지지만, 그 뒤 첫 요청은 기동 시간을 포함해 느려질 수 있어요. 사용자 응답 지연에 민감한 API라면 최소 인스턴스를 유지하고, 내부 배치나 관리 도구처럼 호출이 드문 서비스만 완전히 줄이는 식으로 나누는 게 현실적이에요.

다음은 헬스체크와 배포 전략이에요. 헬스체크 경로가 실제 트래픽을 처리할 준비가 됐는지를 제대로 반영하지 않으면, 새 배포가 준비되기 전에 트래픽이 몰려 오류가 늘어날 수 있어요. 기동 시 마이그레이션이나 캐시 워밍이 필요하다면 준비가 끝난 뒤에 통과하는 엔드포인트를 두는 편이 안전해요.

로그와 메트릭은 플랫폼 기본 화면으로 시작하되, 장기 보관이 필요하면 외부 수집기로 보내는 구성을 추가해요. 인스턴스가 자주 늘고 줄면 로그가 여러 곳에 흩어지므로, 요청 식별자를 로그에 남겨 추적이 끊기지 않게 하는 게 중요해요. 배포 시각과 이미지 태그를 로그에 함께 남기면 롤백 판단이 빨라져요.

## 상황별 선택 기준

트래픽 변동이 큰 공개 API라면 Koyeb serverless가 잘 맞아요. 낮 시간에만 호출이 몰리고 밤에는 거의 없는 서비스라면 스케일 투 제로의 이점이 크고, 최소 인스턴스를 하나만 유지해도 콜드 스타트 체감을 크게 줄일 수 있어요.

반대로 지연 시간이 곧 매출인 서비스나, 커널 수준 튜닝이 필요한 서비스는 직접 관리하는 환경이 나아요. Koyeb은 컨테이너를 실행하는 플랫폼이지 서버 자체를 제공하는 서비스가 아니므로, 호스트에 붙는 에이전트나 특수 드라이버가 필요한 경우 제약이 생겨요.

이미 쿠버네티스를 운영 중인 조직이라면 도입 비용을 냉정하게 비교해야 해요. 사이드카, 서비스 메시, 세밀한 네트워크 정책을 이미 잘 쓰고 있다면 Koyeb으로 옮기는 이득이 크지 않을 수 있어요. 반대로 클러스터를 유지할 인력이 없고 배포만 빠르게 하고 싶다면 관리형 플랫폼이 합리적이에요.

워커 서비스는 따로 떼어 두는 편이 좋아요. 웹 서비스와 같은 서비스에 배치 작업을 섞으면 확장 단위가 어긋나서 비용과 안정성 모두 손해를 봐요. 큐 소비, 정기 작업, 외부 API 동기화는 워커로 분리하고 각자 필요한 만큼만 확장해요.

데이터 저장소는 리전을 함께 봐야 해요. 애플리케이션과 데이터베이스가 멀리 떨어져 있으면 요청마다 네트워크 왕복이 붙어요. 관리형 데이터베이스를 함께 쓰거나, 외부 데이터베이스를 쓴다면 같은 리전에 두는 구성을 우선 검토해요.

## 주의할 점

가장 흔한 실수는 로컬 파일 시스템에 상태를 두는 것이에요. 컨테이너는 언제든 교체될 수 있으므로 세션, 업로드 파일, 캐시는 외부 저장소로 빼야 해요. 볼륨 기능을 쓰더라도 여러 인스턴스가 동시에 같은 파일을 다루는 구조는 피하는 게 안전해요.

빌드 시간과 이미지 크기도 관리 대상이에요. 이미지가 커지면 배포마다 끌어오는 시간이 늘고, 스케일 아웃 반응도 느려져요. 멀티 스테이지 빌드로 실행 이미지를 줄이고, 의존성 캐시가 잘 먹도록 레이어 순서를 정리해요.

시크릿은 환경변수와 분리해서 다뤄야 해요. 저장소에 설정 파일을 커밋하거나 로그에 환경변수를 찍는 습관이 있으면 그대로 유출로 이어져요. 플랫폼이 제공하는 시크릿 기능을 쓰고, 값이 바뀌면 재배포가 필요하다는 점도 기억해요.

벤더 종속도 염두에 둬야 해요. 대시보드에서만 설정을 바꾸면 이력이 남지 않고 재현도 어려워져요. Dockerfile과 환경변수 목록, 배포 절차를 저장소에 문서로 남기고, 가능하면 CLI나 API 스크립트로 같은 작업을 반복할 수 있게 해 두면 이전 비용이 크게 줄어요.

비용은 트래픽 패턴에 따라 달라지므로, 도입 전에 공식 가격 페이지에서 과금 기준을 확인하는 게 좋아요. 특히 유휴 시 인스턴스를 줄이는 구조에서는 요청 분포와 기동 시간이 비용과 체감 속도를 동시에 좌우해요(https://www.koyeb.com/pricing).

## 자주 묻는 질문

### Koyeb serverless는 함수 단위 FaaS인가요?

아니에요. Koyeb은 컨테이너로 만든 웹 서비스와 워커 서비스를 실행하는 플랫폼이고, 함수 하나를 개별 단위로 등록하는 방식이 아니에요. 대신 요청이 없을 때 인스턴스를 줄이는 스케일 투 제로 덕분에 서버리스와 비슷한 비용 구조를 가져요.

### 무료로 시작할 수 있나요?

공식 사이트에 무료 사용 범위가 안내되어 있어요. 다만 무료 범위의 조건과 제한은 시점에 따라 바뀔 수 있으므로, 도입 전에 가격 페이지에서 현재 기준을 확인하는 게 안전해요.

### 콜드 스타트가 걱정되는 서비스에도 쓸 수 있나요?

쓸 수 있어요. 최소 인스턴스를 유지하면 스케일 투 제로를 사실상 끄는 것과 비슷한 효과를 내므로 콜드 스타트를 피할 수 있어요. 대신 유휴 시간에도 인스턴스가 유지되므로 비용 구조가 달라진다는 점을 함께 고려해야 해요.

### 기존 Docker 이미지를 그대로 배포할 수 있나요?

네, 레지스트리에 있는 이미지를 지정하면 빌드 없이 배포할 수 있어요. 이 경우 이미지 태그를 고정해 두어야 배포마다 같은 결과가 나오고, 롤백도 예측 가능해져요.

### 데이터베이스는 어떻게 연결하나요?

관리형 데이터베이스를 함께 쓰거나, 외부 데이터베이스의 연결 정보를 환경변수와 시크릿으로 주입하는 방식이 일반적이에요. 어느 쪽이든 애플리케이션과 같은 리전에 두어 네트워크 왕복을 줄이는 구성이 좋아요.

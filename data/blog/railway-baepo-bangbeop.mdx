Railway 배포는 GitHub 푸시로 자동으로 올리거나, CLI로 현재 디렉터리를 올리는 두 갈래가 중심이에요. 어느 쪽이든 빌드 명령, 시작 명령, 포트, 환경 변수가 맞아야 공개 주소가 살아 있어요. 저장소가 없어도 CLI와 Docker 이미지로 올릴 수 있어요. 아래는 준비물, 두 배포 경로, 실패했을 때 로그를 보는 순서예요.

## 한눈에 보기

서비스는 프로젝트 안에 두고, 배포는 그 서비스의 한 차례 실행이에요. Git 연동은 브랜치 푸시가 배포를 깨우고, CLI는 지금 작업 트리를 올려요. Dockerfile이 있으면 런타임을 직접 고정할 수 있어요. 공통으로 환경 변수와 시크릿, 헬스 체크, 도메인을 배포 전에 정해 두면 재배포 때 같은 실수를 반복하지 않아요.

## Railway 배포 방식 비교

표는 GitHub 연동, CLI, Docker를 시작 지점과 확인할 점으로 나눈 거예요. 팀이 리뷰 후 배포하면 Git 연동이 맞고, 저장소 없이 시험하면 CLI가 빨라요. 언어 런타임이 특이하면 Docker로 이미지 안을 고정해요. 방식을 섞어도 되지만, 빌드 명령이 대시보드와 저장소 설정에 둘 다 있으면 어느 쪽이 적용되는지 문서로 확인해요.

| 항목 | GitHub 연동 | CLI 배포 |
|---|---|---|
| 시작 방식 | 저장소와 브랜치를 선택해 서비스에 연결 | 로컬 디렉터리에서 Railway CLI 명령 실행 |
| 재배포 | 저장소 변경에 맞춰 배포 흐름을 구성 | 필요할 때 명령을 다시 실행 |
| 초기 설정 | GitHub 권한 승인과 저장소 선택 필요 | CLI 설치와 로그인 필요 |
| 적합한 상황 | 협업, 지속적 배포, 변경 추적 | 빠른 테스트, 저장소 없는 실험, 임시 배포 |
| 확인 위치 | Railway 대시보드의 배포와 로그 화면 | CLI 출력과 대시보드 배포 화면 |

## 배포 전 준비 사항

시작 명령이 로컬에서 되는지, 앱이 외부에서 접속 가능한 주소에 바인딩하는지를 먼저 봐요. 플랫폼이 알려 주는 포트를 무시하고 고정 포트만 들으면 헬스 체크가 실패해요. 의존성 설치와 빌드가 같은 명령으로 재현되는지도 봐요. 비밀 값은 저장소에 넣지 않고 서비스 설정으로 빼요.

## GitHub 연동으로 배포하는 방법

Railway에서 프로젝트를 만들고 GitHub 저장소와 브랜치를 연결해요. 비공개 저장소도 권한을 승인하면 연결할 수 있어요. 푸시하면 빌드 로그가 생기고, 실패하면 그 로그의 첫 오류가 원인이에요. 자동 배포를 끌 브랜치와 켤 브랜치를 나눠 두면 실험 커밋이 운영으로 올라가지 않아요. 모노레포면 서비스의 루트 경로를 지정해요.

## CLI로 배포하는 방법

CLI로 로그인한 뒤 프로젝트에 연결하고, 현재 디렉터리에서 배포 명령을 실행해요. 저장소가 없어도 이 경로로 올릴 수 있어요. CI에서 쓰려면 토큰을 비밀 값으로 넣고, 로컬과 같은 서비스에 연결됐는지 확인해요. 잘못된 프로젝트에 연결하면 다른 서비스가 덮여요.

## 환경 변수와 도메인 설정

환경마다 변수 세트를 나누고, 운영 값을 스테이징에 그대로 복사하지 않아요. 공개 URL이 변수에 들어가면 그 환경의 도메인과 맞춰요. 도메인은 배포가 성공한 뒤 네트워킹에서 연결하고, DNS 레코드는 안내된 대상만 넣어요. 변수 변경 뒤에는 재배포가 필요한지 화면 안내를 봐요.

## 상황별 선택 기준

혼자 사이드 프로젝트를 자주 고치면 Git 연동이 편해요. 일회성 데모나 저장소 밖 산출물은 CLI가 맞아요. 팀 운영이면 보호된 브랜치와 환경 분리를 먼저 두고, 데이터베이스는 앱 서비스와 따로 두되 연결 문자열만 변수로 넘기세요. 빌드가 무거운 언어는 Docker로 빌드 단계를 고정하는 편이 재현이 좋아요.

## 주의할 점

빌드 성공과 프로세스 생존은 달라요. 시작 직후 바로 죽으면 런타임 로그를 봐요. 사용하지 않는 서비스와 볼륨을 남겨 두면 배포 방법과 상관없이 자원이 남아요. 롤백은 이전 배포를 다시 활성화하는 쪽인지, 코드를 되돌려 재배포하는 쪽인지 팀에서 정해 두세요. 헬스 체크 경로에 인증을 걸면 정상 앱도 실패로 보여요.

## 자주 묻는 질문

저장소 조건과 빌드 실패 위치가 질문을 만들어요.

### GitHub 저장소 없이 Railway에 배포할 수 있나요?

가능해요. CLI로 현재 디렉터리를 올리거나, Dockerfile이 있으면 이미지 기준으로 배포해요. 자동 배포가 필요해지면 그때 저장소를 연결하면 돼요.

### GitHub 저장소가 비공개여도 연동할 수 있나요?

Railway에 해당 저장소 접근을 허용하면 비공개도 연결돼요. 권한이 빠지면 푸시해도 배포가 시작되지 않아요. 조직 저장소면 조직의 앱 설치 범위도 같이 봐요.

### 빌드가 실패하면 어디부터 확인해야 하나요?

배포 로그에서 의존성 설치인지, 빌드 명령인지, 시작 명령인지 첫 오류 구간을 봐요. 로컬에서 같은 명령을 재현해 보고, 없는 환경 변수가 빌드 중에 필요한지도 확인해요. 런타임 오류는 빌드 성공 뒤의 로그에 있어요.

### 데이터베이스도 Railway에서 함께 운영할 수 있나요?

프로젝트에 데이터베이스 서비스를 추가하고, 연결 정보를 앱의 환경 변수로 넘기는 구성이 일반적이에요. 앱을 재배포해도 데이터베이스 볼륨은 따로 남으니, 지우기 전에 백업 여부를 확인해요. 세부 이름은 공식 배포 문서를 봐요.

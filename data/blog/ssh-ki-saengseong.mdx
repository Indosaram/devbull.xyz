SSH 키 생성은 내 컴퓨터에 개인 키와 공개 키 쌍을 만들고, 공개 키만 서버에 등록하는 일이에요. 개인 키는 복사해서 옮기지 않고, 서버에는 공개 키 한 줄만 추가해요. 알고리즘은 새 서버면 ed25519를 먼저 검토하고, 오래된 장비만 RSA가 필요할 수 있어요. 아래는 만들기, 등록, 권한, 상황별 키 분리예요.

![ssh 키 생성 총정리: ssh-keygen부터 배포까지 소제목 카드. 한눈에 보기, 비교 표, 단계별 방법, 상황별 선택](/static/images/ssh-ki-saengseong/diagram.webp)

## 한눈에 보기

키는 사용자 홈의 ssh 디렉터리에 두는 것이 기본이에요. 공개 키는 서버의 authorized_keys에 한 줄로 들어가고, 개인 키는 권한이 느슨하면 클라이언트가 거절해요. 암호를 걸면 키 파일 유출 때 한 단계 더 막히고, CI처럼 사람 입력이 없으면 에이전트나 배포 전용 키를 검토해요. 기존 키를 덮어쓰지 않게 경로를 먼저 확인해요.

## 비교 표

표는 ed25519, RSA, 그 외 알고리즘의 용도를 나눈 거예요. 신규는 ed25519가 널리 쓰이고, 오래된 장비만 RSA를 검토해요. DSA는 새로 만들지 않아요. 옵션 표의 경로와 주석을 쓰면 키가 여러 개일 때 구분하기 쉬워요.

| 항목 | Ed25519 | RSA | ECDSA |
|---|---|---|---|
| OpenSSH 지원 | 지원해요 | 지원해요 | 지원해요 |
| 공개 키 길이 | 짧은 편이에요 | 긴 편이에요 | 중간 정도예요 |
| 호환성 | 최신 환경에서 널리 쓰여요 | 오래된 환경과 맞추기 쉬워요 | NIST 곡선 환경에서 써요 |
| 주로 쓰는 상황 | 새 개발용 키, Git 호스팅 | 기존 장비, 조직 표준 | 조직에서 ECDSA를 요구할 때 |
| 생성 명령 예시 | `ssh-keygen -t ed25519` | `ssh-keygen -t rsa` | `ssh-keygen -t ecdsa` |

## 단계별 방법

있는 키 확인, 생성, 공개 키 확인, 등록, 접속 시험 순서로 하면 덮어쓰기를 피해요.

### 기존 키와 디렉터리 확인

ssh 디렉터리와 기존 개인 키, 공개 키가 있는지 먼저 봐요. 없으면 디렉터리 권한을 소유자만 쓰게 맞춰요. 이미 쓰는 키 위에 같은 파일 이름으로 만들면 접속이 끊길 수 있어요.

### 키 쌍 만들기

종류와 파일 경로, 주석을 지정해 생성해요. 암호 프롬프트가 나오면 사람용 키는 암호를 거는 편이 좋아요. 생성 도구의 기본 알고리즘은 설치본 매뉴얼을 따라요.

### 공개 키 확인

공개 키 파일은 개인 키 이름에 공개 접미사가 붙은 쪽이에요. 내용을 서버에 등록하기 전에 한 줄인지 확인해요. 개인 키 내용을 채팅이나 티켓에 붙이지 마세요.

### 서버에 공개 키 등록

서버 계정 홈의 authorized_keys에 공개 키 한 줄을 추가해요. 파일 소유자와 권한이 계정과 맞지 않으면 서버가 무시해요. 다른 사람의 키를 지우지 않게 줄을 추가만 해요.

### 접속 테스트

명시적 키 경로로 한 번 접속해 보고, 실패하면 서버 로그의 인증 거절을 봐요. 성공하면 설정 파일에 호스트 별칭과 키 경로를 적어 다음부터 경로를 빼먹지 않게 해요. 에이전트를 쓸 거면 그 키만 등록해요.

## 상황별 선택

용도마다 키를 나누면 유출 때 폐기 범위가 줄어요.

### 개발 노트북에서 서버 접속

개인 키 하나에 암호를 걸고, 공개 키만 필요한 서버에 등록해요. 노트북을 바꾸면 새 키를 만들고 옛 공개 키는 서버에서 빼요. 개인 키를 클라우드 노트에 올리지 마세요.

### 배포 자동화와 CI

배포 전용 키를 따로 만들고, 그 키가 할 수 있는 명령을 제한할 수 있으면 제한해요. 비밀 저장소에 개인 키를 넣고 로그에 찍지 않아요. 사람용 키와 배포 키를 섞지 마세요.

### 여러 서버를 운영할 때

서버 그룹마다 키를 나눌지, 한 키에 공개 키만 배포할지를 정해요. 폐기할 때는 authorized_keys에서 해당 줄만 지워요. 설정 파일의 호스트별 키 경로가 섞이면 잘못된 키로 시도해요.

### Windows와 WSL

Windows OpenSSH와 WSL은 홈 디렉터리가 달라요. 어느 쪽 클라이언트를 쓰는지 정하고 그 홈에 키를 두세요. 권한을 Windows와 Linux 기준으로 각각 맞춰야 거절이 안 나요.

## 주의할 점

개인 키를 서버에 복사하지 마세요. 공개 키와 개인 키를 바꿔 등록하면 접속이 안 돼요. 권한이 넓으면 클라이언트와 서버 모두 키를 무시할 수 있어요. 공유 계정의 authorized_keys는 누가 줄을 넣었는지 남기기 어려워요. 유출이 의심되면 그 공개 키를 지우고 새로 만들어요.

## 자주 묻는 질문

등록 위치, 새로 만들기, 암호, 알고리즘, 권한이 반복돼요.

### ssh 키 생성 후 공개 키는 어디에 등록하나요?

서버 계정 홈의 authorized_keys에 공개 키 한 줄을 넣어요. Git 호스트를 쓰면 그 계정의 SSH 키 설정에 같은 공개 키를 등록해요. 개인 키는 어느 쪽에도 올리지 않아요.

### 기존 키가 있는데 새로 만들어도 되나요?

다른 파일 이름으로 만들면 기존 키는 유지돼요. 같은 경로로 만들면 덮어써서 기존 서버 접속이 끊길 수 있어요. 새 공개 키를 등록한 뒤 옛 키를 폐기하는 순서가 안전해요.

### 암호문은 꼭 설정해야 하나요?

사람용 키는 거는 편이 좋아요. 입력이 불가능한 자동화는 배포 전용 키와 비밀 저장, 가능하면 명령 제한을 같이 봐요. 암호가 없다고 공개 키 등록 방식이 달라지지는 않아요.

### Ed25519와 RSA 중 무엇을 고르면 되나요?

새 서버와 최신 OpenSSH면 ed25519를 먼저 검토해요. 상대가 그 알고리즘을 거부할 때만 RSA를 검토하고, 길이 정책은 그 장비 문서를 따라요. DSA는 신규에 쓰지 않아요.

### 권한 오류가 나면 어떻게 확인하나요?

개인 키 파일, ssh 디렉터리, 서버의 authorized_keys 소유자와 권한을 봐요. 그룹이나 다른 사용자가 쓸 수 있으면 무시되는 경우가 많아요. 서버 인증 로그의 문구가 클라이언트 거절인지 서버 거절인지 갈라 줘요.

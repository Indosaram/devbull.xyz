## 한눈에 보기

@pulumi/awsx는 클래식 프로바이더 위에 자주 쓰는 구성을 컴포넌트로 올린 라이브러리예요. 코드가 짧아지는 대신, 내부에서 여러 리소스가 생길 수 있어요. 그래서 업그레이드 전에 미리보기로 교체와 삭제를 봐야 해요. CLI, 언어 런타임, 클라우드 자격 증명이 없으면 패키지만으로는 배포가 안 돼요.

## @pulumi/awsx 패키지가 하는 일

네트워크, 로드밸런서, 컨테이너 서비스처럼 연결이 많은 구성을 한 컴포넌트로 선언하게 해 줘요. 컴포넌트 출력을 다음 컴포넌트에 넘기면 대상 그룹 연결 같은 반복을 줄일 수 있어요. 모든 AWS 리소스를 대체하지는 않아서, 세밀한 자원은 클래식 패키지가 필요해요. 옵션 이름은 설치한 버전의 레지스트리 문서를 따라요.

## 클래식 프로바이더와 비교

표는 추상화 수준, 코드 길이, 제어 범위를 나눈 거예요. awsx는 표준 웹 구성을 빨리 반복할 때 맞고, aws는 대역과 보안 그룹을 직접 설계할 때 맞아요. 한 프로그램에서 둘을 같이 쓸 수 있어요. 컴포넌트가 감춘 부분을 계속 열어야 하면 클래식 쪽이 읽기 쉬워요.

| 항목 | `@pulumi/aws` 단독 | `@pulumi/awsx` 함께 사용 |
| --- | --- | --- |
| 추상화 수준 | AWS 리소스 단위 | 여러 리소스를 묶은 컴포넌트 단위 |
| 코드 분량 | 상대적으로 많음 | 상대적으로 적음 |
| 세부 옵션 제어 | 폭이 넓음 | 컴포넌트가 노출한 범위 |
| 변경 영향 범위 | 리소스 단위로 좁게 관리 | 컴포넌트 단위로 함께 바뀔 수 있음 |
| 잘 맞는 상황 | 네트워크·보안을 직접 설계할 때 | 표준 구성을 빠르게 반복할 때 |

## 단계별 설치와 첫 배포

CLI와 프로젝트, 패키지, 코드, 미리보기 순서로 가면 실패 위치가 분명해요.

### 사전 준비

Pulumi CLI, Node, AWS 자격 증명을 준비해요. 상태 백엔드를 팀과 공유하지 않으면 나중 협업에서 스택이 갈라져요. 리전과 계정은 로컬 기본값에 맡기지 말고 스택 설정으로 드러내요.

### 프로젝트 만들기

언어를 TypeScript나 JavaScript로 두고 프로젝트를 만들면 진입점과 스택 파일이 생겨요. 이미 있는 Node 프로젝트라면 Pulumi 설정 파일만 추가해도 돼요. 스택 이름을 환경과 맞춰 두면 운영과 시험이 섞이지 않아요.

### 패키지 설치

npm으로 @pulumi/awsx를 설치해요. @pulumi/pulumi와 @pulumi/aws가 같이 잡히는 경우가 많으니, 잠금 파일에 올라간 조합을 확인해요. CI는 잠금 파일 기준 설치로 재현해요. 아래 명령은 설치 한 줄이에요.

```bash
npm install @pulumi/awsx
```

### 코드 작성

진입점에서 awsx 컴포넌트를 선언하고, 출력을 다음 컴포넌트에 넘기는 형태가 기본이에요. 아래 예시는 흐름만 보여주는 최소 형태라, 옵션 이름은 사용 중인 버전 문서를 확인해야 해요. 이미지 태그를 매번 달라지는 값으로 두면 배포마다 결과가 바뀌어요.

```typescript
import * as pulumi from "@pulumi/pulumi";
import * as awsx from "@pulumi/awsx";

const vpc = new awsx.ec2.Vpc("app-vpc", {
  numberOfAvailabilityZones: 2,
});

const listener = new awsx.lb.ApplicationListener("app-listener", {
  port: 80,
});

const service = new awsx.ecs.FargateService("app-service", {
  cluster: "app-cluster",
  taskDefinitionArgs: {
    containers: {
      app: {
        image: "nginx:latest",
        memory: 512,
        portMappings: [listener],
      },
    },
  },
});
```

### 미리보기와 배포

미리보기로 생성, 변경, 삭제를 사람이 읽은 뒤 업을 실행해요. 출력은 스택 출력으로 확인하고, 삭제는 별도 명령이에요. 운영 스택은 미리보기 없이 자동 승인하지 않는 편이 안전해요.

## 상황별 선택 기준

표준 웹 서비스를 빠르게 반복하면 awsx가 맞아요. 네트워크를 직접 설계하는 조직은 클래식 리소스 중심이 낫고, awsx는 신규 부분만 도입해요. 이미 aws로 쓴 스택을 한 번에 바꾸지 마세요. 컴포넌트 업그레이드가 내부 리소스 교체로 이어지면 미리보기에서 교체 표시를 먼저 봐요.

## 주의할 점

예제와 설치 버전이 다르면 임포트 경로에서 먼저 실패해요. 상태 파일은 팀 백엔드에 두고 잠금이 되게 해요. 최신 이미지 태그는 재현을 깨요. 삭제 보호는 컴포넌트가 대신 해 주지 않으니 스택 정책으로 챙겨요. 자격 증명을 코드에 넣지 마세요.

## 자주 묻는 질문

CLI와의 관계, 다른 도구 대체 여부, 혼용, 버전 업이 질문의 중심이에요.

### npm의 @pulumi/awsx와 Pulumi CLI는 무슨 관계인가요?

패키지는 프로그램 안의 라이브러리고, CLI는 미리보기와 배포를 실행하는 도구예요. 둘 다 있어야 실제 반영이 돼요. 패키지만 설치했다고 클라우드 자원이 생기지는 않아요.

### awsx를 쓰면 Terraform이나 CloudFormation을 대체할 수 있나요?

Pulumi 프로그램으로 같은 계열의 인프라를 선언할 수는 있어요. 기존 상태와 팀 절차를 자동으로 가져오지는 않아요. 이관은 자원 단위로 미리보기를 보고 결정해요.

### 기존 @pulumi/aws 코드와 함께 쓸 수 있나요?

한 프로그램에서 같이 쓸 수 있고, 리소스 참조도 주고받을 수 있어요. 같은 자원을 두 패키지가 동시에 소유하게 만들면 충돌해요. 소유 경계를 코드에 드러내요.

### 버전을 올릴 때 무엇을 확인해야 하나요?

잠금 파일과 레지스트리의 변경 안내를 보고, 미리보기에서 교체와 삭제가 있는지 봐요. 운영 스택은 시험 스택에서 먼저 올려요. CLI와 패키지 조합도 같이 맞춰요.

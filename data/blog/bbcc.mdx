bbcc는 하나의 표준으로 뜻이 고정된 약어가 아니에요. 배포 스크립트나 운영 문서에서 이 표기를 만나면 뜻을 추측하기 전에, 어느 계층의 이름으로 쓰였는지부터 봐요. 네트워크 포트 옆인지, 빌드 산출물인지, 환경 변수인지에 따라 후보가 갈려요. 외부 등록 목록과 사내 용어집을 차례로 대조한 뒤에야 변수 이름이나 파이프라인 단계로 굳히는 편이 안전해요.

## 한눈에 보기

- bbcc는 단일 표준 약어가 아니므로, 뜻을 추측하기 전에 등장 위치를 먼저 봐요.
- 네트워크, 빌드, 애플리케이션 중 어느 계층에 붙는지 나누면 후보가 크게 줄어요.
- 외부 표준 문서와 사내 저장소를 차례로 대조한 뒤, 확정한 뜻을 용어집에 남겨요.
- 확정 전에는 변수 이름이나 파이프라인 단계 이름으로 굳히지 않아요.

## bbcc의 뜻이 하나로 정해지지 않는 이유

네 글자 약어는 머리글자를 조합하기 쉬워요. 빌드, 브랜치, 캐시, 설정처럼 배포에서 자주 쓰는 단어가 비슷한 머리글자를 가지면, 같은 철자에 다른 뜻이 붙어요. 시간이 지나면 원래 조합을 아는 사람만 남고 문서에는 결과만 남아요.

대소문자 관례도 혼동을 키워요. 어떤 팀은 대문자를 시스템 이름에, 소문자를 변수에 쓰는데, 그 규칙이 문서에 없으면 같은 표기가 다른 대상처럼 보여요.

축약은 대개 대화에서 먼저 생겨요. 회의에서 줄여 부르던 말이 이슈 제목이 되고, 커밋 메시지와 로그로 옮겨 가요. 풀네임이 한 번도 안 적히면 나중에 되짚을 근거가 없어요.

## 비교 표: 확인 지점별로 보는 신호

| 확인 지점 | 무엇을 보는가 | 판단에 쓰는 신호 |
| --- | --- | --- |
| 최초 등장 위치 | 이슈, 커밋 메시지, 장애 기록 | 누가 어떤 상황에서 처음 적었는지 |
| 붙는 계층 | 포트, 아티팩트, 환경 변수 | 어느 계층의 이름처럼 쓰이는지 |
| 표기 관례 | 대소문자, 하이픈, 밑줄 | 사내 명명 규칙과 맞는지 |
| 외부 표준 여부 | 표준 문서, 등록 목록 | 등록된 이름인지 아닌지 |
| 사내 정의 | 용어집, 설계 결정 기록, 안내 문서 | 뜻을 밝힌 문장이 있는지 |

## 단계별로 뜻을 확정하는 방법

등장 지점, 계층, 외부 문서, 사내 정의, 기록 순서로 가면 같은 조사를 반복하지 않아요.

### 첫 단계: 최초 등장 지점을 찾습니다

저장소 전체에서 표기를 검색하고, 가장 오래된 등장 지점을 봐요. 이슈와 커밋 메시지까지 같이 보면, 코드보다 대화 기록에 풀네임이 남아 있는 경우가 많아요. 대소문자를 구분하는 검색과 구분하지 않는 검색을 각각 돌려요.

### 둘째 단계: 붙는 계층을 나눕니다

포트 번호 옆인지, 빌드 산출물 이름인지, 환경 변수 이름인지 나눠요. 계층이 정해지면 볼 문서도 정해져요. 네트워크면 등록 목록과 표준 문서, 빌드면 사내 파이프라인 정의를 먼저 봐요. 이 단계에서 후보의 상당수가 걸러져요.

### 셋째 단계: 공식 문서와 대조합니다

외부 표준일 가능성이 있으면 등록 목록과 표준 문서를 읽어요. 표준 문서는 요구 강도에 따라 표현을 나누므로, 인용할 때 그 구분을 같이 적으면 오해가 줄어요. 등록 목록에 없으면 사내 정의일 가능성이 커요.

### 넷째 단계: 저장소 안의 정의를 확인합니다

용어집, 설계 결정 기록, 배포 안내를 차례로 봐요. 정의가 없으면 그 이름을 만든 사람이나 마지막으로 고친 사람의 기록을 봐요. 커밋 메시지에 배경이 남아 있는 경우가 많아요. 이때 본 내용은 출처와 함께 적어야 다음 사람이 처음부터 다시 찾지 않아요.

### 다섯째 단계: 확정 결과를 기록합니다

확정한 뜻, 확정한 날짜, 근거 링크를 한곳에 모아요. 같은 표기가 다른 뜻으로도 쓰이면 그 목록도 같이 적어요. 기록은 짧아도 되지만, 근거 링크가 빠지면 다음 사람이 다시 처음부터 찾아요.

## 상황별 선택 기준

**외부 표준 이름일 가능성이 높을 때**는 등록 목록과 표준 문서를 가장 먼저 봐요. 표기법과 대소문자까지 문서에 적힌 그대로 따르는 편이 맞아요.

**사내 서비스 이름일 때**는 저장소 안내와 설계 결정 기록을 우선해요. 외부 자료에는 근거가 없으니 검색에 오래 쓰지 않아요.

**로그에서만 보이는 축약일 때**는 로그 형식 정의서를 봐요. 정의서가 없으면 로그를 만드는 코드의 출력 부분을 보는 것이 가장 빨라요.

**오타나 음차일 가능성이 있을 때**는 검색 범위를 넓혀요. 비슷한 철자의 다른 표기를 같이 검색하면 원래 의도가 드러나는 경우가 있어요.

## 주의할 점

확정되지 않은 이름을 변수나 디렉터리 이름으로 먼저 굳히지 않아요. 배포 파이프라인에 들어간 이름은 되돌리는 비용이 커요.

대소문자를 섞어 쓰는 것도 피해요. 파일 시스템에 따라 대소문자 구분이 달라서, 로컬에서 되던 이름이 배포 환경에서 어긋날 수 있어요.

환경 변수 이름을 정할 때는 이미 쓰이는 이름과 겹치지 않는지 먼저 봐요. 겹친 이름은 조용히 덮이고, 결과는 장애로 나타나요.

근거 문서를 같이 적을 수 없는 수치, 버전, 가격은 단정하지 않아요. 일반 절차와 개념만 적는 편이 안전해요.

로그에 이름을 남길 때는 개인정보나 인증 정보가 같이 나오지 않게 마스킹 규칙을 봐요.

## 자주 묻는 질문

### bbcc가 사내 약어인지 표준 약어인지 어떻게 구분하나요?

등록 목록과 표준 문서를 먼저 보고, 그다음 사내 저장소를 봐요. 외부 문서에 같은 철자가 없고 사내 문서에만 있으면 사내 약어로 보는 편이 맞아요. 두 곳 모두에 있는데 뜻이 다르면 별도 항목으로 나눠 기록해요.

### 배포 스크립트에 bbcc라는 변수가 이미 있는데 이름을 바꿔야 하나요?

뜻이 확정되고 현재 이름이 오해를 부르면 바꾸는 편이 좋아요. 바꾸기 전에 참조하는 곳을 모두 찾고, 배포를 끊지 않는 교체 순서를 정해요. 뜻이 아직이면 이름을 바꾸기보다 뜻을 먼저 확정해요.

### bbcc가 로그에만 보이고 문서에는 없을 때는 어떻게 하나요?

로그를 출력하는 코드를 먼저 봐요. 출력 형식을 만드는 부분에 출처가 주석으로 남아 있는 경우가 많아요. 코드에도 없으면 로그 형식 정의서나 관측 도구 설정을 봐요.

### 팀에 용어집이 없으면 무엇부터 만들어야 하나요?

지금 문제가 된 표기 하나부터 시작해요. 표기, 확정된 뜻, 근거 링크, 확정한 날짜만 있으면 충분해요. 항목이 늘면 그때 검색과 색인을 붙이면 되고, 처음부터 큰 체계를 만들 필요는 없어요.

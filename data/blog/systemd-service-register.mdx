systemd 서비스 등록은 유닛 파일로 실행 파일, 계정, 재시작, 부팅 시 시작을 선언하는 일이에요. 패키지가 만들어 준 유닛이 없으면 /etc/systemd/system에 직접 두고, 바꾼 뒤에는 데몬 리로드가 필요해요. 재시작과 리로드는 유닛 정의를 다시 읽는 일과 프로세스를 다시 띄우는 일이 달라요. 아래는 섹션 구조와 등록 순서예요.

![systemd 서비스 등록과 배포: 유닛 파일부터 재시작까지 소제목 카드. 한눈에 보기, 유닛 파일의 섹션 구조, 배포 방식 비교, 단계별로 서비스 등록하기](/static/images/systemd-service-register/diagram.webp)

## 한눈에 보기

유닛 파일은 Unit, Service, Install 섹션으로 나뉘어요. ExecStart는 셸을 거치지 않아서 파이프를 그대로 쓸 수 없어요. enable은 부팅 시 시작이고, start는 지금 띄우는 일이에요. 로그는 저널에서 보는 구성을 먼저 두고 파일 로그는 필요할 때만 더해요.

## 유닛 파일의 섹션 구조

표는 각 섹션의 역할과 자주 쓰는 지시자, 놓치기 쉬운 점을 담아요. After는 순서만 정하고 대상의 존재를 보장하지 않으니, 꼭 필요하면 Requires를 같이 봐요. Install이 없으면 enable이 부팅 연결을 못 만들어요.

| 섹션 | 하는 일 | 자주 쓰는 지시자 | 놓치기 쉬운 점 |
| --- | --- | --- | --- |
| `[Unit]` | 유닛 설명과 다른 유닛과의 순서·의존 관계 정의 | `Description`, `After`, `Wants`, `Requires` | `After`는 순서만 정할 뿐 상대 유닛의 존재를 보장하지 않으므로 필요하면 `Requires`를 함께 씁니다 |
| `[Service]` | 프로세스를 어떻게 실행하고 감시할지 정의 | `Type`, `ExecStart`, `User`, `Restart`, `EnvironmentFile` | `ExecStart`는 셸을 거치지 않고 실행되므로 파이프나 리다이렉션을 그대로 쓸 수 없습니다 |
| `[Install]` | `enable` 할 때 어느 타깃에 연결할지 정의 | `WantedBy` | 이 섹션이 없으면 자동 시작 등록이 되지 않아 재부팅 후 서비스가 뜨지 않습니다 |

## 배포 방식 비교

표는 systemd 유닛, 컨테이너 오케스트레이션, 별도 프로세스 매니저를 비교해요. 서버 한 대에 바이너리를 두면 유닛이 단순하고, 여러 노드 롤링은 오케스트레이션이 맞아요. 프로세스 매니저만 쓰면 부팅 연동과 로그를 따로 붙여야 해요.

| 방식 | 적합한 경우 | 장점 | 고려할 점 |
| --- | --- | --- | --- |
| systemd 유닛 | 단일 서버에 바이너리를 직접 두고 운영 | 추가 도구 없이 부팅 시 시작과 비정상 종료 복구를 관리 | 무중단 전환은 배포 스크립트와 리버스 프록시 쪽에서 직접 설계해야 함 |
| 컨테이너 오케스트레이션 | 여러 노드에 걸친 확장과 롤링 배포 | 선언형 배포와 상태 점검이 기본 제공 | 클러스터 자체의 운영 비용과 학습 부담이 큼 |
| 별도 프로세스 매니저 | 소규모 구성이나 임시 운영 | 설정이 단순하고 도입이 빠름 | 부팅 연동과 로그 수집을 따로 붙여야 함 |

## 단계별로 서비스 등록하기

실행 파일, 계정, 환경 파일, 유닛, 리로드, 로그 순서로 등록하면 권한 문제가 빨리 보여요.

### 1. 실행 파일과 작업 디렉터리 정리

절대 경로의 실행 파일과 작업 디렉터리를 정해요. 상대 경로는 유닛의 작업 디렉터리에 따라 달라져요. 배포할 때마다 경로가 바뀌면 유닛도 같이 갱신해야 해요.

### 2. 전용 실행 계정 만들기

루트로 오래 돌리지 말고 전용 계정을 만들어요. 그 계정이 실행 파일과 데이터 디렉터리를 읽을 수 있는지 확인해요. 홈이 없는 계정은 환경 파일 경로를 절대 경로로 적어요.

### 3. 환경 변수 파일 분리

비밀은 유닛 파일에 적지 않고 EnvironmentFile로 빼요. 파일 소유자는 루트, 읽기는 서비스 계정만 되게 좁혀요. 값에 따옴표와 공백이 있으면 파싱이 비어 보일 수 있어요.

### 4. 유닛 파일 작성

Type, ExecStart, User, Restart, WantedBy를 적어요. ExecStart는 실행 파일 절대 경로로 시작하고 셸 문법을 넣지 않아요. 재시작 정책은 실패와 정상 종료를 구분해서 정해요.

```
[Unit]
Description=Backend API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=app
Group=app
WorkingDirectory=/srv/app
EnvironmentFile=/etc/app/app.env
ExecStart=/srv/app/bin/api
Restart=on-failure
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

### 5. 데몬 리로드와 자동 시작 등록

유닛을 추가하거나 고친 뒤 daemon-reload를 해요. enable로 부팅 연결을 만들고 start로 지금 띄워요. 리로드 없이 재시작만 하면 옛 정의가 남을 수 있어요.

### 6. 상태와 로그 확인

status로 활성과 최근 종료 코드를 보고, 저널로 시작 오류를 봐요. 주소에 바인딩됐는지는 앱 로그와 포트를 같이 봐요. 실패가 반복되면 재시작 간격과 시작 명령을 먼저 고쳐요.

## 상황별 선택

단일 서버의 장기 실행 프로세스는 유닛이 맞아요. 무중단 교체가 필요하면 리버스 프록시와 배포 스크립트를 같이 설계해요. 짧은 배치는 타이머 유닛을 검토해요. 컨테이너로 이미 운영하면 호스트 유닛은 컨테이너 런타임만 맡게 해요.

## 주의할 점

벤더 유닛을 직접 고치지 말고 drop-in을 써요. 환경 파일 경로가 틀리면 값이 빈 채로 시작해요. Restart를 무조건 켜면 설정 오류가 재시작 루프가 돼요. 로그를 파일로만 남기면 저널과 권한이 이중으로 필요해요.

## 자주 묻는 질문

restart와 reload, 옛 설정, 빈 환경 변수, 재시작 반복, 파일 로그가 반복돼요.

### systemctl restart와 daemon-reload는 각각 언제 필요한가요?

유닛 파일을 추가하거나 고치면 daemon-reload로 정의를 다시 읽어요. 프로세스를 새 명령으로 다시 띄울 때는 restart예요. 정의만 고치고 reload를 빼먹으면 옛 유닛으로 재시작해요.

### 유닛 파일을 고쳤는데 이전 설정대로 동작합니다.

daemon-reload를 안 했거나, 다른 경로의 유닛이 우선일 수 있어요. cat으로 병합 결과를 봐요. drop-in과 본파일이 다른 명령을 가지고 있지 않은지 확인해요.

### 환경 변수 파일을 만들었는데 값이 비어 있습니다.

경로, 권한, 줄 형식을 봐요. 따옴표나 공백 때문에 키가 다르게 읽힐 수 있어요. 유닛의 EnvironmentFile 경로가 그 파일과 같은지 확인해요.

### 서비스가 계속 재시작을 반복합니다.

시작 즉시 죽는 설정 오류에 Restart가 붙어 있는 경우가 많아요. 저널의 첫 오류를 고친 뒤 재시작 정책을 다시 봐요. 포트 충돌과 없는 파일도 같은 증상으로 보여요.

### 로그를 파일로 따로 남기고 싶습니다.

기본은 저널이에요. 앱이 파일에 쓰게 하면 그 디렉터리 권한과 회전을 따로 관리해야 해요. 표준 출력을 저널에 두고 수집기가 가져가게 하는 편이 유닛은 단순해요.

nginx 설정 확인은 어느 파일을 읽고 있는지, 문법이 통과하는지, 요청이 의도한 블록으로 가는지를 순서대로 보는 일이에요. 문법 성공만으로 라우팅이 맞다고 보면 안 돼요. 반영 전에는 검사, 반영 후에는 오류 로그와 실제 요청을 봐요. 아래는 위치, include, 프록시, 리로드까지 점검 순서예요.

## 한눈에 보기

실행 중인 nginx가 읽는 설정 경로와, 그 파일이 include하는 디렉터리를 먼저 맞춰요. 그다음 문법 검사로 오탈자와 없는 파일 참조를 걸러요. server와 location이 요청을 어떻게 나누는지, 프록시 대상이 살아 있는지를 이어서 봐요. 리로드는 문법 통과 뒤에만 하고, 오류 로그로 반영 여부를 확인해요.

## 점검 순서 비교 표

표는 증상별로 먼저 볼 위치와 명령을 나눈 거예요. 기동 실패는 문법과 파일 경로, 잘못된 사이트로 가는 요청은 server_name과 location, 업스트림 오류는 프록시 대상과 로그예요. 순서를 바꾸면 멀쩡한 파일을 고치게 돼요. 컨테이너면 호스트 경로가 아니라 컨테이너 안 경로를 봐요.

| 순서 | 확인 대상 | 사용하는 수단 | 건너뛰었을 때 생기는 일 |
| --- | --- | --- | --- |
| 1 | 설정 파일 경로 | `nginx -V` 출력의 설정 경로 | 다른 파일을 고치고 반영됐다고 착각해요 |
| 2 | include 구조 | `nginx -T` | include 순서가 어긋나 중복 정의가 생겨요 |
| 3 | 문법과 참조 파일 | `nginx -t` | reload 단계에서 실패하고 이전 설정으로 남아요 |
| 4 | server·location·listen | 최종 설정과 실제 요청 | 요청이 의도하지 않은 블록으로 흘러가요 |
| 5 | 프록시·업스트림 | upstream, proxy 지시어 | 게이트웨이 오류나 응답 지연으로 보여요 |
| 6 | 반영과 로그 | reload, error.log, access.log | 반영 여부를 확인하지 못한 채 넘어가요 |

## 단계별 확인 방법

파일 위치, 문법, 블록, 프록시, 반영 순서로 가면 원인 범위가 줄어요.

### 설정 파일 위치와 include 구조를 확인해요

마스터 프로세스가 연 설정 경로를 확인하고, include가 가리키는 디렉터리까지 따라가요. include는 적힌 순서대로 읽고, 디렉터리 와일드카드는 파일 이름 순으로 읽히는 경우가 많아요. 심볼릭 링크가 끊기면 사이트 파일이 빠져요. 배포 도구가 다음 배포에서 손본 파일을 덮는지도 봐요. 아래 예시는 include가 여러 디렉터리를 모으는 형태예요.

```
http {
    include /etc/nginx/mime.types;
    include /etc/nginx/conf.d/*.conf;
    include /etc/nginx/sites-enabled/*;
}
```

### `nginx -t`로 문법을 검사해요

문법 검사는 반영 전에 해요. 설정이 가리키는 인증서 파일이 없는 것도 이 단계에서 걸리는 경우가 있어요. 성공이어도 지금 운영 중인 설정 파일을 검사한 것인지 경로를 확인해요. 다른 파일을 검사하려면 설정 경로 옵션을 써요. 검사가 실패하면 반영 단계가 실행되지 않게 스크립트를 나눠요.

### server와 location 블록, listen 지시어를 봐요

listen 포트와 실제로 열린 포트가 같은지 봐요. 같은 포트를 여러 server가 쓰면 server_name으로 갈라지고, 기본 서버가 의도한 블록인지도 봐요. location은 더 구체적인 경로와 정규식이 섞이면 선택이 달라져요. alias와 root, try_files의 끝 슬래시도 경로가 어긋나는 지점이에요.

### 프록시와 업스트림 설정을 확인해요

proxy_pass 대상이 기동 중인지, 업스트림 이름이 정의와 같은지 봐요. 헤더를 넘기지 않으면 백엔드가 잘못된 호스트로 응답할 수 있어요. 시간 제한이 너무 짧으면 느린 업스트림이 오류로 보여요. 변경 후 업스트림 로그와 nginx 오류 로그를 같이 봐요.

### reload로 반영하고 로그를 확인해요

문법 통과 뒤에 리로드해요. 리로드는 기존 연결을 유지한 채 설정을 바꾸는 쪽이고, 재시작은 프로세스를 새로 띄워요. 반영 뒤 오류 로그에 설정 읽기 실패가 없는지, 테스트 요청이 기대한 server로 가는지 확인해요. 안 바뀌면 include되지 않은 파일을 고친 경우가 많아요.

## 점검에 자주 쓰는 명령

설정 경로 확인, 문법 검사, 리로드, 오류 로그 보기를 한 세트로 외워 두면 돼요. 프로세스에 어떤 설정 파일이 열려 있는지도 같이 보면 다른 파일을 고치는 실수를 막아요. 컨테이너면 그 안에서 같은 순서를 실행해요. 명령의 정확한 플래그는 설치한 nginx 문서를 따라요.

| 목적 | 명령 | 확인 포인트 |
| --- | --- | --- |
| 설정 경로와 빌드 옵션 확인 | `nginx -V` | 설정 경로, 로드된 모듈 |
| 최종 설정 출력 | `nginx -T` | include 순서, 중복 정의 |
| 문법 검사 | `nginx -t` | 오류 파일과 줄 번호 |
| 특정 파일만 검사 | `nginx -t -c 경로` | 단독 검사 시 의존 관계 |
| 설정 반영 | `nginx -s reload` | 실패 여부와 로그 |
| 프로세스 상태 확인 | `ps` 또는 서비스 관리 도구 | 워커 정상 기동 여부 |

## 상황별 선택

문법 오류면 리로드하지 말고 검사 메시지의 파일과 줄을 고쳐요. 잘못된 사이트로 가면 server_name과 기본 서버를 봐요. 업스트림 오류면 백엔드 생존과 프록시 주소를 봐요. 설정은 맞는데 반영이 안 되면 include와 리로드 대상을 봐요. 바이너리를 바꿨으면 리로드가 아니라 업그레이드 절차를 문서에서 봐요.

## 주의할 점

검사 성공과 의도한 라우팅은 달라요. 리로드 실패를 재시작으로 반복하면 중단 시간이 늘어요. 운영 파일과 저장소 파일이 다르면 다음 배포가 되돌려요. 로그 경로를 바꾸면 예전 파일을 보고 있을 수 있어요. 권한 없는 인증서 경로는 문법 단계에서 잡혀요.

## 자주 묻는 질문

검사가 서비스에 영향을 주는지, 리로드가 안 먹는 이유, 파일 하나만 검사하는 방법, 재시작과의 차이를 자주 물어요.

### nginx -t는 서비스에 영향을 주나요?

문법과 참조 파일을 검사하는 단계라, 그 자체로 트래픽을 끊는 반영은 아니에요. 다만 잘못된 바이너리나 경로로 실행하면 기대한 설정이 아닐 수 있어요. 반영은 검사 통과 뒤 리로드로 따로 해요.

### 설정을 고쳤는데 reload해도 반영되지 않아요.

include되지 않은 파일을 고쳤거나, 다른 경로의 nginx를 리로드한 경우가 많아요. 실행 중인 프로세스가 연 설정과 방금 고친 파일을 비교해요. 문법 검사도 같은 경로로 했는지 봐요.

### include된 파일 하나만 따로 검사할 수 있나요?

조각 파일만 검사하면 상위 http 블록 문맥이 빠져 실패하거나, 반대로 놓치는 지시어가 있어요. 전체 설정을 검사하는 쪽이 맞아요. 문제 파일은 검사 메시지의 경로로 찾아요.

### reload와 restart는 어떻게 다른가요?

리로드는 설정을 다시 읽고 기존 연결을 이어 가는 쪽이에요. 재시작은 프로세스를 내렸다가 다시 띄워요. 워커 수처럼 프로세스 구성이 바뀌는 항목은 리로드만으로 안 될 수 있으니 문서를 봐요.

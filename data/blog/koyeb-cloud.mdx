koyeb cloud는 서버를 직접 만들지 않고 컨테이너를 배포하고 운영하는 서버리스 플랫폼입니다. Git 저장소나 컨테이너 이미지를 연결하면 빌드부터 배포, 헬스 체크, 도메인 연결까지 플랫폼이 대신 처리합니다. 이 글은 서버 운영과 배포를 맡고 있는 백엔드 개발자가 Koyeb Cloud를 처음 검토할 때 확인해야 할 구조와 절차, 그리고 실제로 부딪히기 쉬운 지점을 정리합니다.

## 한눈에 보기

Koyeb Cloud를 이해할 때 가장 중요한 개념은 "애플리케이션은 묶음이고, 실제로 트래픽을 받는 것은 서비스"라는 구분입니다. 애플리케이션은 배포 단위를 묶는 논리적 이름에 가깝고, 그 아래에 만들어지는 서비스가 컨테이너 실행과 라우팅을 담당합니다. 그래서 콘솔이나 CLI에서 무언가를 만들 때도 앱을 먼저 만들고 서비스를 정의하는 순서가 자연스럽습니다.

- 애플리케이션은 여러 서비스를 담는 상위 단위이며, 환경별로 나누어 관리하기에 적합합니다.
- 서비스는 Git 저장소, 사전 빌드된 컨테이너 이미지, 또는 CLI를 통한 배포로 만들 수 있습니다.
- 빌드는 빌드팩 방식과 Dockerfile 방식을 모두 지원하므로, 이미 검증된 이미지가 있다면 그대로 올릴 수 있습니다.
- 헬스 체크, 오토스케일링, 유휴 시 인스턴스를 내리는 설정 같은 운영 기능이 콘솔과 CLI 양쪽에서 제공됩니다.
- 배포 후에는 로그와 메트릭을 플랫폼 화면에서 확인하고, 커스텀 도메인과 인증서는 플랫폼이 관리합니다.

정리하면 Koyeb Cloud는 "컨테이너는 그대로 쓰되, 그 컨테이너를 굴리는 인프라와 배포 파이프라인은 위임하는" 모델입니다. 쿠버네티스 클러스터를 직접 운영하지 않으면서도 컨테이너 기반 배포의 이점을 가져가고 싶은 팀에 잘 맞습니다.

## Koyeb Cloud의 동작 구조

배포 요청이 들어오면 플랫폼은 크게 세 단계를 거칩니다. 먼저 소스를 가져와 빌드하고 컨테이너 이미지를 만듭니다. 다음으로 그 이미지를 선택한 리전의 인스턴스로 실행하고, 마지막으로 외부 트래픽을 엣지를 통해 해당 인스턴스로 라우팅합니다. 이 흐름을 이해하면 "왜 빌드는 성공했는데 서비스가 죽어 있는지" 같은 문제를 훨씬 빠르게 좁힐 수 있습니다.

첫 번째 단계인 빌드에서는 저장소에 Dockerfile이 있으면 그 정의를 따르고, 없으면 빌드팩이 언어와 프레임워크를 추론해 빌드합니다. 빌드 결과물은 이미지로 고정되므로, 같은 커밋을 다시 배포하면 같은 결과가 나오는 것이 일반적입니다. 다만 빌드팩이 감지하는 런타임 버전은 프로젝트 설정 파일에 명시해 두는 편이 예측 가능합니다.

두 번째 단계인 실행에서는 서비스 정의에 적어 둔 포트, 환경 변수, 헬스 체크 설정이 그대로 적용됩니다. 인스턴스는 선택한 리전에 배치되고, 오토스케일링을 켜 두면 트래픽이나 부하 지표에 따라 인스턴스 수가 조정됩니다. 이때 애플리케이션은 상태를 로컬 디스크에 두지 않는 무상태 설계여야 인스턴스가 늘고 줄어도 문제가 생기지 않습니다.

세 번째 단계인 라우팅에서는 공개 엔드포인트가 열리고, 커스텀 도메인을 연결하면 인증서 발급과 갱신을 플랫폼이 처리합니다. 즉 애플리케이션 코드 입장에서는 "지정된 포트로 요청을 받는다"는 사실만 지키면 되고, 그 앞단의 확장과 인증서 관리는 플랫폼의 몫이 됩니다.

## 배포 방식 비교

어떤 방식으로 올릴지 정하는 것이 첫 번째 결정입니다. 아래 표는 공식 문서에서 확인한 배포 경로를 운영 관점에서 비교한 것입니다.

| 배포 방식 | 준비물 | 잘 맞는 상황 | 확인할 점 |
| --- | --- | --- | --- |
| Git 저장소 연결 | 빌드 가능한 저장소, 런타임 버전 명시 | 코드 변경을 자주 배포하는 일반적인 API 서버 | 빌드팩이 언어 버전을 제대로 감지하는지 |
| Dockerfile 빌드 | Dockerfile, 빌드 컨텍스트 | 런타임과 시스템 패키지를 직접 제어해야 하는 서비스 | 멀티 스테이지 빌드로 이미지 크기를 줄였는지 |
| 사전 빌드 이미지 | 레지스트리에 푸시된 이미지 | CI에서 이미 검증한 아티팩트를 그대로 배포할 때 | 태그를 커밋 해시 등으로 고정했는지 |
| CLI 배포 | koyeb CLI, 인증 토큰 | 스크립트나 자동화 파이프라인에 배포를 끼워 넣을 때 | 토큰 권한 범위를 최소화했는지 |

Git 연결 방식은 진입 장벽이 가장 낮습니다. 저장소를 연결하고 빌드 설정과 실행 명령을 지정하면 이후에는 브랜치에 푸시하는 것만으로 배포가 이어집니다. 반면 시스템 라이브러리나 특정 런타임 패치가 필요하다면 Dockerfile을 두는 쪽이 결과를 예측하기 쉽습니다.

사전 빌드 이미지 방식은 CI와 배포의 역할을 분리하고 싶을 때 유용합니다. 빌드와 테스트를 CI에서 끝내고, 통과한 이미지만 플랫폼에 올리면 배포 시점의 변수를 줄일 수 있습니다. CLI 방식은 콘솔에서 손으로 하던 일을 스크립트로 옮기는 용도로 적합하며, 앱과 서비스를 선언적으로 정의해 두고 반복 실행하는 형태로 발전시키기 좋습니다.

## 단계별 배포 절차

1. 실행 조건을 먼저 정리합니다. 애플리케이션이 어떤 포트로 요청을 받는지, 헬스 체크에 쓸 경로는 무엇인지, 어떤 환경 변수와 시크릿이 필요한지를 문서로 적어 둡니다. 이 단계에서 빠진 값은 배포 후 장애로 돌아오기 때문에 가장 중요합니다.
2. 저장소나 이미지를 준비합니다. Git을 쓸 경우 빌드에 필요한 파일이 모두 커밋되어 있는지 확인하고, 이미지를 쓸 경우 레지스트리에 푸시한 뒤 태그를 고정합니다.
3. 애플리케이션을 만들고 그 아래에 서비스를 정의합니다. 콘솔에서 진행하든 CLI로 진행하든 순서는 같습니다. 서비스 정의에는 소스 위치, 빌드 방식, 실행 명령, 포트, 환경 변수, 헬스 체크가 포함됩니다.
4. 리전과 인스턴스 규격을 고릅니다. 사용자와 가까운 리전을 고르면 지연이 줄어들고, 인스턴스 규격은 메모리 사용량과 동시 처리량을 기준으로 여유 있게 잡습니다.
5. 첫 배포를 실행하고 로그를 확인합니다. 빌드 로그와 런타임 로그를 나누어 보면서, 빌드 실패인지 실행 실패인지 구분하는 것이 핵심입니다.
6. 헬스 체크가 정상 응답을 돌려주는지 확인한 뒤 커스텀 도메인을 연결합니다. 인증서 발급까지 끝나면 외부에서 접근 가능한 상태가 됩니다.
7. 이후 배포를 자동화합니다. Git 연동을 켜 두거나, CI 마지막 단계에서 CLI를 호출하는 방식으로 정리하면 배포 절차가 사람 손을 떠나게 됩니다.

각 단계에서 공통적으로 중요한 것은 "실패했을 때 어디를 볼지"를 미리 정해 두는 것입니다. 빌드 단계의 실패는 대부분 의존성과 런타임 버전 문제이고, 실행 단계의 실패는 대부분 포트 바인딩과 환경 변수 누락, 헬스 체크 경로 불일치에서 나옵니다.

## 상황별 선택 기준

Koyeb Cloud가 잘 맞는 경우는 대체로 다음과 같습니다. 사이드 프로젝트나 초기 서비스처럼 인프라에 쓸 여력은 적지만 컨테이너 배포는 유지하고 싶은 경우, 트래픽 변동이 커서 유휴 시간에 인스턴스를 내리는 이점을 보고 싶은 경우, 그리고 이미 Dockerfile로 빌드 가능한 자산이 있어서 플랫폼만 갈아타면 되는 경우입니다.

반대로 맞지 않는 경우도 분명합니다. 커널 파라미터 조정이나 특수 네트워크 구성처럼 호스트 수준 제어가 필요하다면 관리형 플랫폼보다 직접 운영하는 편이 낫습니다. 대용량 파일을 로컬 디스크에 계속 쌓는 구조라면 오브젝트 스토리지나 별도 스토리지로 분리하는 설계가 선행되어야 합니다. 상태를 가진 데이터베이스를 같은 서비스 안에 두는 구성도 권장되지 않으므로, 관리형 데이터베이스나 외부 저장소를 함께 검토해야 합니다.

운영 인력이 이미 쿠버네티스에 익숙하고 클러스터를 보유하고 있다면, 굳이 플랫폼을 추가로 도입할 이유가 줄어듭니다. 반대로 배포 파이프라인과 인증서 관리에 쓰는 시간을 줄이는 것이 목표라면 Koyeb Cloud 같은 추상화가 실질적인 이득이 됩니다.

## 주의할 점

가장 흔한 실수는 로컬 디스크에 상태를 두는 것입니다. 인스턴스는 언제든 교체될 수 있으므로 업로드 파일, 세션, 캐시를 컨테이너 내부 경로에 저장하면 재배포 시점에 사라집니다. 세션은 외부 저장소로, 파일은 오브젝트 스토리지로 옮기는 것이 기본입니다.

포트 바인딩도 자주 걸리는 지점입니다. 애플리케이션이 루프백 주소에만 바인딩하면 외부에서 접근할 수 없으므로, 모든 인터페이스에 바인딩하고 플랫폼이 전달하는 포트 값을 읽어 쓰도록 설정해야 합니다. 헬스 체크 경로는 인증이 필요 없는 가벼운 엔드포인트로 두는 편이 안전합니다.

유휴 시 인스턴스를 내리는 설정을 켜면 콜드 스타트 지연이 생깁니다. 응답 속도에 민감한 API라면 최소 실행 인스턴스를 유지하는 쪽을 검토하고, 배치 작업이나 내부 도구처럼 지연이 덜 중요한 서비스에만 유휴 중지를 적용하는 편이 좋습니다.

비용은 실행 중인 인스턴스와 사용한 자원을 기준으로 계산되는 구조이므로, 요금 체계는 배포 전에 공식 가격 페이지에서 직접 확인해야 합니다. 무료 사용 범위와 인스턴스 규격 정책은 시점에 따라 달라질 수 있으므로, 오래된 블로그의 숫자를 기준으로 견적을 내는 것은 피해야 합니다. 마지막으로 환경 변수와 시크릿은 분리해 관리하고, 로그에 값이 찍히지 않도록 마스킹 처리를 확인합니다.

## 자주 묻는 질문

### Koyeb Cloud는 무료로 시작할 수 있나요?

공식 사이트의 가격 안내에서 무료 사용 범위와 인스턴스별 과금 기준을 확인할 수 있습니다. 무료 범위와 정책은 시점에 따라 조정될 수 있으므로, 배포 전에 현재 조건을 직접 확인하는 편이 안전합니다.

### Dockerfile이 없어도 배포할 수 있나요?

네, 빌드팩 방식으로 언어와 프레임워크를 감지해 빌드할 수 있습니다. 다만 시스템 패키지 설치나 특수한 런타임 설정이 필요하다면 Dockerfile을 두는 쪽이 결과를 예측하기 쉽습니다.

### 유휴 시 인스턴스를 내리는 설정은 어떤 서비스에 적합한가요?

트래픽이 간헐적인 내부 도구나 배치성 API에 적합합니다. 외부 사용자가 항상 응답 속도를 기대하는 서비스라면 콜드 스타트 지연이 사용자 경험을 해칠 수 있으므로 최소 인스턴스를 유지하는 구성을 검토해야 합니다.

### 기존 Docker Compose 구성을 그대로 옮길 수 있나요?

Compose 파일을 그대로 인식해 실행하는 방식은 아니므로, 서비스별로 컨테이너를 나누어 배포하는 형태로 옮기는 것이 일반적입니다. 데이터베이스처럼 상태를 가진 구성 요소는 관리형 서비스나 외부 저장소로 분리하는 편이 안전합니다.

### 리전은 무엇을 기준으로 고르나요?

주 사용자와 가까운 리전을 고르면 네트워크 지연이 줄어듭니다. 여기에 데이터 보관 위치에 대한 요구사항과, 애플리케이션이 의존하는 외부 서비스의 위치를 함께 고려해 결정하는 것이 좋습니다.

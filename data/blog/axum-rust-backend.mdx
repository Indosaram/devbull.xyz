axum으로 백엔드를 만들면 라우터와 추출기, 상태, tower 미들웨어로 API 서버를 구성해요. Tokio 런타임 위에서 동작하고, 데이터베이스 풀은 State로 핸들러에 넘겨요. 배포 때는 포트, 종료 신호, 로그가 코드 구조만큼 중요해요. 아래는 프레임워크 비교부터 운영에서 볼 점까지예요.

## 한눈에 보기

핸들러는 async 함수이고, 입력은 추출기, 공유 자원은 State예요. 공통 로그와 제한은 tower 레이어로 두고 업무 로직과 나눠요. 서버 주소는 설정의 포트를 읽고, 종료 때 진행 중 요청을 끝낼 시간을 둬요. 작은 API부터 라우터를 나누는 기준을 정해 두면 나중에 덜 꼬여요.

## axum과 다른 Rust 웹 프레임워크 비교

표는 axum, actix-web, warp의 라우팅과 미들웨어를 나눈 거예요. axum은 tower를 그대로 쓰고, actix-web은 자체 미들웨어가 두텁고, warp는 필터 조합이에요. 팀이 tower에 익숙하면 axum이 운영 코드와 맞아요. 성능 숫자보다 미들웨어와 추출기 스타일로 고르세요.

| 항목 | axum | actix-web | warp |
| --- | --- | --- | --- |
| 기반 구조 | hyper 위에서 Tower 서비스 모델 사용 | 자체 런타임 계층과 액터 계열 설계, Tokio 생태계와 연동 | hyper 위에서 Filter 조합 사용 |
| 라우팅 표현 | Router에 경로와 메서드 라우터를 등록 | 매크로와 속성 기반 라우팅을 폭넓게 지원 | 필터를 and/or로 합성해 경로 구성 |
| 미들웨어 | Tower의 Layer와 Service를 그대로 사용 | 자체 미들웨어 트레이트 사용 | 필터 합성으로 전후 처리 |
| 요청 파싱 | FromRequestParts, FromRequest 추출기 | 추출기 트레이트 | 필터 단계에서 직접 추출 |
| 배울 것 | Tower 개념과 추출기 타입 규칙 | 프레임워크 문법 전반 | 필터 합성 사고방식 |

## 단계별로 axum 백엔드 구성하기

프로젝트에 axum과 tokio를 넣고, 헬스 라우트부터 띄워요. 추출기로 경로와 본문을 받고, 풀을 State로 넣어요. 에러를 한 응답 형식으로 맞춘 뒤, 추적 레이어를 바깥에 붙여요. 바인드와 종료를 설정과 신호에 연결하면 배포 형태가 나와요.

## 라우팅과 추출기 설계 요령

리소스마다 라우터를 나누고 상위에서 합쳐요. 추출 실패의 오류 형식을 팀 규칙으로 정해요. 본문을 미들웨어에서 소비하면 추출기가 빈 값을 받아요. 경로 설계와 권한 검사를 한 함수에 몰지 마세요.

## 미들웨어와 Tower 생태계

추적, 제한, 압축은 tower-http에서 가져오고, 인증은 보호 라우터에만 붙여요. 나중에 추가한 레이어가 바깥에서 먼저 요청을 봐요. 없는 경로에도 헤더가 필요하면 전체 레이어, 매칭된 경로만이면 route 레이어예요.

## 상태 공유와 데이터베이스 연결

풀은 Clone되는 State로 넘기고 핸들러에서 꺼내 써요. 요청마다 연결을 새로 만들지 않아요. 풀 설정과 타임아웃은 앱 설정으로 빼고 코드에 고정하지 마세요. 테스트는 다른 풀이나 대역으로 바꿔 끼울 수 있게 타입을 좁혀요.

## 에러 처리와 응답 설계

내부 오류와 클라이언트 오류의 상태 코드를 나누고, 본문 형식은 하나로 맞춰요. 미들웨어가 다른 형식을 쓰면 클라이언트가 분기하기 어려워요. 내부 문자열을 그대로 노출하지 않아요.

## 배포와 운영에서 확인할 점

컨테이너가 듣는 주소와 플랫폼이 주입하는 포트를 맞춰요. 종료 신호를 무시하면 배포 때마다 요청이 끊겨요. 로그는 표준 출력으로 남기고, 헬스 경로는 인증 없이 가볍게 둬요. 설정과 시크릿은 이미지 밖에 둬요.

## 상황별 선택 가이드

JSON API만이면 axum과 추적, 제한으로 시작해요. 기존 actix 코드가 많으면 이관 이유를 따로 정해요. 웹소켓이나 파일은 그 예제를 붙이되 종료와 상태를 같은 패턴으로 유지해요. hyper를 직접 쓰는 범위는 연결 커스텀으로 좁혀요.

## 자주 묻는 질문

Tokio 의존, 프레임워크 선택, 커넥션, 미들웨어 순서, 라우터 분할이 반복돼요.

### axum은 Tokio 없이도 동작하나요?

axum의 서버 실행은 Tokio 런타임을 전제로 하는 구성이 일반적이에요. 다른 런타임으로 억지 조합하기보다 tokio 기능 플래그를 필요한 만큼 켜요. 런타임 설정은 공식 문서의 서버 예제를 따라요.

### actix-web 대신 axum을 고르는 기준은 무엇인가요?

tower 레이어를 그대로 쓰고 추출기 스타일이 팀에 맞으면 axum이에요. 이미 actix로 운영 중이면 이관 비용이 기준이에요. 예제 양만으로 바꾸지 마세요.

### 핸들러에서 데이터베이스 커넥션은 어떻게 꺼내나요?

풀을 State로 넣고 핸들러 인자로 추출해요. 풀에서 연결을 빌려 쓰고 스코프가 끝나면 돌려요. 전역 정적 풀은 테스트가 어려워져요.

### 미들웨어 적용 순서는 어떻게 정해야 하나요?

나중에 붙인 레이어가 바깥에서 먼저 실행돼요. 추적을 가장 바깥에 두면 전체 구간이 보여요. 인증은 공개 라우터와 분리해 붙이세요.

### 라우터가 커지면 어떻게 나누는 게 좋나요?

도메인이나 리소스 단위로 Router를 만들고 nest나 merge로 합쳐요. 공통 레이어는 상위, 권한 레이어는 보호 라우터에 둬요. 파일만 나누고 타입이 공유되지 않으면 다시 꼬여요.

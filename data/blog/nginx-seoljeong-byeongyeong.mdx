## 한눈에 보기

실행 중인 프로세스가 연 설정과 include를 먼저 맞춰요. 고친 파일이 그 목록에 없으면 리로드해도 안 바뀌어요. 검사, 리로드, 테스트 요청, 실패 시 백업 복귀 순서를 팀 절차로 두세요. 워커 수처럼 프로세스 구성이 바뀌는 항목은 리로드만으로 안 될 수 있어요.

## 설정 파일 구조를 먼저 파악해요

본파일의 include가 conf.d나 사이트 디렉터리를 읽는지 확인해요. 도메인 설정은 server, 경로 설정은 location에 두는 습관을 유지하면 변경 범위가 줄어요. 여러 파일이 같은 지시어를 덮으면 나중 파일이 이겨요. 배포 도구가 다음 배포에 손본 파일을 덮는지도 봐요.

## 자주 바꾸는 설정 비교 표

표는 서버 이름, 포트, 문서 루트, 프록시, 업로드 크기, 압축, 워커, 로그가 어느 블록에 있고 어떤 반영이 필요한지를 나눈 거예요. 대부분의 HTTP 변경은 리로드예요. 워커 수와 바이너리 교체는 별도 절차일 수 있어요.

| 항목 | 주로 두는 위치 | 변경 예시 | 반영 방법 |
| --- | --- | --- | --- |
| 서버 이름 | server 블록 | `server_name`에 도메인 추가 | reload |
| 리스닝 포트 | server 블록 | `listen` 지시어 조정 | reload 후 접속 확인 |
| 문서 루트 | server, location 블록 | `root`, `alias` 경로 수정 | reload |
| 프록시 대상 | location 블록 | `proxy_pass` 업스트림 변경 | reload |
| 업로드 크기 | http, server, location 블록 | `client_max_body_size` 조정 | reload |
| 응답 압축 | http 블록 | `gzip` 관련 지시어 추가 | reload |
| 워커 프로세스 수 | main 컨텍스트 | `worker_processes` 조정 | 재시작이 필요할 수 있음 |
| 로그 경로 | http, server 블록 | `access_log`, `error_log` 변경 | reload |

## 단계별 설정 변경 방법

읽히는 파일 확인부터 롤백까지 여섯 단계예요.

### 1단계: 실제로 읽히는 파일 확인하기

마스터가 연 설정 경로와 include 목록을 적어요. 고칠 파일이 그 목록에 있는지 봐요. 컨테이너면 마운트 경로를 봐요.

### 2단계: 백업과 버전 관리

서버 파일과 저장소 중 무엇이 원본인지 정하고, 변경 전 내용을 남겨요. 여러 사람이 다른 조각을 동시에 고치면 include 순서를 합의해요. 백업 없이 리로드하면 롤백이 추측이 돼요.

### 3단계: 설정 파일 편집

바꿀 지시어만 해당 블록에 고쳐요. proxy_pass 슬래시와 alias 끝 슬래시는 경로가 바뀌는 지점이에요. 주석으로 왜 바꿨는지 한 줄 남기면 다음 변경이 쉬워요.

### 4단계: 문법 검사

같은 설정 경로로 nginx -t를 해요. 실패하면 메시지의 파일과 줄을 고치고 다시 검사해요. 통과 전에는 리로드하지 않아요.

### 5단계: 무중단 반영

검사 통과 뒤 리로드해요. systemd면 그 유닛으로, 컨테이너면 그 안의 마스터로 신호를 보내요. 다른 바이너리를 리로드하면 고친 파일이 안 읽혀요.

### 6단계: 반영 확인과 롤백

테스트 요청의 응답 헤더와 오류 로그를 봐요. 기대한 서버가 아니면 include와 server_name을 다시 봐요. 실패하면 백업을 되돌리고 검사 후 다시 리로드해요.

## 상황별 선택: reload와 restart

표는 server와 location, 업스트림 변경은 리로드, 워커 수와 바이너리 교체는 별도 절차일 수 있다고 나눈 거예요. 기동 실패를 재시작으로 반복하면 중단이 길어요. 연결을 유지해야 하면 리로드를 먼저 검토해요.

| 상황 | 권장 방식 | 이유 |
| --- | --- | --- |
| server, location 규칙 변경 | reload | 기존 연결을 유지한 채 교체 |
| 업스트림 대상 변경 | reload | 새 워커가 새 설정을 사용 |
| 워커 프로세스 수 조정 | 재시작이 필요할 수 있음 | 프로세스 구성 자체가 달라짐 |
| 실행 바이너리 교체 | 공식 업그레이드 절차 | 무중단 교체는 별도 절차로 처리 |
| 설정 오류로 기동 실패 | 원인 수정 후 기동 | 재시작 반복은 중단 시간을 늘림 |

## 주의할 점

문법 성공은 라우팅 성공이 아니에요. 기본 서버가 바뀌면 모르는 호스트가 다른 사이트로 가요. 로그 경로를 바꾸면 예전 파일을 보고 있을 수 있어요. 저장소와 서버 파일이 다르면 다음 배포가 변경을 지워요.

## 자주 묻는 질문

재시작 없이 반영되는지, 검사 통과 후 실패, 파일 분할, 리로드와 재시작이 반복돼요.

### nginx 설정 변경을 재시작 없이 반영할 수 있나요?

많은 HTTP 설정은 리로드로 반영해요. 프로세스 구성이 바뀌는 항목은 문서에서 재시작이 필요한지 봐요. 문법 오류면 리로드는 거절되는 쪽이 일반적이에요.

### nginx -t는 통과하는데 요청이 실패하는 이유는 무엇인가요?

문법은 맞지만 server_name, location, 업스트림 대상이 의도와 다를 수 있어요. 오류 로그와 응답이 어느 블록인지 봐요. 업스트림이 죽어 있으면 문법과 무관하게 실패해요.

### 설정 파일을 여러 개로 나눠 관리해도 되나요?

include로 나누는 것이 일반적이에요. 본파일이 그 파일을 읽는지 확인해요. 조각만 검사하면 상위 문맥이 빠져요.

### reload와 restart 중 무엇을 선택해야 하나요?

연결을 유지할 설정 변경은 리로드예요. 바이너리 교체나 문서가 재시작을 요구하는 항목은 그 절차를 따라요. 실패 원인을 모르면 재시작을 반복하지 말고 로그를 봐요.

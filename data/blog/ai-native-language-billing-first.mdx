에이전트 청구서에서 코드 텍스트가 차지하는 몫은 0.8%다. 사용자가 손댈 수 있는 항목을 전부 지워도 6%다. 같은 버그를 7파일 리포와 202파일 리포에 넣고 돌려보니 입력 토큰은 18%만 늘었다. 리포는 29배가 됐는데.

새 언어를 만드는 일은 이 0.8%를 노리는 일이다. 청구서의 나머지는 매 턴 다시 올라간다.

## 청구서를 분해하면

"Token Reduction Is Not Cost Reduction"(arXiv 2607.12161, 2026-07)은 Claude Code 세션 1,212개, 요청 11,773건을 구성요소별로 나눴다. 토큰 수가 아니라 비용 기준으로.

| 구성요소                             | 컨텍스트 비중 | 비용 비중 |
| ------------------------------------ | ------------- | --------- |
| 하네스 기본(시스템 프롬프트·툴 정의) | 71.6%         | **74.7%** |
| 숨은 사고(hidden thinking)           | 21.8%         | 19.4%     |
| 툴 출력                              | 3.5%          | 3.3%      |
| 툴 호출 인자                         | 1.6%          | 1.4%      |
| **디스크에서 읽은 파일 텍스트**      | 0.9%          | **0.8%**  |
| 대화 히스토리                        | 0.5%          | 0.5%      |

사람이 실제로 손댈 수 있는 항목은 이 여섯 개가 전부다. 코드는 맨 아래에 있다.

이 표는 Claude Code와 Haiku 4.5 가격으로 잰 특정 워크로드의 실측 평균이다. 원문도 _"These are empirical averages from the coding-agent workloads evaluated in this study, not industry averages"_ 라고 적어둔다. 모델과 하네스가 달라지면 비율도 달라진다. 다만 코드가 맨 아래라는 순서는 내 측정(29배 → 18%)과 같은 방향을 가리킨다.

하네스 프롬프트는 매 턴 다시 청구된다. 코드는 한 번 읽고 끝나지만 시스템 프롬프트와 툴 스키마는 200턴이면 200번 올라간다.

| ------------- | ------------------------- |
| 코드 50% 압축 | **0.4%**                  |
| 턴 10% 감소   | **약 7.5%** (74.7% × 10%) |

## 29배 실험

인용만으로는 부족해서 직접 돌렸다. 같은 버그를 7파일 리포와 202파일 리포에 각각 넣고 같은 프롬프트로 에이전트를 돌렸다.

처음에는 5개씩 병렬로 돌렸다.

| 조건         | 7파일                             | 202파일                            |
| ------------ | --------------------------------- | ---------------------------------- |
| 병렬(동시 5) | 6, 21, 40, 35, 43 → 평균 **29.0** | 10, 12, 10, 12, 40 → 평균 **16.8** |

작은 리포가 더 오래 걸렸다. 원인은 리포가 아니라 실행 순서였다. 작은 리포 5개를 먼저 돌리고 큰 리포 5개를 나중에 돌려서, 대기 시간이 조건과 완전히 겹쳐 있었다.

같은 리포, 같은 과제가 병렬에서는 40턴 걸렸고 혼자 돌리니 7턴이 됐다. 앞의 "+50%"도 "-86%"도 잡음이었다.

토큰은 이렇게 나왔다.

| 리포    | 평균 입력 토큰 | 턴    |
| ------- | -------------- | ----- |
| 7파일   | 161,602        | 9.50  |
| 202파일 | 190,729        | 10.50 |

파일 수는 29배인데 입력 토큰은 1.18배다. 나머지는 턴 수에서 나온다. 순차 8회의 턴당 입력은 14,710~21,092토큰이었다. 한 줄짜리 버그를 고치는 데도 매 턴 그만큼을 다시 보냈다. 청구 토큰의 54.5%는 캐시 읽기였다(실행별 50.6~59.7%). 같은 대화를 매 턴 재전송했다는 뜻이다.

## 압축하면 비싸진다

문법을 압축하면 조금은 싸질 것 같다. 이 가정을 직접 반박한 실험이 있다.

"Beyond Human-Readable"(arXiv 2604.07502, 2026-04):

> _aggressive compression **increased total session cost by 67%** despite reducing input tokens by 17%_

입력 토큰은 17% 줄었는데 세션 비용은 67% 늘었다. 모델이 압축된 형식을 해석하느라 더 많이 추론한 탓이다. 저자들의 결론은 "의미 밀도 최적화"이지 "최소 토큰"이 아니다.

다른 압축 실험의 환율도 나쁘다.

| 개입                                            | 토큰 절감          | 품질 손실                |
| ----------------------------------------------- | ------------------ | ------------------------ |
| 코드 미니피케이션 (2606.01326)                  | **-42%** 입력 토큰 | 해결률 **-12%p**         |
| 파일 탐색 → Tree-sitter 지식그래프 (2603.27277) | 10배 적은 토큰     | 답변 품질 **83% vs 92%** |

토큰 42%를 아끼려고 해결률 12%p를 내는 거래다. 지식그래프 쪽은 토큰을 10분의 1로 줄이는 대신 품질이 9%p 떨어졌다.

## 토크나이저는 이미 수렴했다

토크나이저가 유리하게 쪼개지는 문법을 만들면 어떨까. 이것도 측정돼 있다.

Tokka-Bench(arXiv 2610.08794)는 20개 프로그래밍 언어를 재고 이렇게 결론낸다.

> _programming-language efficiency has **converged** among recent tokenizers_

최근 토크나이저 사이의 차이는 `cl100k`와 `o200k`를 비교해 -1.4% ~ +2.4% 수준이다. Anthropic의 최신 토크나이저는 같은 텍스트에 토큰이 약 30% 더 많다. 추세는 새 언어 설계자에게 불리한 쪽으로 가고 있다.

모델은 낯선 언어를 만나면 Python으로 먼저 프로토타이핑하고 번역한다. 새 언어를 주면 그 언어로 사고하는 게 아니라 익숙한 언어로 사고한 뒤 옮긴다. 번역 비용이 새 문법의 절약분을 즉시 잡아먹는다.

## 레버는 언어 밖에 있다

같은 돈을 쓰면서 효과가 큰 순서다. 전부 언어를 바꾸지 않고 할 수 있는 일이다.

| 순위 | 레버                       | 측정된 효과                                  |
| ---- | -------------------------- | -------------------------------------------- |
| 1    | **하네스 고정비용 줄이기** | 리포 29배 → 입력 **18%** 증가뿐 (내 실측)    |
| 2    | **툴 호출을 코드로**       | 150,000 → 2,000 토큰, **-98.7%** (Code Mode) |
| 3    | **피드백에 대안을 넣기**   | 14/50 → **36/50**, **+44%p** (VeriHarness)   |
| 4    | **편집 형식을 diff로**     | **20% → 61%** (Aider, 같은 모델·같은 언어)   |
| 5    | 언어 표면                  | 분산의 **16%** 상한                          |
| —    | 문법 압축                  | 청구서의 **0.4%**                            |

4번이 특히 시사적이다. Aider는 언어를 그대로 두고 편집 형식만 unified diff로 바꿔 성공률을 3배로 올렸다. 논문 제목이 _"Unified diffs make GPT-4 Turbo 3X less lazy"_ 다. 진단도 정확하다.

> _GPT is terrible at working with source code line numbers_ … _choose an edit format that GPT is already familiar with_

훈련 분포와 일치하는 형식이 이긴다. 새 언어가 지는 이유도, diff가 이기는 이유도, 코드 모드가 이기는 이유도 같다.

검증기 없이 자기교정을 기대하면 안 된다. "LLMs Cannot Self-Correct Reasoning Yet"(arXiv 2310.01798, ICLR 2024)는 외부 피드백이 없으면 성능이 오히려 나빠질 수 있다고 보고한다.

## 새 언어를 검토 중이라면

만들기 전에 이 네 개부터 재라.

1. **총 세션 비용을 재라.** 입력 토큰이 아니라. 입력이 줄고 비용이 느는 경우가 실제로 있다(-17% → +67%).
2. **턴 수를 종속변수로 삼아라.** 코드 압축률은 지표가 아니다. 압축을 잘해도 턴이 그대로면 돈도 그대로다.
3. **하네스부터 의심하라.** 시스템 프롬프트·툴 스키마·메모리 주입이 매 턴 얼마나 올라가는지 세라. 내 측정에서는 턴당 입력이 1.4만~2.1만 토큰이었고, 청구 토큰의 54.5%가 캐시 읽기였다.
4. **형식을 먼저 바꿔라.** 언어를 바꾸는 것보다 편집 형식을 바꾸는 게 3배 싸다.

## 한계

- **내 실측은 n=4다.** 순차 4회씩, 총 8회. 리포 규모 효과가 없다는 결론은 이 표본에서 유효하고, 더 큰 효과가 없다고 단정하지는 않는다.
- **병렬 측정은 실패한 실험이다.** 조건과 대기 순서가 겹쳐 있었다. 순차로 다시 쟀고, 이 글에는 둘 다 적었다.
- **인용 논문을 재현하지 않았다.** 2607.12161의 0.8%·74.7%, Aider의 20%→61%, VeriHarness의 14/50→36/50은 원문 보고값이다. 다시 돌린 건 리포 규모 실험 하나뿐이다.
- **"턴 10% → 비용 7.5%"는 산술이다.** 74.7%가 매 턴 재청구된다는 구조에서 계산한 값이지, 그 자체를 실험한 논문이 있어서 인용한 게 아니다.
- **원래 이 글에는 내 산술 오류가 있었다.** "청구 토큰의 98.7%가 캐시 읽기"라고 썼는데, `billed = input + cacheRead + output`이 8회 전부에서 정확히 맞아떨어지므로 두 항목은 더해지는 별개 값이다. 나머지로 나눈 게 틀렸고 올바른 값은 54.5%다. 발행 전 수치 대조에서 잡아 바로잡았다.

방향은 뒤집히지 않는다. 하네스가 청구서의 4분의 3을 차지하고 코드는 1% 미만이라는 두 사실은 서로 다른 측정에서 나왔고, 내 실측(29배 → 18%)도 같은 방향을 가리킨다.

## 한눈에 보기

"is this correct?"는 대개 설정 파일 몇 줄을 붙여넣고 판단을 구하는 질문이에요. 이 질문에 스스로 답하려면 감각이 아니라 순서가 필요해요. 문법 검사로 형식을 걸러내고, 공식 문서로 의도를 대조하고, 같은 조건을 스테이징에서 재현한 뒤, 로그와 헬스체크로 결과를 확인하면 돼요.

- 문법 검사는 최소 조건이에요. 통과했다고 해서 의도까지 맞는 것은 아니에요.
- 공식 문서의 옵션 설명과 내 설정이 같은 전제를 공유하는지 확인해요.
- 로컬 노트북에서의 성공은 운영 환경 성공의 근거가 아니에요.
- 언제든 되돌릴 수 있는 상태에서만 적용해요.

## 무엇을 기준으로 맞다고 판단할까

설정이 맞는지 판단하는 기준은 한 가지가 아니에요. 형식, 의도, 환경, 관측, 복구라는 서로 다른 층위를 각각 확인해야 해요. 아래 표는 그 층위를 정리한 것이에요.

| 확인 항목 | 맞다고 볼 수 있는 근거 | 자주 하는 착각 |
| --- | --- | --- |
| 문법 | 설정 파서가 오류 없이 통과해요 | 문법 통과가 동작 보장이라고 믿어요 |
| 의도 | 공식 문서의 옵션 설명과 일치해요 | 블로그 예제를 그대로 복사해요 |
| 환경 | 스테이징에서 같은 결과가 재현돼요 | 로컬 성공을 운영 성공으로 봐요 |
| 관측 | 로그와 헬스체크가 기대대로 남아요 | 에러 로그가 없으면 정상이라고 봐요 |
| 복구 | 되돌리는 절차가 문서로 있어요 | 문제가 생긴 뒤에 롤백을 생각해요 |

이 표에서 가장 자주 무너지는 칸은 의도와 환경이에요. 문법은 도구가 대신 봐주지만, 내가 무엇을 하려는지와 그 전제가 운영 환경에서도 성립하는지는 사람이 확인해야 해요.

## 단계별 검증 절차

**먼저 문법 검사로 후보를 걸러요.** Nginx라면 nginx -t로 설정 파일을 파싱하고, systemd 유닛이라면 systemd-analyze verify로 유닛 파일을 검사해요. 컨테이너 이미지는 docker build가 중간에 실패하지 않는지 보고, 쿠버네티스 매니페스트는 kubectl apply --dry-run=server로 API 서버 검증을 받아요. 인프라 코드라면 terraform validate와 plan 결과를 확인해요. 이 단계에서 걸러지는 것은 형식 오류이지 설계 오류가 아니에요.

**다음으로 공식 문서와 의도를 대조해요.** 옵션 이름이 비슷해도 기본값과 적용 범위가 달라요. 타임아웃 계열 지시어는 어느 단계에서 적용되는지에 따라 체감 동작이 달라지고, 프록시 관련 헤더는 설정 위치에 따라 전달 여부가 갈려요. 내가 기대하는 동작을 한 문장으로 적고, 그 문장을 공식 문서의 설명과 비교해 보세요. 문장으로 적을 수 없다면 아직 의도가 정리되지 않은 상태예요.

**이어서 스테이징에서 같은 조건을 재현해요.** 운영과 스테이징의 차이는 대개 설정 파일보다 환경 변수, 시크릿, 네트워크 경로, 파일 권한에서 나와요. 같은 이미지, 같은 환경 변수, 같은 볼륨 마운트를 맞춘 뒤 실제 요청을 흘려보내세요. 재현이 되면 그때부터는 추측이 아니라 실험이 돼요.

**그다음 로그와 헬스체크로 결과를 관측해요.** 애플리케이션 로그, 리버스 프록시 액세스 로그, 시스템 저널을 함께 봐요. 헬스체크는 프로세스가 살아 있는지가 아니라 실제로 요청을 처리할 수 있는지를 물어야 해요. 준비 상태와 생존 상태를 구분해 두면 배포 중 무의미한 트래픽 유입을 줄일 수 있어요.

**마지막으로 되돌릴 방법을 준비해요.** 이전 리비전, 이전 이미지 태그, 이전 설정 파일을 미리 확보하고 복구 절차를 한 화면에 적어 둬요. "is this correct?"에 대한 진짜 답은 맞다는 확신이 아니라, 틀렸을 때 빠르게 원상복구할 수 있다는 사실에서 나와요.

## 상황별 선택

**정적 설정 파일만 바뀌었을 때**는 문법 검사와 리로드 절차 확인만으로도 상당 부분 방어가 돼요. 다만 리로드가 실패하면 이전 설정으로 자동 복귀하는지까지 확인해 두세요.

**애플리케이션 이미지가 바뀌었을 때**는 빌드 재현성과 실행 사용자, 환경 변수 주입 방식을 먼저 봐요. 이미지가 같아도 주입되는 값이 다르면 동작이 달라져요.

**인프라 코드가 바뀌었을 때**는 plan 결과를 사람이 읽는 것이 핵심이에요. 삭제 예정 리소스가 있는지, 교체가 발생하는지 확인하지 않으면 적용 후에 되돌리기 어려운 상황을 만나요.

**급하게 핫픽스를 넣어야 할 때**는 검증 단계를 줄이되 생략하지는 마세요. 문법 검사와 헬스체크 확인만 남기고, 나머지는 배포 후 추적 과제로 남겨 두는 편이 안전해요.

## 주의할 점

- 문법 통과와 의도 일치는 다른 문제예요. 도구가 통과시킨 설정이 요구사항과 어긋날 수 있어요.
- 복사한 예제의 전제 조건을 확인해요. 특정 디렉터리 구조나 권한을 가정한 예제가 많아요.
- 시크릿을 그대로 붙여넣지 않아요. 검토를 요청할 때는 값을 마스킹하고 구조만 공유하세요.
- dry-run은 API 검증이지 동작 검증이 아니에요. 실제 트래픽에서의 결과는 별도로 확인해야 해요.
- 재시작을 첫 번째 조치로 삼지 않아요. 재시작은 증거를 지우는 행동이 될 수 있어요.
- 검증 결과를 기록해요. 어떤 조건에서 무엇을 확인했는지 남겨야 다음 배포에서 같은 질문을 반복하지 않아요.

## 자주 묻는 질문

### is this correct?라고 물을 때 무엇을 먼저 확인해야 하나요?

질문을 받는 입장이든 하는 입장이든, 먼저 확인할 것은 설정의 문법과 그 설정이 놓인 위치예요. 어느 파일의 어느 블록에 들어가는지, 상위 설정이 무엇을 상속하는지가 드러나야 판단이 가능해요. 그다음에 기대하는 동작을 한 문장으로 붙이면 검토 속도가 크게 달라져요.

### nginx -t가 통과하면 바로 적용해도 되나요?

문법 검사 통과는 파싱이 된다는 뜻일 뿐, 라우팅이나 프록시 동작이 의도대로 된다는 뜻은 아니에요. 리로드 전에 스테이징에서 같은 요청을 재현하고, 리로드 후 액세스 로그와 에러 로그를 확인하는 편이 안전해요. 리로드 실패 시 이전 설정으로 돌아가는지도 함께 확인해 두세요.

### 로컬에서는 되는데 운영에서만 실패하면 어디를 의심해야 하나요?

환경 변수, 시크릿 주입 방식, 파일 권한, 네트워크 경로, 그리고 프록시 뒤에서 전달되는 헤더를 순서대로 의심해 보세요. 로컬과 운영의 차이를 목록으로 만들고 하나씩 지워가는 방식이 가장 빠릅니다. 차이를 지울 때마다 결과를 기록해 두면 원인 후보가 금방 좁혀져요.

### 동료에게 설정 검토를 부탁할 때 무엇을 함께 보내야 하나요?

설정 파일 조각, 관련된 상위 설정의 위치, 기대하는 동작, 실제로 관찰된 결과를 함께 보내세요. 여기에 실행 환경과 사용 중인 도구의 종류를 덧붙이면 검토자가 문서를 다시 찾아볼 필요가 없어요. 시크릿과 내부 호스트 이름은 마스킹해서 보내는 것이 기본이에요.

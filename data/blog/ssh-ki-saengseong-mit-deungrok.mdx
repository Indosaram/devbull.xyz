ssh 키 생성과 등록은 내 컴퓨터에서 키 쌍을 만든 뒤, 공개키만 서버의 `authorized_keys`나 Git 호스팅의 SSH 키 칸에 넣는 일이에요. 접속할 때 서버는 짧은 도전을 보내고, 비밀키로 만든 서명이 공개키와 맞으면 비밀번호 없이 로그인돼요. 확장자가 없는 비밀키는 작업 계정 홈의 `.ssh`에만 두고, `.pub` 한 줄만 밖으로 내보내요. 서버가 여러 대이거나 배포 계정이 따로 있으면 키 파일도 용도별로 나눠 두는 편이 나중에 폐기하기 쉬워요.

## 한눈에 보기

서버가 믿는 것은 공개키이고, 내가 증명하는 수단은 비밀키예요. 그래서 서버에 올라가는 파일은 항상 `.pub`이고, 같은 이름의 비밀키를 붙이면 등록이 아니라 유출이 돼요. 작업 순서는 키 생성, 공개키 한 줄 확인, 서버 등록, 권한 좁히기, 로그인 시도로 고정해 두면 빠뜨리는 단계가 줄어요.

- 키 쌍 생성: `ssh-keygen -t ed25519 -C "용도 메모"`
- 공개키 확인: `cat ~/.ssh/id_ed25519.pub`
- 서버 등록: `ssh-copy-id user@host` 또는 `authorized_keys`에 직접 추가
- 권한 정리: `~/.ssh`는 700, `authorized_keys`는 600
- 접속 확인: `ssh -i ~/.ssh/id_ed25519 user@host`

이름이 비슷해도 쓰는 시점이 달라요. `ssh-keygen`은 만들기, `ssh-copy-id`는 공개키 옮기기, `ssh`는 로그인, `ssh-add`는 이미 만든 비밀키를 에이전트에 올리기예요.

## 키 종류와 용도 비교

새 키는 ed25519로 만드는 경우가 많아요. 문자열이 짧아 줄바꿈이 섞일 일이 적고, 최근 OpenSSH에서 기본으로 다루는 알고리즘이에요. 상대 서버나 장비가 이 형식을 거절하면 RSA로 다시 만들고, 등록 위치는 똑같이 `authorized_keys`예요. ECDSA는 ed25519가 안 될 때의 차선으로만 보고, 장비 쪽 지원 여부를 먼저 보는 편이 안전해요.

| 항목 | ed25519 | RSA | ECDSA |
| --- | --- | --- | --- |
| 주 사용처 | 새 서버, Git 호스팅, 개인 작업 키 | 오래된 sshd나 네트워크 장비 | ed25519를 거절하는 일부 환경 |
| 만드는 법 | `ssh-keygen -t ed25519` | `ssh-keygen -t rsa` 후 길이는 기본보다 넉넉히 | `ssh-keygen -t ecdsa` |
| 장점 | 문자열이 짧고 최신 OpenSSH에서 우선으로 다룸 | 오래된 클라이언트와도 맞물림 | RSA보다 키가 짧음 |
| 주의점 | 아주 오래된 클라이언트는 알고리즘을 모름 | 짧게 만들면 보안이 약해짐 | 구현 이슈 이력이 있어 지원 여부부터 봄 |
| 등록 | 공개키 한 줄을 authorized_keys에 추가 | 같은 방식 | 같은 방식 |

알고리즘만 바꿔도 서버 설정 파일을 종류별로 다시 쓸 필요는 거의 없어요. 클라이언트 생성 옵션만 달라지고, 검증 경로는 공개키 한 줄을 읽는 쪽으로 같아요.

## 단계별 방법

로컬에서 쌍을 만든 다음 공개키만 옮기고, 권한을 좁힌 뒤에 로그인을 시도하는 순서가 안전해요. 순서를 바꾸면 비밀키를 서버에 올리거나, 권한 때문에 서버가 키를 무시하는 일이 생겨요.

### 1) 키 쌍 생성하기

가장 단순한 형태는 알고리즘과 메모를 지정하는 명령이에요. `-C`에 넣는 값은 인증에 쓰이지 않는 주석이라, 서버 이름이나 용도를 적어 두면 나중에 어떤 키인지 구분하기 쉬워요.

`ssh-keygen -t ed25519 -C "deploy@was"`

실행하면 저장 경로를 묻고, 이어서 passphrase를 받아요. 경로를 비워 두면 홈 아래 `.ssh`에 비밀키와 `.pub`가 같이 생겨요. 같은 이름이 이미 있으면 덮어쓸지 묻는데, 그 키로 접속 중인 서버가 있으면 거절해야 해요.

서버마다 키가 달라야 하면 `-f`로 파일 이름을 나눠요. `ssh-keygen -t ed25519 -f ~/.ssh/id_deploy_was -C "deploy"`처럼 두면, 한 파일이 새어 나갔을 때 교체 범위를 그 용도로 한정할 수 있어요.

### 2) 공개키 확인하기

등록할 내용은 `.pub` 파일의 한 줄이에요. 앞에는 `ssh-ed25519` 같은 알고리즘 이름, 가운데는 키 본문, 끝에는 주석이 붙어요.

`cat ~/.ssh/id_ed25519.pub`

지문만 대조할 때는 `ssh-keygen -lf ~/.ssh/id_ed25519.pub`를 써요. 서버에 이미 들어간 줄과 내 파일이 같은지 볼 때, 본문 전체를 눈으로 비교하는 것보다 실수가 적어요. 붙여넣을 때는 줄 중간에서 끊지 말고, 앞뒤 공백도 넣지 않아요.

### 3) 서버에 공개키 등록하기

비밀번호 로그인이 아직 열려 있으면 `ssh-copy-id`가 짧아요. 지정한 공개키를 읽어 서버 `authorized_keys`에 덧붙이고, 디렉터리 권한도 맞춰 줘요.

`ssh-copy-id -i ~/.ssh/id_ed25519.pub user@host`

비밀번호 로그인을 닫아 둔 계정이나 자동화 호스트는 직접 추가하는 편이 분명해요. 서버에 들어간 뒤 `.ssh`를 만들고 권한을 좁힌 다음, 공개키 한 줄만 이어 붙이면 돼요.

`mkdir -p ~/.ssh`
`chmod 700 ~/.ssh`
`echo "ssh-ed25519 AAAA... deploy@was" >> ~/.ssh/authorized_keys`
`chmod 600 ~/.ssh/authorized_keys`

Git 호스팅은 웹 화면의 SSH 키 항목에 같은 공개키를 붙여요. 계정 전체에 거는 키와 저장소 배포용 키는 권한이 다르니, 배포 파이프라인에는 그 저장소만 받는 키를 따로 두는 편이 안전해요.

### 4) 권한 정리하기

sshd는 키가 들어 있는 디렉터리와 파일이 다른 사용자에게 열려 있으면 그 키를 무시하는 경우가 많아요. 그래서 홈의 `.ssh`와 `authorized_keys`, 로컬 비밀키 권한을 먼저 좁혀요.

`chmod 700 ~/.ssh`
`chmod 600 ~/.ssh/authorized_keys`
`chmod 600 ~/.ssh/id_ed25519`

소유자가 현재 로그인 계정과 다르면 권한을 맞춰도 읽히지 않아요. `chown -R user:user ~/.ssh`처럼 계정에 맞추고, SELinux를 쓰는 배포판에서 파일을 새로 만들었다면 `restorecon -R ~/.ssh`로 컨텍스트를 되돌려요.

### 5) 접속 테스트와 ssh-agent

등록 뒤에는 `ssh -i ~/.ssh/id_ed25519 user@host`로 로그인을 시도해요. 거절되면 `-v`를 붙여 어느 키를 제안했고 서버가 무엇을 거절했는지 봐요. 서버 쪽 이유는 배포판의 인증 로그나 systemd 저널에 남아요.

passphrase를 걸었다면 매 접속마다 치지 않도록 에이전트에 올려요. 세션에서 `eval "$(ssh-agent -s)"`를 실행한 뒤 `ssh-add ~/.ssh/id_ed25519`를 하면, 그 세션 안에서는 암호를 다시 묻지 않아요. 자주 쓰는 호스트는 `~/.ssh/config`의 Host 항목에 HostName, User, IdentityFile을 적어 두면 별칭만으로 접속할 수 있어요.

## 상황별 선택

서버 한 대에 개인 계정으로 들어가는 정도라면 키 하나로 충분해요. 배포, 점프 호스트, 공용 장비가 섞이면 키를 용도별로 나누는 편이 폐기할 때 덜 아파요.

- 개인 개발 서버: 계정당 키 하나를 만들고 `ssh-copy-id`로 등록해요.
- 배포 자동화: 배포 전용 키를 따로 만들고, 서버에서는 그 키에 허용할 명령만 묶어 두요.
- 여러 서버 운영: `~/.ssh/config`에 Host 별칭과 IdentityFile을 적어 두고 골라 써요.
- 점프 호스트 경유: `ProxyJump`로 중간 서버를 적으면 한 번의 접속 명령으로 이어져요.
- 키 교체: 새 키를 먼저 등록해 로그인을 본 뒤에 기존 줄을 지워요.

한 비밀키를 모든 서버와 Git 계정에 재사용하면, 그 파일 하나가 새었을 때 교체 목록이 끝없이 늘어요. 용도별로 나누고, 새 키를 먼저 등록해 로그인이 된 뒤에 옛 줄을 지워요.

## 주의할 점

비밀키는 저장소, 메신저, 티켓에 올라가면 그 순간부터 폐기 대상이에요. `.pub`가 아닌 파일을 붙여넣었는지도 등록 직후 한 번 봐요. 서버에 비밀키 본문이 들어가 있으면 지우고 키 쌍을 새로 만드는 쪽이 맞아요.

`sshd_config`에서 공개키 인증이 꺼져 있거나 `AuthorizedKeysFile` 경로가 기본과 다르면, 파일을 제대로 만들어도 로그인이 안 돼요. 설정을 고친 뒤에는 문법 검사를 먼저 하고, 서비스를 다시 읽혀요. 재시작 전에 기존 세션을 하나 열어 두면, 실수로 자신을 잠그는 상황을 피할 수 있어요.

호스트 키 경고는 그냥 넘기지 않아요. 서버를 재설치했다면 지문이 바뀌는 것이 자연스럽지만, 그렇지 않은데 경고가 뜨면 접속을 멈추고 관리자에게 지문을 대조해요. 재설치가 맞다면 `known_hosts`에서 그 호스트 줄만 지우고 다시 접속해요.

passphrase는 비워 두지 않는 쪽을 권해요. 노트북이 열렸을 때 비밀키 파일만으로 서버에 들어가지 못하게 막아 주기 때문이에요. 입력이 거슬리면 에이전트에 올려 세션 동안만 재사용하면 돼요.

## 자주 묻는 질문

### ssh 키는 어디에 저장되나요?

기본 위치는 사용자 홈의 `.ssh`예요. `ssh-keygen`이 경로를 물었을 때 그냥 넘어가면 비밀키와 `.pub`가 그 폴더에 생겨요. `-f`로 다른 경로를 골랐다면 접속 때 `-i`로 그 파일을 지정하거나, `~/.ssh/config`의 IdentityFile에 같은 경로를 적어야 해요.

### 기존 키를 덮어써도 되나요?

그 파일로 들어가는 서버가 하나라도 있으면 덮어쓰지 않아요. 덮어쓰는 순간 예전에 등록해 둔 공개키와 짝이 깨져서 로그인이 거절돼요. 다른 이름으로 새 키를 만들고, 서버에 추가한 뒤 로그인이 되는 것을 본 다음에 옛 줄을 지워요.

### 서버에서 접속이 거부될 때 무엇을 확인해야 하나요?

`authorized_keys`에 공개키가 한 줄로 들어갔는지, 앞뒤에 잘린 글자가 없는지부터 봐요. 이어서 `.ssh`와 `authorized_keys`의 권한과 소유자가 현재 계정인지 봐요. 여기가 맞는데도 거절되면 `sshd_config`의 공개키 인증과 `AuthorizedKeysFile` 경로, 그리고 서버 인증 로그를 같이 봐요.

### passphrase를 꼭 걸어야 하나요?

필수는 아니에요. 다만 비밀키 파일이 복사돼도 암호 없이는 못 쓰게 하려면 걸어 두는 편이 안전해요. 매번 치기 싫으면 `ssh-agent`와 `ssh-add`로 그 세션 안에만 올려 두면 돼요.

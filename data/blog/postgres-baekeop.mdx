Postgres 백업은 논리 백업으로 객체와 데이터를 덤프하거나, 물리 백업으로 데이터 디렉터리를 복사하거나, WAL을 쌓아 특정 시점으로 되돌리는 갈래가 있어요. 파일만 만들어 두고 복원을 한 번도 안 해 보면 장애 때 못 써요. 도구 이름보다 복구 목표, 즉 무엇을 어느 시점까지 되돌려야 하는지를 먼저 정해요. 아래는 방식 비교와 복원 검증이에요.

## 한눈에 보기

논리 백업은 pg_dump와 pg_dumpall, 물리 백업은 pg_basebackup이 대표예요. PITR은 베이스 백업과 WAL 아카이브가 둘 다 있어야 해요. 백업 파일은 운영 디스크와 다른 곳에 두고, 복원 절차를 따로 연습해요. 버전과 확장, 역할이 복원 대상과 맞아야 완전 복구에 가까워져요.

## 논리 백업과 물리 백업 비교

표는 도구, 단위, 장점, 주의점을 나눈 거예요. 논리 백업은 테이블이나 데이터베이스 단위로 옮기기 좋고, 큰 용량에서는 시간이 길어질 수 있어요. 물리 백업은 클러스터 전체를 같은 계열 버전으로 되돌릴 때 맞아요. PITR은 WAL이 끊기면 목표 시점까지 못 가요.

| 항목 | 논리 백업 | 물리 백업 |
| --- | --- | --- |
| 백업 단위 | 데이터베이스, 스키마, 테이블 등 선택 가능 | 클러스터 전체 |
| 대표 도구 | `pg_dump`, `pg_dumpall` | `pg_basebackup`, WAL 아카이빙 |
| 복원 방식 | SQL 실행 또는 `pg_restore`로 객체 복원 | 데이터 디렉터리 교체 후 서버 기동 |
| 장점 | 선택적 복원과 이관에 유연함 | 전체 복구와 시점 복구에 적합함 |
| 주의점 | 백업 중 잠금과 일관성 영향 확인 필요 | 같은 주 버전과 호환 환경 확인 필요 |

## 단계별 백업 방법

어떤 복구가 필요한지에 맞춰 도구를 고르고, 만든 파일을 다른 위치에서 읽어 봐요.

### pg_dump로 논리 백업

한 데이터베이스나 스키마, 테이블을 덤프해요. 형식은 나중에 선택 복원이 필요하면 커스텀 형식을 검토해요. 덤프 중에도 서비스는 살아 있지만, 긴 덤프는 부하가 되니 시간을 피해서 돌려요. 역할과 테이블스페이스 전역 객체는 이 도구만으로 안 담길 수 있어요.

### pg_dumpall로 클러스터 전체 백업

역할과 테이블스페이스처럼 클러스터 공통 객체가 필요할 때 써요. 데이터베이스가 여러 개면 이 출력이 논리 백업의 전체를 덮는 데 가까워요. 용량과 비밀이 들어 있을 수 있으니 보관 권한을 좁혀요.

### pg_basebackup으로 물리 백업

데이터 디렉터리 복사에 가까워서, 복원 서버의 버전과 경로, 권한을 같이 봐야 해요. 복제 연결 권한이 있어야 떠요. 백업이 끝나는 동안 WAL이 따라붙는지 확인해야 단독으로도 기동할 수 있어요.

### WAL 아카이빙과 PITR

베이스 백업 이후의 WAL을 빠짐없이 보관해야 특정 시점으로 되돌릴 수 있어요. 아카이브 명령이 실패하면 그 구간 이후는 복구가 끊겨요. 보관 기간은 실수 데이터를 발견하는 데 걸리는 시간보다 길게 잡되, 숫자 한도는 운영 정책으로 정해요.

## 상황별 선택 기준

개발 데이터를 다른 환경으로 옮기면 pg_dump가 맞아요. 서버 전체를 같은 메이저로 되살릴 준비면 물리 백업을 추가해요. 잘못된 갱신을 시간 단위로 되돌려야 하면 PITR이 필요해요. 하나만 고르기보다, 논리 백업으로 시작하고 복구 목표가 생기면 물리를 더하는 순서가 현실적이에요.

## 복원 절차와 검증

논리 복원은 빈 데이터베이스에 덤프를 적용하고, 물리 복원은 데이터 디렉터리를 교체한 뒤 기동해요. 복원 후 애플리케이션 계정으로 읽기, 최근 행, 확장 설치 여부를 확인해요. 백업 파일 크기만 보고 성공으로 두지 마세요. 연습 복원을 주기적으로 해야 절차가 남아요.

## 주의할 점

백업을 같은 디스크에만 두면 디스크 장애에 같이 죽어요. 덤프에 개인정보와 비밀번호가 들어가면 보관 권한이 운영 데이터와 같아요. 메이저 버전이 다르면 물리 백업은 바로 기동하지 못해요. 복원 명령을 운영 인스턴스에 잘못 실행하면 데이터를 덮어요.

## 자주 묻는 질문

무엇을 먼저 둘지, 보관 위치, PITR 준비, 논리 백업의 한계를 자주 물어요.

### pg_dump와 pg_basebackup 중 무엇을 먼저 도입해야 하나요?

객체 단위로 옮기고 내용을 검토할 수 있는 pg_dump를 먼저 두는 팀이 많아요. 서버 전체 복구가 목표면 pg_basebackup을 추가해요. 둘은 대체재가 아니라 복구 목표가 달라요.

### 백업 파일은 운영 서버와 같은 곳에 두어도 되나요?

임시 생성 위치로는 될 수 있지만, 보관은 다른 디스크와 다른 권한으로 옮겨요. 같은 곳만 있으면 서버 장애 때 백업도 없어요. 전송 뒤 원본 임시 파일은 정책에 따라 지워요.

### PITR은 어떻게 준비하나요?

베이스 백업과 그 이후 WAL 아카이브가 끊기지 않게 해요. 아카이브 실패 알림이 없으면 복구 시점에야 알아요. 복구 연습으로 목표 시점까지 재생되는지를 확인해요.

### 논리 백업만으로 장애 복구가 가능한가요?

데이터베이스 내용을 다시 만드는 복구는 가능해요. 장애 직전의 마지막 트랜잭션까지 되돌리려면 WAL이 필요해요. 역할과 설정 파일은 덤프 범위 밖일 수 있어요.

GitHub Actions 자동배포는 푸시나 수동 실행으로 워크플로를 깨워, 러너가 배포 명령을 대신 실행하는 구조예요. 서버에 SSH로 스크립트를 돌리거나, 이미지를 만들어 레지스트리에 올리거나, 클라우드 권한을 짧게 위임할 수 있어요. 시크릿, 동시 실행, 환경 보호 규칙을 빼면 배포가 겹치거나 키가 로그에 남아요. 아래는 방식 비교와 워크플로를 만드는 순서예요.

## 한눈에 보기

워크플로는 저장소의 정해진 경로에 두고, 이벤트와 잡을 선언해요. 잡 안의 단계는 위에서 아래로 실행되고, 한 단계가 실패하면 뒤는 실행되지 않아요. 운영 배포는 환경에 묶어 승인 규칙과 시크릿을 나눌 수 있어요. 자동배포가 알려 주는 것은 명령 성공이지, 서비스가 요청을 받는지는 헬스 체크로 따로 확인해야 해요.

## 배포 방식 비교

표는 SSH 원격 실행, 컨테이너 이미지, 클라우드 연동을 자격 증명과 롤백 관점으로 나눈 거예요. 이미 서버에 배포 스크립트가 있으면 SSH가 가장 짧아요. 인스턴스가 여러 대면 이미지 태그를 바꾸는 편이 예측이 좋아요. 장기 키를 저장소에 두기 싫으면 짧은 위임 방식을 검토해요. 방식과 상관없이 시크릿 이름과 러너가 대상에 닿는지는 먼저 확인해요.

| 항목 | 서버에서 직접 pull | SSH 원격 실행 | 이미지 빌드 후 배포 |
| --- | --- | --- | --- |
| 준비 난이도 | 낮음 | 보통 | 높음 |
| 서버 접속 정보 위치 | 서버 내부 키 | 저장소 시크릿 | 레지스트리 자격 증명 |
| 빌드 부하 위치 | 대상 서버 | 러너 | 러너 |
| 롤백 방법 | 이전 커밋으로 재배포 | 이전 커밋으로 재배포 | 이전 이미지 태그로 교체 |
| 잘 맞는 상황 | 단일 소규모 서버 | 단일·소수 서버, 기존 운영 방식 유지 | 다수 인스턴스, 무중단 교체 |

## 단계별로 만드는 자동배포

서버 준비, 시크릿, 워크플로 파일, 첫 실행 순서로 가면 실패 위치가 분명해져요.

### 저장소와 서버 준비

배포할 브랜치를 정하고, 서버에는 그 브랜치만 받을 계정과 배포 스크립트를 둬요. 스크립트는 코드 갱신, 의존성, 재시작, 헬스 체크 순서가 좋아요. 재시작 직후 바로 성공으로 보지 말고, 응답할 때까지 기다린 뒤 실패하면 이전 상태로 되돌리는 분기를 넣어요.

### 시크릿 등록

개인 키가 필요하면 저장소 또는 환경 시크릿에 넣고, 워크플로에서는 그 이름만 참조해요. 호스트 이름과 사용자도 시크릿이나 변수로 빼면 로그에 고정 값이 덜 남아요. 포크에서 온 풀 리퀘스트에는 시크릿이 전달되지 않으니, 외부 기여로 배포가 돌면 안 돼요.

### 워크플로 파일 작성

푸시와 수동 실행을 같이 두고, 운영 배포는 동시 실행 그룹으로 겹치지 않게 해요. 진행 중인 배포를 취소하지 않으면 이전 배포가 중간에 끊기지 않아요. 아래 예시는 체크아웃 뒤 SSH 키를 준비하고 알려진 호스트를 등록하는 앞부분이에요. 실제 배포 명령은 그 다음 단계에서 서버의 스크립트를 호출하면 돼요. 키 파일 권한이 느슨하면 SSH가 거절해요.

```yaml
name: deploy

on:
  push:
    branches: [main]
  workflow_dispatch:

concurrency:
  group: deploy-production
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: SSH 키 준비
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          ssh-keyscan -H "${{ secrets.SSH_HOST }}" >> ~/.ssh/known_hosts

      - name: 원격 배포 스크립트 실행
        run: |
          ssh "${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}" 'bash -s' < scripts/deploy.sh
```

### 첫 실행과 로그 확인

파일을 기본 브랜치에 푸시하면 Actions 탭에서 실행이 보여요. 실패한 단계의 로그에서 시크릿 이름, 호스트 키, 방화벽, 스크립트 종료 상태를 나눠 봐요. 명령이 성공해도 서비스 로그와 헬스 체크를 한 번 더 봐야 사용자 요청이 살아 있는지 알 수 있어요.

## 상황별 선택

서버가 하나고 스크립트가 있으면 SSH 원격 실행으로 시작해요. 같은 이미지를 여러 곳에 맞출 때는 레지스트리 배포가 롤백도 이전 태그로 단순해요. 클라우드 권한은 장기 키 대신 짧은 위임을 검토해요. 승인이 필요하면 환경 보호 규칙으로 검토자 승인 뒤에만 진행되게 해요. 외부에서 서버에 못 들어가면 그 망 안의 셀프 호스티드 러너를 쓰되, 러너 업데이트는 직접 맡아야 해요.

## 주의할 점

시크릿은 로그에서 가려지지만, 스크립트가 값을 변형해 출력하면 가림이 풀려요. 디버그 출력에 키를 찍지 마세요. 동시 배포를 허용하면 재시작이 겹쳐 롤백 지점이 흐려져요. 워크플로 권한을 기본보다 넓게 열면 토큰이 할 수 있는 일이 커져요. 배포 스크립트의 성공과 애플리케이션 성공을 같은 단계로 두지 마세요.

## 자주 묻는 질문

비용 조건, 롤백, 접속 불가, 겹치는 커밋이 자주 나와요.

### github actions 자동배포는 무료인가요?

공개 저장소와 비공개 저장소의 포함 범위는 계정 플랜과 문서 기준으로 달라요. 분 단위 한도 숫자는 여기 적지 않고, 과금 문서를 봐요. 셀프 호스티드 러너는 깃허브 사용량 과금과 별도로 그 머신의 운영이 남아요.

### 배포가 실패하면 자동으로 롤백되나요?

기본 워크플로는 실패하면 멈출 뿐, 이전 배포로 되돌리지는 않아요. 롤백은 스크립트나 이후 단계에 직접 넣어야 해요. 이미지 배포라면 이전 태그를 다시 가리키는 단계를 실패 분기에 둘 수 있어요.

### 서버에 직접 접속할 수 없는 환경에서도 쓸 수 있나요?

깃허브 호스티드 러너가 서버에 닿지 않으면 SSH 배포는 실패해요. 그 망 안에 러너를 두거나, 서버가 바깥으로 이미지를 당겨 가게 구성을 바꿔요. 방화벽에서 러너 접속을 열기 전에 키가 유출돼도 할 수 있는 일을 제한해요.

### 배포 중에 새 커밋이 올라오면 어떻게 되나요?

동시 실행을 제한하지 않으면 두 배포가 겹쳐요. 그룹을 두고 진행 중 취소를 끄면 지금 배포가 끝난 뒤 다음이 돌아요. 취소를 켜면 이전 배포가 중간에 끊기니, 스크립트가 중간에 끊겨도 안전한지 먼저 봐요.

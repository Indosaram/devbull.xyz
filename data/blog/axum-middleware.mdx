axum 미들웨어는 핸들러 앞뒤를 감싸는 tower 레이어예요. 공통 로그와 헤더는 함수로 붙이고, 추적이나 CORS처럼 정형화된 일은 tower-http 레이어를 조합하는 편이 안전해요. 어디에 붙이느냐에 따라 없는 경로에도 실행되는지, 매칭된 라우트에만 실행되는지가 갈려요. 아래는 작성 방법, 적용 위치, 본문을 건드렸을 때 생기는 실수를 순서대로 정리해요.

## 한눈에 보기

요청은 라우터에서 레이어를 지나 핸들러로 가고, 응답은 반대로 빠져나와요. 그래서 레이어는 핸들러 진입 전과 응답이 나가기 전, 두 지점에 끼어들 수 있어요. 상태가 필요 없으면 from_fn, 풀이나 설정이 필요하면 from_fn_with_state를 써요. 연결 단위로 세밀하게 제어할 때만 Layer를 직접 구현하면 되고, 대부분은 from_fn으로 충분해요. 공통 처리와 업무 로직을 나누지 않으면 순서와 책임이 금방 섞여요.

## 미들웨어 방식 비교

손으로 자주 쓰는 쪽은 from_fn 계열이고, 추적·CORS·압축은 이미 있는 레이어를 붙이는 영역이에요. 표는 상태 접근, 요청 전후 처리, 재사용성을 나눠 둔 거예요. 상태 없는 로그와 헤더 주입은 from_fn, 인증처럼 공유 상태가 필요하면 from_fn_with_state가 맞아요. Layer 직접 구현은 난도가 높으니, 함수로 안 되는 요구가 생길 때까지 미루는 편이 좋아요.

| 항목 | from_fn | from_fn_with_state | tower::Layer 직접 구현 | tower-http 레이어 |
| --- | --- | --- | --- | --- |
| 작성 난이도 | 낮음 | 낮음 | 높음 | 매우 낮음 |
| 상태 접근 | 불가 | 가능 | 가능 | 레이어 설정으로 대체 |
| 요청 전 처리 | 가능 | 가능 | 가능 | 레이어마다 다름 |
| 응답 후 처리 | 가능 | 가능 | 가능 | 레이어마다 다름 |
| 추천 용도 | 로깅, 헤더 주입 | 인증, 설정 전달 | 연결 단위 제어 | 추적, CORS, 압축 |
| 재사용성 | 보통 | 보통 | 높음 | 높음 |

## 단계별로 미들웨어 작성하고 적용하기

의존성을 고르고, 함수를 작성한 뒤, 라우터의 어느 층에 붙일지 정하는 순서예요. 코드 예시는 각 단계 아래에 그대로 두었어요.

### 의존성 준비

Cargo.toml에 axum과 함께 tower, tower-http를 넣어요. tower-http는 쓰는 기능만 feature로 켜면 빌드가 가벼워져요. 추적, CORS, 압축, 타임아웃 가운데 실제로 응답에 필요한 것만 활성화하면 돼요.

### from_fn으로 기본 미들웨어 작성

가장 단순한 형태는 요청을 읽고 next.run을 호출하는 함수예요. 호출 전이 요청 단계, 호출 후가 응답 단계예요. 반환은 Response로 두고, 핸들러가 만든 응답을 그대로 돌려주면 업무 로직을 바꾸지 않아요. 아래 예시는 메서드와 경로를 남긴 뒤 상태 코드를 찍어요.

```rust
use axum::{
    extract::Request,
    middleware::Next,
    response::Response,
};

async fn log_request(request: Request, next: Next) -> Response {
    let method = request.method().clone();
    let path = request.uri().path().to_string();

    // 요청 단계: 핸들러 진입 전에 할 일을 여기서 처리해요
    let response = next.run(request).await;

    // 응답 단계: 핸들러가 만든 응답을 그대로 받아요
    println!("{method} {path} -> {}", response.status());
    response
}
```

### 상태가 필요한 미들웨어 작성

설정이나 공용 클라이언트가 필요하면 from_fn_with_state를 써요. 인자 순서는 상태 추출기, 요청, Next가 일반적이에요. 상태는 Clone이어야 하고, 라우터에 넘긴 상태와 같은 타입이어야 해요. 헤더 값이 잘못된 문자면 삽입이 실패할 수 있으니, 미들웨어에서 패닉으로 연결을 끊지 않게 실패를 갈라 두세요.

```rust
use axum::{
    extract::{Request, State},
    http::HeaderValue,
    middleware::Next,
    response::Response,
};

#[derive(Clone)]
struct AppState {
    service_name: String,
}

async fn tag_response(
    State(state): State<AppState>,
    request: Request,
    next: Next,
) -> Response {
    let mut response = next.run(request).await;

    if let Ok(value) = HeaderValue::from_str(&state.service_name) {
        response.headers_mut().insert("x-service", value);
    }

    response
}
```

### Router에 적용하기

작성한 함수는 layer 또는 route_layer로 붙여요. layer는 라우터 전체를 감싸서, 매칭되는 라우트가 없어도 실행돼요. route_layer는 라우트가 맞을 때만 실행돼요. 인증처럼 핸들러에 닿기 전에 막아야 하는 일은 route_layer에 두면 의도가 분명해요. 상태 레이어는 with_state로 넘긴 값과 같이 붙어요.

```rust
use axum::{middleware, routing::get, Router};

let state = AppState {
    service_name: "api".to_string(),
};

let app = Router::new()
    .route("/health", get(health))
    .route_layer(middleware::from_fn(log_request))
    .layer(middleware::from_fn_with_state(state.clone(), tag_response))
    .with_state(state);
```

### tower-http 레이어 조합

추적, 압축, CORS는 직접 만들지 않고 tower-http에서 가져와요. 모든 오리진을 허용하는 설정은 개발 중에만 편하고, 운영에서는 허용 오리진과 메서드를 좁혀야 해요. 나중에 추가한 레이어가 바깥쪽에서 먼저 요청을 보니, 추적 레이어를 가장 바깥에 두면 전체 구간을 관찰하기 좋아요.

```rust
use tower_http::{
    compression::CompressionLayer,
    cors::CorsLayer,
    trace::TraceLayer,
};

let app = Router::new()
    .route("/health", get(health))
    .layer(TraceLayer::new_for_http())
    .layer(CompressionLayer::new())
    .layer(CorsLayer::permissive());
```

## 상황별 선택 기준

이 처리가 라우트를 아는지부터 보면 위치가 정해져요. 모든 요청의 추적과 로그는 tower-http 추적 레이어를 먼저 붙여요. 인증은 from_fn_with_state로 쓰고 route_layer에 두며, 공개 라우트와 보호 라우트를 라우터로 나누면 경계가 분명해요. 응답 헤더만 고칠 때는 응답을 매핑하는 쪽이 읽기 쉬워요. 본문 검사가 필요하면 소비와 복원을 같이 해야 해서, 추출기나 핸들러가 더 나은 경우도 많아요.

## 주의할 점

본문은 한 번 읽으면 사라지니, 검사만 하고 끝내면 핸들러는 빈 본문을 받아요. 분해한 뒤 다시 조립하는 흐름을 아래 예시처럼 유지해야 해요. 레이어 순서가 바뀌면 CORS와 압축처럼 서로 영향을 주는 기능의 결과가 달라지고, 복잡해지면 ServiceBuilder로 한 번에 선언하는 편이 읽기 좋아요. route_layer는 매칭 실패 때 실행되지 않아서, 없는 경로에도 공통 헤더가 필요하면 layer를 써요. 미들웨어 안에서 오래 걸리는 외부 호출을 그대로 두면 요청 전체가 밀리니, 시간 제한을 같이 두거나 블로킹 작업은 별도 경로로 빼요. 에러 응답 형식도 핸들러와 맞추지 않으면 클라이언트가 원인을 읽기 어려워요.

```rust
use axum::{body::Body, extract::Request, middleware::Next, response::Response};

async fn inspect_body(request: Request, next: Next) -> Response {
    let (parts, body) = request.into_parts();
    let bytes = axum::body::to_bytes(body, usize::MAX).await.unwrap();

    // 본문을 다시 붙여야 핸들러가 읽을 수 있어요
    let request = Request::from_parts(parts, Body::from(bytes));
    next.run(request).await
}
```

## 자주 묻는 질문

적용 위치와 본문, 순서가 질문을 가장 많이 만들어요.

### axum middleware와 tower 레이어는 같은 건가요?

axum 미들웨어는 tower의 레이어와 서비스 위에 있어요. from_fn은 함수 하나로 레이어를 만들게 감싼 도구이고, 안에서는 tower 조합으로 동작해요. 그래서 tower 생태계 레이어를 라우터에 그대로 붙일 수 있어요.

### 미들웨어에서 요청 본문을 읽어도 되나요?

가능하지만 기본 선택으로 두지는 않는 편이 좋아요. 읽은 뒤 다시 넣지 않으면 핸들러가 빈 본문을 받고, 큰 본문을 메모리에 올리면 부담이 커져요. 검증이 목적이면 추출기나 핸들러에서 처리하는 쪽이 경계가 분명해요.

### 특정 라우트에만 미들웨어를 적용하려면 어떻게 하나요?

보호할 경로만 별도 라우터로 만들고 거기에 route_layer를 붙인 뒤, 상위 라우터에 합치면 돼요. 공개 경로와 보호 경로의 경계가 코드 구조에 그대로 보여요.

### 적용 순서는 어떻게 결정되나요?

나중에 추가한 레이어가 바깥쪽에서 먼저 요청을 받아요. 응답은 안에서 바깥으로 지나가요. 추적을 가장 바깥에 두면 전체 구간을 한 줄로 보기 좋아요.

### from_fn과 from_fn_with_state 중 무엇을 먼저 고려해야 하나요?

상태가 없으면 from_fn으로 시작해요. 풀이나 설정이 필요해지면 from_fn_with_state로 바꾸면 되고, 차이는 인자 하나라 옮기기 부담이 크지 않아요.

Axum은 PDF를 만드는 라이브러리가 아니라, 만든 바이트를 HTTP 응답으로 내보내는 웹 프레임워크예요. 생성은 별도 크레이트가 하고, Axum은 경로, 헤더, 상태 코드, 전달 방식을 맡아요. 큰 파일을 요청마다 메모리에 올리면 서버가 밀리니, 생성 위치와 응답 방식을 먼저 나눠요. 아래는 역할 분리, 헤더, 블로킹 작업을 런타임 밖으로 빼는 순서예요.

## 한눈에 보기

클라이언트가 원하는 것은 PDF 바이트와 올바른 콘텐츠 유형이에요. 핸들러는 입력을 검증하고, 생성은 전용 함수에 맡기고, 응답은 바이트와 헤더를 감싸요. 생성이 CPU를 오래 쓰면 비동기 런타임을 막지 않게 블로킹 작업으로 분리해요. 파일명과 다운로드 여부는 Content-Disposition으로 정해요. 테스트는 상태 코드와 헤더, 본문 앞부분이 PDF 형식인지를 같이 봐요.

## Axum과 PDF 처리 역할 비교

표는 라우팅, 생성, 헤더, 대용량 전달을 어느 층이 맡는지 나눈 거예요. Axum 라우터는 경로와 추출기, PDF 크레이트는 문서 구성, tower-http는 압축이나 제한처럼 공통 처리에 써요. 생성 라이브러리를 핸들러 안에 직접 펼치면 테스트와 재사용이 어려워져요. 실패하면 PDF가 아닌 오류 응답을 같은 형식으로 돌려요.

| 구분 | Axum이 맡는 일 | PDF 쪽에서 결정할 일 | 운영 시 확인할 점 |
|---|---|---|---|
| 라우팅 | 경로와 메서드 정의, 핸들러 연결 | 문서 식별자와 생성 요청 구분 | 권한 검사 위치와 경로 충돌 |
| 생성 | 생성 작업을 호출하거나 큐에 위임 | 라이브러리, 템플릿, 폰트, 이미지 처리 | 실패 재시도와 작업 상태 관리 |
| 응답 | 헤더와 본문 반환 | 바이트 크기, 스트리밍 가능 여부 | 메모리 사용량과 타임아웃 |
| 정적 파일 | 라우트에서 파일 제공기로 위임 | 파일 저장 위치와 이름 규칙 | 캐시, 범위 요청, 접근 제어 |
| 보안 | 인증·인가 미들웨어 적용 | 민감 정보 포함 여부 | 파일명 정규화와 헤더 인젝션 방지 |
| 관측 | 로그, 추적, 오류 응답 | 생성 시간과 실패 원인 기록 | 사용자별 남용 탐지와 감사 로그 |

## 단계별 구현 방법

경로를 나누고, 바이트를 응답으로 감싸고, 헤더를 명시한 뒤, 크기와 블로킹 여부를 봐요.

### 라우트와 핸들러를 분리합니다

다운로드 경로와 미리보기 경로를 나누면 헤더 정책이 분명해져요. 핸들러는 식별자와 권한만 확인하고, 문서 내용은 서비스 함수가 돌려주게 해요. 쿼리로 레이아웃을 모두 받지 말고, 서버에 정의된 서식만 고르게 하면 입력이 안전해요.

### PDF 바이트를 응답으로 감쌉니다

생성 결과가 바이트라면 그 바이트를 본문으로 두고 성공 상태로 돌려요. 생성이 실패하면 PDF 본문 대신 오류 응답을 돌려요. 빈 바이트를 성공으로 내보내면 클라이언트가 깨진 파일로 받아요.

### 헤더를 명시합니다

콘텐츠 유형은 PDF로 두고, 파일을 저장하게 하려면 Content-Disposition에 파일명을 넣어요. 파일명에 한글이나 공백이 있으면 헤더 인코딩 규칙을 지켜요. 캐시가 되면 안 되는 개인 문서면 캐시 제어도 같이 닫아요.

### 큰 파일은 스트리밍을 검토합니다

한 번에 메모리에 올리지 않아도 되면 스트림으로 본문을 내보내요. 생성이 끝나기 전에 응답을 열면 중간 실패를 상태 코드로 바꾸기 어렵다는 점을 알고 선택해요. 작은 문서면 바이트 응답이 더 단순해요.

### 생성 작업은 비동기 런타임 밖으로 분리합니다

PDF 조판은 CPU를 붙잡는 일이 많아요. 그런 작업은 블로킹 풀로 넘겨 다른 요청의 런타임을 막지 않게 해요. 공식 문서의 spawn_blocking 설명을 기준으로 적용하면 돼요. 대기 시간이 길면 요청 시간 제한도 같이 정해요.

### 테스트는 헤더와 본문을 함께 확인합니다

상태 코드만 보면 빈 파일도 통과해요. 콘텐츠 유형, 파일명 헤더, 본문이 PDF 시그니처로 시작하는지 같이 검사해요. 권한 실패는 PDF가 아닌 오류인지 별도 케이스로 둬요.

## 상황별 선택 기준

요청 한 번에 작은 문서를 만들면 핸들러에서 생성 후 바이트 응답이 맞아요. 배치로 많은 문서를 만들면 작업을 큐에 넣고 완료 뒤 저장소 주소를 주는 편이 요청 시간을 지키기에 좋아요. 이미 만들어진 파일을 내려 주기만 하면 생성 크레이트 없이 파일 응답이면 충분해요. 브라우저에서 바로 열지, 저장만 할지는 Disposition으로 갈라요.

## 주의할 점

사용자 입력을 PDF에 그대로 넣으면 레이아웃이 깨지거나 의도하지 않은 내용이 들어갈 수 있어요. 폰트가 배포 이미지에 없으면 로컬에서만 글자가 보여요. 임시 파일을 디스크에 쓰면 요청 종료 때 지워요. 압축 레이어를 켜면 일부 클라이언트가 PDF 처리를 헷갈릴 수 있으니, 다운로드 경로는 압축 제외를 검토해요.

## 자주 묻는 질문

내장 기능인지, 스트리밍이 되는지, 파일명을 어떻게 주는지를 자주 물어요.

### 질문: Axum에 PDF 생성 기능이 내장되어 있나요?

없어요. Axum은 HTTP 계층이고, PDF 조판은 별도 크레이트를 골라 붙어요. 고를 때는 폰트, 라이선스, 비동기와의 궁합을 문서에서 봐요.

### 질문: PDF를 메모리에 올리지 않고 스트리밍할 수 있나요?

본문을 스트림으로 내보낼 수 있어요. 다만 생성 도중 실패하면 이미 헤더를 보낸 뒤라 상태 코드로 돌리기 어려워요. 실패를 먼저 확정할 수 있는 작은 문서는 바이트 응답이 안전해요.

### 질문: PDF 다운로드 파일명은 어떻게 지정하나요?

Content-Disposition 헤더의 파일명으로 지정해요. 브라우저가 바로 열게 하려면 inline, 저장 창을 내려면 attachment를 써요. 특수문자가 있으면 헤더 값 규칙을 지켜요.
